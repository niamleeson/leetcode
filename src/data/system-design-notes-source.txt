@@ dropbox
Understanding the Problem
- Build cloud file storage with uploads, downloads, sharing, and synchronization across a user's devices.
- Separate file bytes from file metadata. Object storage handles large immutable objects; the application handles ownership, permissions, and versions.

Functional Requirements
- Upload and download files from any device.
- Share files with other users and list files shared with the current user.
- Synchronize local changes to the cloud and cloud changes to other devices.
- Editing files in the browser and previewing their contents are outside the core scope.

Non-functional Requirements | 1
- Support files up to 50 GB without restarting an entire upload after a network failure.
- Prioritize availability, durable storage, secure access, and fast transfers.
- Metadata may propagate asynchronously, but permission checks and upload completion must remain authoritative.

Core Entities | 2
- File: raw bytes stored in object storage, identified independently from its display name.
- FileMetadata: file ID, owner, name, size, content type, storage location, version, and upload status.
- SharedFiles: user ID and file ID mapping, plus permissions. Index by user to efficiently list incoming shares.
- ChangeEvent and upload-part records support synchronization and resumable transfers.

API
- Create an upload session with metadata; return a file ID and signed upload instructions.
- Request a download URL after authenticating the user and checking access to the file.
- Share a file with another user and list files owned by or shared with the caller.
- Fetch changes since the last synchronization cursor; acknowledge or complete an upload only after server verification.
- Derive the caller's identity from a validated session token, rather than a user ID supplied in the request body.

High-Level Design

1) Upload files | 3,4,5
- Storing files on an application server couples capacity and availability to that server and makes horizontal scaling difficult.
- Forwarding every upload through the application to object storage fixes durability but doubles the transfer path and consumes application bandwidth.
- Prefer a metadata request followed by direct client-to-object-storage transfer using a short-lived presigned URL.
- Save metadata as pending first. Mark the file available after confirming the object or multipart upload actually exists.

2) Download and share files | 6,7
- The file service checks permissions and returns a signed object-storage or CDN URL; file bytes bypass application servers.
- Use a CDN for geographically distributed downloads. Private content still requires signed URLs or equivalent authorization.
- An embedded share list is simple, but finding all files shared with a user becomes expensive.
- A separate user-to-file table supports that query directly and avoids maintaining conflicting copies of the share relationship.

3) Synchronize devices | 8,9
- A local watcher detects changed files and uploads changed content, updating the authoritative metadata version.
- Other devices consume change events and download newer content. Push notifications improve responsiveness; cursor-based polling recovers missed events.
- Track create, update, and delete events. Retain tombstones long enough for offline devices to observe deletions.
- Compare versions before overwriting content; concurrent local edits require an explicit conflict policy rather than silent data loss.

Deep Dives

1) Large files and resumable uploads | 10
- Split large files into independently retryable parts and record an upload ID, part numbers, and returned ETags.
- Resume by asking which parts already exist, uploading only missing parts, then completing the multipart upload.
- Client reports are hints. Verify parts with the storage provider before marking them complete; ordinary object-created events do not report every multipart part.
- Use file and chunk fingerprints to recognize repeated uploads and avoid transferring unchanged content.
- Clean up abandoned upload sessions and incomplete parts after a bounded retention period.

2) Transfer performance
- Upload independent parts concurrently within bandwidth and memory limits; expose progress using confirmed uploaded bytes.
- Fixed-size chunks are simple, but an insertion shifts subsequent boundaries. Content-defined chunking can preserve reuse after edits.
- Compress when the bandwidth savings exceed CPU cost; already compressed media may gain little. Compress before encryption.
- Cache popular downloads near users and avoid caching every private file indefinitely.

3) Security
- Encrypt transfers with TLS and stored files with storage encryption; keep encryption keys separate from application data.
- Recheck access before issuing a signed URL and choose a short expiration because an issued bearer URL remains usable until expiry.
- Verify upload size, type, ownership, and completion on the server. Never trust a client-provided storage key to authorize access.

Final Design | 11
- Clients transfer file bytes directly to object storage or the CDN; the file service manages metadata, permissions, and signed URLs.
- Multipart state and server verification make uploads resumable without declaring incomplete files ready.
- A change feed, device cursors, and version checks connect independent uploads into reliable synchronization.
- Scale metadata services separately from storage bandwidth and background processing.

High-Level Design

1) Search businesses | 3
- The search service queries indexed business data and applies distance and other filters.
- Start with database indexes appropriate to the access patterns; a full scan for every nearby-business query will not scale.
- Return business summaries and rating aggregates without fetching every review.

2) Read details and write reviews | 4,5
- Fetch business details by primary key and reviews by business ID; cache popular business pages.

- Keep the review and its effect on aggregate rating consistent through a transaction or a clearly defined asynchronous projection.
- Invalidate or refresh cached detail data after changes; search freshness may follow a separate update pipeline.

Deep Dives

1) Maintain average ratings | 6,7
- Computing an average over every review on each search is expensive; store rating sum and review count instead.
- A scheduled aggregation job reduces write coupling but leaves results stale between runs.
- Synchronous updates provide fresher results. Use atomic increments or version-checked transactions to prevent concurrent reviews from overwriting each other.

- PostgreSQL with full-text and spatial extensions is a simpler alternative when it meets the workload.
- Choose based on actual query and scale requirements; specialized search adds operational cost and eventual consistency.

4) Search named locations
- Resolve a city or neighborhood name to a region or polygon, then run the spatial query within that boundary.
- Disambiguate duplicate names and distinguish a named area from a simple radius around a point.
- Cache stable geographic metadata; exact business eligibility still depends on the business coordinates.

Final Design | 10
- A durable business/review database owns the records and uniqueness rules.
- Search indexes handle discovery; caches accelerate frequently viewed details.
- Rating aggregates and index updates use explicit consistency and recovery rules, so performance improvements do not silently lose reviews.

@@ dealing-with-contention
The Race Condition | 1
- A read-check-write sequence is unsafe when multiple requests can act on the same old value.
- Examples include booking one seat, decrementing inventory, accepting the highest bid, and claiming a driver.
- State the invariant first, then place its validation and update inside an atomic boundary.

The Solution

1) Conditional writes
- Make the database update conditional on the current state, such as available quantity being sufficient or a version matching.
- Check affected-row count to distinguish success from a lost race; do not assume an executed statement changed a row.
- A unique constraint can enforce one record per logical identity more reliably than a prior application-level existence check.

2) Pessimistic locking | 2
- Lock the relevant rows, read their current state, apply the update, and commit a short transaction.
- Competing writers wait rather than independently proceeding with stale state.
- Acquire multiple locks in a consistent order and handle deadlock or timeout failures with bounded retries.
- Never hold a transaction open while a person checks out or an external network request runs; represent longer claims as durable reservations.

3) Optimistic concurrency control
- Read state with a version and write only if that version is unchanged.
- A conflict means another writer won; reload and re-evaluate the business rule before retrying.
- This works well with modest contention, but repeated conflicts can waste substantial work on a hot resource.
- Use a monotonically changing version to detect state that changed and later returned to the same visible value.

4) Isolation levels | 3
- Read committed prevents dirty reads but does not make every multi-statement invariant safe.
- Repeatable-read or snapshot isolation provides stable snapshots but can still allow anomalies such as write skew depending on the database.
- Serializable isolation targets serial-equivalent behavior, often by aborting conflicting transactions that the application must retry.
- Choose isolation and explicit constraints from the required invariant, not from a vague claim that transactions solve all races.

5) Distributed locks
- Use shared locks when the protected action cannot fit within one database's transaction or conditional-write boundary.
- Locks need unique ownership tokens, bounded leases, safe release, and renewal behavior.
- A paused worker may resume after its lease expires. Fencing tokens let the protected resource reject that stale worker's writes.
- A lock service cannot make an external side effect transactional; downstream idempotency and recovery still matter.

Choosing the Right Approach
- Prefer a conditional update for a simple invariant and a database transaction for related records in one store.
- Use optimistic checks when conflicts are uncommon and short pessimistic transactions when contention makes retries expensive.
- Introduce distributed coordination only when the protected state actually crosses the simpler boundary.
- Separate a fast atomic claim from a longer workflow such as payment or fulfillment.

Common Deep Dives | 4,5
- Prevent deadlocks by ordering locks consistently, limiting lock scope, and retrying aborted transactions.
- Prevent the ABA problem with versions that change on every transition, even if the visible value returns to its original state.
- A single highly contested resource has a serialization limit; queues, admission control, partitioned inventory, or combining operations may reduce contention.
- More application servers do not increase the throughput of one exclusively locked row.
- Make retries idempotent so a lost response does not repeat an already completed side effect.

Conclusion | 6
- Describe the invariant, atomic boundary, conflict response, and crash recovery together.
- The correct primitive is the one that still prevents invalid state under concurrent requests, timeouts, retries, and delayed workers.

- TTL limits staleness but does not provide immediate consistency.

@@ kafka
Overview
- Kafka is a durable distributed event log used to decouple producers and consumers, retain events, and support replay.
- It can serve queue-like workloads through consumer groups, while independent groups process the same retained events separately.

A Motivating Example | 1,2,3,4,5
- Producers publish match events, and separate consumers update scoreboards, statistics, and notifications.
- Partitioning lets unrelated matches process in parallel while a key keeps one match's events ordered.

Basic Terminology and Architecture
- Brokers store partitions; a topic groups partitions belonging to one event stream.
- Each partition is an ordered append-only log with offsets identifying positions.
- A consumer group assigns each partition to at most one active consumer in that group.
- Ordering is per partition, not automatically across the entire topic.

How Kafka Works | 6,7,8
- Producers select a partition, commonly using a key, and append records containing a payload and optional metadata.
- A partition leader accepts writes and followers replicate them; acknowledgements and in-sync replica settings affect durability.
- Consumers fetch records and track committed offsets independently from producer writes.
- Committing before processing risks loss after a crash; committing after processing permits duplicates that must be handled safely.
- Retention is based on configured time, size, or compaction policy rather than simply deleting a record when one consumer reads it.

- Partition count bounds useful parallelism for one consumer group; extra consumers beyond available partitions remain idle.
- Choose keys for both ordering and load distribution. One popular key remains a hot partition.
- Batch and compress records to reduce network and storage overhead.
- Put references to large files in events instead of using the log as an unbounded media-transfer path.
- Adding partitions can change key routing; consider its effect on ordering during transitions.

- Replication and leader election recover from broker failure according to the configured acknowledgement and replica policies.
- Use an appropriate replication factor, acknowledgements, and minimum in-sync replicas for the loss tolerance.
- Consumer-group rebalances move partition ownership; processors must stop cleanly and resume from safe offsets.
- Monitor consumer lag and retained capacity so a long outage does not outlast the data needed for recovery.

Handling Retries and Errors | 9
- Idempotent producers reduce duplicates caused by retrying an uncertain append.
- Consumer side effects still need idempotency or compatible transactions; producer idempotence alone does not make the entire pipeline exactly once.
- Retry transient failures with an explicit strategy, and isolate poison records through retry or dead-letter topics where appropriate.
- Retrying later can affect ordering, so decide whether a failed record blocks its partition or moves to a separate recovery path.

When to Use and Summary
- Use Kafka for replayable event pipelines, stream processing, and multiple independent downstream consumers.
- A simpler work queue may be preferable when built-in visibility timeouts, delayed delivery, or per-message retry management dominate the requirements.
- Explain partition keys, consumer groups, offset commits, retention, and failure semantics whenever Kafka is central to the design.

- Tables represent related entities, primary keys identify rows, and foreign keys enforce supported relationships.
- Atomicity means all-or-nothing transaction effects; consistency means preserving declared invariants.
- Isolation describes concurrent transaction behavior; durability concerns committed data surviving failures under the configured guarantees.
- SELECT reads data; INSERT, UPDATE, and DELETE modify it; schema and transaction commands define structure and execution boundaries.

Summary
- Start with a sound schema, explicit constraints, and query-driven indexes.
- Scale measured bottlenecks and retain clear transaction, replication, and recovery semantics as infrastructure grows.

@@ flink
Overview | 1
- Flink runs distributed stateful computations over event streams.
- It is useful when continuous aggregation, joins, event-time windows, or pattern detection require more than a simple stateless consumer.

Basic Concepts | 2
- Sources ingest records and sinks write results; operators transform, filter, group, join, or aggregate streams.
- keyBy partitions related records to the same logical keyed state.
- Parallel operator instances process different partitions, with network exchanges where the graph requires redistribution.
- A hot key can limit one operator instance even when overall parallelism is high.

State
- Keyed state associates values with each logical key, such as a running count or recent event history.
- Operator state belongs to an operator instance and must be redistributed appropriately when parallelism changes.
- Bound state with TTL, window cleanup, or explicit lifecycle rules so an infinite stream does not imply infinite memory or disk growth.
- Store large raw payloads outside computation state when references are sufficient.

Watermarks and Windows | 3
- Event time comes from the event; processing time is when the worker handles it.
- Watermarks estimate how far event time has progressed and help decide when a window can produce results.
- Tumbling windows do not overlap; sliding windows overlap; session windows group activity separated by bounded gaps.
- Late events require an allowed-lateness and correction or side-output policy.
- A stalled source partition can hold back watermark progress unless idleness and source behavior are handled appropriately.

Basic Use
- Define a job graph, configure sources, serializers, state, parallelism, and sinks, then submit it to the cluster.
- A metrics dashboard can aggregate event counts and write current results to a serving store.
- Fraud detection can maintain recent per-account state and evaluate event sequences as they arrive.
- Keep application rules distinct from transport guarantees; a correct checkpoint does not make a flawed aggregation correct.

How Flink Works | 4,5
- The JobManager coordinates scheduling and recovery; TaskManagers execute parallel operator work.
- Task slots allocate execution resources, while operator parallelism determines how work is divided.
- Network shuffles, serialization, state access, and sink throughput can become bottlenecks.
- Backpressure propagates upstream when downstream operators or sinks cannot keep up.

State Backends and Checkpoints
- State backends determine where active state lives and how it is accessed; choose from expected size and latency requirements.
- Checkpoints capture recoverable operator state and source positions consistently across the dataflow.
- After failure, restore state and replay from the corresponding source positions.
- Exactly-once internal state recovery does not automatically make an arbitrary external API side effect exactly once.
- End-to-end guarantees require compatible transactional or idempotent sinks and replayable sources.
- Savepoints support controlled upgrades or migration, with compatibility and state evolution planned explicitly.

In Your Interview
- Propose Flink for high-volume continuous computation with event-time or stateful requirements.
- Name the partition key, state, windows, late-data policy, and sink behavior.
- Explain recovery and hot-key handling, and monitor lag, checkpoint duration, backpressure, and state growth.
- A small stateless queue worker may be simpler when these capabilities are unnecessary.

Conclusion
- Flink combines parallel operators, managed state, and coordinated recovery.
- Its value comes from the required computation semantics; correctness still depends on keys, time handling, state bounds, and external sink contracts.

@@ zookeeper
Overview
- ZooKeeper coordinates distributed processes using small replicated records, ordered writes, sessions, and change notifications.
- It is a coordination service, not a general-purpose high-volume application database or message broker.

A Motivating Example | 1,2,3,4,5
- Servers need a shared view of membership, configuration, and ownership without relying on one process's memory.
- Durable coordination lets a replacement discover who owns a shard or whether a leader's session has expired.
- The protected application still needs to reject stale owners after coordination changes.

ZooKeeper Basics | 6,7,8
- Znodes form a hierarchical namespace and contain small data values and version metadata.
- Persistent znodes survive clients; ephemeral znodes are tied to a session; sequential znodes receive ordered suffixes.
- An ensemble uses a leader and quorum-based replication for ordered updates.
- Watches notify clients about relevant changes, but clients must reread state and reestablish applicable watches rather than treating notifications as a complete durable event log.

Key Capabilities

1) Configuration and service discovery
- Store small configuration records with versions and notify interested processes when they change.
- Services can register ephemeral membership records so expired sessions eventually remove dead members.
- Cached membership can become stale; callers still need connection failure handling and retry logic.

2) Leader election and locks
- Ephemeral sequential znodes can order contenders; the lowest eligible sequence owns leadership or a lock.
- Watching the predecessor reduces the herd effect compared with waking every contender on each release.
- Session expiration releases ephemeral ownership, but a paused old process may continue executing afterward.
- Use fencing tokens or version checks at the protected resource to reject work from an obsolete owner.

How ZooKeeper Works | 9
- ZAB orders and replicates updates through the ensemble with quorum agreement.
- Writes are coordinated; reads can be served by individual replicas and may require additional synchronization when a particular freshness guarantee is needed.
- Client session ordering and globally ordered writes do not imply every arbitrary read is immediately the latest state.
- Sessions use heartbeats and timeouts; a transient disconnection differs from a confirmed expired session.
- Durable logs and snapshots support recovery, while quorum availability determines whether coordination writes can proceed.

Handling Failures
- On reconnect, inspect current state rather than assuming previously held ownership remains valid.
- An uncertain create operation may have succeeded before its response was lost; use identifiable records to reconcile safely.
- Keep coordination payloads and request rates small so application traffic cannot overwhelm the ensemble.
- Operate an appropriate odd-sized ensemble across failure domains and monitor latency, sessions, storage, and quorum health.

When to Use | 10,11
- ZooKeeper fits leader election, shard ownership, service coordination, and infrastructure designs needing ordered shared metadata.
- Smart routing can read an ownership map and send requests directly to responsible servers.
- Modern systems may use alternatives such as etcd, Consul, managed coordination, or database primitives depending on their required guarantees.
- Avoid adding a coordination cluster when a single database conditional write already enforces the needed invariant.

Summary
- ZooKeeper supplies coordination primitives; applications compose them into discovery, election, and locking protocols.
- Session handling, watch recovery, and fencing are essential parts of those protocols.
- Keep the data plane separate from the coordination plane and state exactly which operation needs quorum-backed agreement.
