@@ dropbox
Understanding the Problem
- The service stores files in the cloud. Users can upload, download, share, and synchronize files across their devices.
- File bytes and metadata have separate storage. Object storage keeps large, immutable objects. The application manages ownership, permissions, and versions.

Functional Requirements
- Users can upload and download files from any device.
- Users can share files with other users. They can also list files that other users share with them.
- The service sends local changes to the cloud. It sends cloud changes to the other devices.
- The initial design does not include a browser editor or file previews.

Non-functional Requirements | 1
- The service supports files up to 50 GB. After a network failure, the client can continue an upload.
- The design needs high availability, durable storage, secure access, and fast transfers.
- Metadata updates can reach devices at different times. Permission decisions and upload completion must use authoritative state.

Core Entities | 2
- File: the bytes in object storage. Its identifier does not depend on its display name.
- FileMetadata contains the file ID, owner, name, size, content type, storage location, version, and upload status.
- SharedFiles connects a user ID to a file ID and its permissions. An index on user ID supports shared-file lists.
- ChangeEvent records support synchronization. Records for each upload part let the client continue an interrupted transfer.

API
- The client creates an upload session with metadata. The API returns a file ID and signed upload instructions.
- The service authenticates the user before it returns a download URL. It also verifies access to the file.
- The API supports file sharing. It lists files that the caller owns or has permission to access.
- The client requests changes after its last synchronization cursor. The server verifies an upload before it acknowledges completion.
- The service gets the caller's identity from a validated session token. A user ID in the request does not establish identity.

High-Level Design

1) Upload files | 3,4,5
- Files on an application server depend on that server's capacity and availability. Additional application servers cannot automatically access those files.
- An application server can forward uploads to object storage for durability. However, each byte crosses two transfer paths. This consumes application bandwidth.
- The client first requests upload metadata. Then it uploads directly to object storage with a presigned URL that expires soon.
- The service first saves pending metadata. It marks the file available only after it verifies the object or completed multipart upload.

2) Download and share files | 6,7
- The file service verifies permissions. It returns a signed URL for object storage or a CDN. File bytes bypass application servers.
- A CDN supports downloads across regions. Private files still need signed URLs or an equivalent authorization method.
- A share list inside each file record is simple. However, a query for all files shared with one user is expensive.
- A separate table connects users to files. It supports this query directly. One share record also avoids conflicting copies of permissions.

3) Synchronize devices | 8,9
- A local watcher detects a file change. The client uploads the changed content. The service updates the authoritative metadata version.
- Other devices read change events and download new content. Push notifications reduce delay. Polling from a saved cursor recovers missed events.
- The change feed records file creation, updates, and deletion. A production design can retain deletion markers for offline devices.
- The article uses last-write-wins for concurrent edits. This can discard an older edit. Version checks and conflict copies are possible extensions.

Deep Dives

1) Large files and resumable uploads | 10
- The client divides a large file into parts. Each part supports a separate retry. The client records the upload ID, part numbers, and returned ETags.
- To continue an upload, the client requests the list of existing parts. It uploads missing parts. Then it completes the multipart upload.
- Client reports do not prove completion. The server verifies parts with the storage provider. Ordinary object-created events do not describe every multipart part.
- File and chunk fingerprints identify repeated content. The client can avoid another transfer of unchanged bytes.
- A cleanup job removes abandoned sessions and incomplete parts after a defined retention period.

2) Transfer performance
- Independent parts can upload concurrently within bandwidth and memory limits. The progress display counts bytes that the provider has confirmed.
- Fixed-size chunks are simple. However, an insertion changes later chunk boundaries. Content-defined chunking can retain reusable chunks after an edit.
- Compression is useful when bandwidth savings exceed CPU costs. Previously compressed media can have little additional reduction. Compression occurs before encryption.
- The cache keeps popular downloads near users. Private files do not need unlimited cache retention.

3) Security
- TLS protects transfers. Storage encryption protects stored files. Encryption keys have separate storage from application data.
- The service verifies access before it issues a signed URL. The URL expires soon because its holder can use it until expiration.
- The server verifies upload size, type, ownership, and completion. A storage key from the client does not establish access permission.

Final Design | 11
- Clients transfer bytes directly through object storage or a CDN. The file service manages metadata, permissions, and signed URLs.
- Multipart records let uploads continue after failures. Server verification prevents the service from presenting incomplete files as ready.
- The change feed and each device's last synchronization position connect separate uploads into a synchronization process.
- Metadata services, storage transfers, and background workers can scale separately.

@@ yelp
Understanding the Problem
- The service lists nearby businesses. Users can read business details and submit reviews.
- The design combines geographic search, text filters, and ratings. Review writes must remain correct as search traffic increases.

Functional Requirements
- Users can search by location, text, category, and rating.
- Users can read business details and existing reviews.
- A user can submit a rating and review. Each business permits at most one review from that user.
- The initial design does not include advanced recommendations or tools for business owners.

Non-functional Requirements | 1
- Most requests read search results or business details. The target search latency is below 500 ms. The design supports 100 million daily users and 10 million businesses.
- Business discovery needs high availability. The database must retain reviews and enforce the rule for unique reviews.
- Search indexes and cached ratings can lag behind the database. The design must specify the maximum acceptable delay.

Core Entities | 2
- Business contains its ID, name, description, category, address, coordinates, and combined rating fields.
- Review contains the business ID, author ID, rating, text, and timestamps.
- User identifies the authenticated reviewer. A unique composite key on user ID and business ID prevents duplicate reviews.
- Location contains a region name and its geometry. It supports searches within a city or neighborhood.

API
- Search requests contain text, latitude and longitude, radius, category, rating filters, and an optional pagination cursor.
- The client requests business details by business ID. It reads reviews in separate pages.
- A review request contains the business ID, rating, and text. The service gets the author from authentication.
- The response includes a cursor with a stable result order. This avoids large offsets as the user reads more results.

High-Level Design

1) Search businesses | 3
- The Business Service queries indexed business data. It applies distance and other filters.
- Database indexes must support the required queries. A full scan for each nearby-business search cannot support large traffic volumes.
- Search results contain business summaries and combined ratings. The service does not need to read every review for each result.

2) Read details and write reviews | 4,5
- The service reads business details by primary key. It reads reviews by business ID. A cache stores frequently requested business pages.
- Before commit, the Review Service validates the author, the 1-5 rating range, and the business record.
- A transaction can keep the review and combined rating consistent. An asynchronous projection is another option with defined update rules.
- After a change, the service updates or removes cached details. A separate process can update the search index.

Deep Dives

1) Maintain average ratings | 6,7
- An average across all reviews is expensive to calculate for each search. The database can store the rating sum and review count.
- A scheduled job updates combined ratings separately from review writes. Its results remain stale between runs. Diagram 6 shows this alternative.
- Synchronous updates produce fresher ratings. The article uses optimistic locking to prevent lost updates. Diagram 7 shows this approach.
- For an edited review, the service adds the difference between the old and new rating. The review count stays the same.
- An optimistic conflict needs a bounded retry. A popular business can need batches of rating updates or asynchronous aggregation.

2) Enforce one review per user
- Two requests can both find that a review does not exist. A separate insertion after this check permits a race.
- A unique constraint on the user and business pair prevents duplicate reviews. It also applies to concurrent requests and retries.
- The API must define repeated submissions. It can edit the existing review or return a conflict.

3) Search complex queries | 8,9
- Elasticsearch combines inverted indexes, text relevance, geographic filters, and sorting. However, the service must maintain a second data model.
- Change data capture sends committed database changes to Elasticsearch through a stream and consumer. Failed updates need retries or an index rebuild.
- PostgreSQL with text and spatial extensions can provide a simpler design if it supports the required load.
- Query and capacity requirements determine the search technology. A separate search system adds maintenance work and eventual consistency.

4) Search named locations
- The service converts a city or neighborhood name into a region or polygon. Then it searches within that boundary.
- Different places can have the same name. The service must identify the intended place. A named region differs from a radius around coordinates.
- The service can compute each business's named areas when it creates the business. A keyword index on area identifiers avoids repeated polygon checks.

Final Design | 10
- The durable database owns business and review records. It enforces the uniqueness rules.
- Search indexes support business discovery. Caches make repeated requests for details faster.
- Combined ratings and search indexes need explicit consistency and recovery rules. Faster queries must not cause the loss of reviews.

@@ local-delivery-service
Understanding the Problem
- The service lists products that nearby distribution centers can deliver. Customers can order several items together.
- Availability depends on location and stock. A browsing result does not guarantee that the same stock will remain at checkout.

Functional Requirements
- Customers can query items that distribution centers can deliver to their location within one hour.
- Customers can place one order for several items. Availability combines stock from eligible distribution centers.
- Concurrent orders must not claim the same physical stock.
- Payments, driver routing, product search, cancellations, and returns are outside the initial scope.

Non-functional Requirements | 1
- Availability requests should take less than 100 ms. They must scale separately from order writes.
- Orders require consistent stock updates. Checkout must check current inventory even when the browsing result came from a cache.
- The text assumes 10,000 distribution centers, 100,000 catalog items, and approximately 10 million daily orders. Order records must survive failures.

Core Entities | 2
- Item describes a product type. Its identifier is the same across distribution centers.
- DistributionCenter contains the physical location and its delivery area.
- Inventory identifies physical stock at a distribution center. The quantity model groups this stock by center and item ID.
- Order and OrderItem record the customer, selected inventory, quantities, and delivery information.

API | 3
- GET /v1/availability accepts the customer's coordinates and pagination parameters. It returns available items and quantities.
- POST /v1/order accepts the location and requested items. A production API can add an idempotency key for safe retries.
- The order response contains the committed order or an inventory conflict. The service checks delivery eligibility again during checkout.

High-Level Design

1) Find available items | 4,5,6
- The Nearby Service first identifies distribution centers near the customer. The initial version uses geographic distance.
- The Availability Service reads inventory for those centers. It adds quantities across eligible centers and returns the combined result.
- An index on distribution center and item ID avoids a scan of all inventory.
- Product metadata changes less often than inventory quantities. Separate cache policies can reflect these different update rates.

2) Place an order | 7,8
- The Orders Service checks stock and records the order within one PostgreSQL transaction. The transaction also updates inventory.
- A serializable transaction, row locks, or conditional updates can protect stock. A separate application check cannot prevent concurrent claims.
- A multi-item order must fail as a unit if any item is unavailable. Consistent lock order reduces deadlock risk.
- Separate inventory and order databases require coordination and recovery after partial failure. One transactional database avoids that extra work.
- Payments are outside this article's scope. If added, slow payment calls must occur outside the short inventory transaction.

Deep Dives

1) Incorporate traffic and driving time | 9,10,11
- Geographic distance does not account for roads, rivers, or traffic. A nearby center can still exceed the delivery limit.
- A travel-time request for every center is expensive. The Nearby Service keeps an updated local copy of center locations.
- The service first filters centers by a generous geographic radius. It asks the Travel Time Service about only those candidates.
- Only centers within the delivery-time limit remain eligible. Any cached travel estimate needs an expiration that reflects traffic changes.

2) Scale availability reads | 12,13,14
- Redis can store availability results in a cache. On a miss, the Availability Service reads PostgreSQL and fills the cache.
- Cached quantities can be stale. The Orders Service still checks authoritative inventory and invalidates affected cache entries after a write.
- Read replicas serve browsing traffic. Regional partitions keep queries near the distribution centers they need.
- A practical cache key should group requests with the same eligible centers. Every arbitrary coordinate would provide poor cache reuse.
- A popular product or center can receive concentrated traffic. Capacity checks must include these local peaks.

Final Design
- The Nearby Service selects eligible centers. The Availability Service reads their inventory through the chosen cache or replica path.
- The Orders Service writes inventory and order records together on the PostgreSQL leader.
- A geographic filter reduces the number of calls to the Travel Time Service.
- Browsing can tolerate a short update delay. Checkout must still reject stock that another order has claimed.

- Booking groups one customer's tickets under a durable ID. It records the total price and payment state.

- A reservation request claims selected tickets temporarily. The response contains a booking ID and expiration time.
- A confirmation request supplies the booking ID and payment token. A status endpoint can support recovery after a lost response.
- Each state change checks current ownership and purchase state. A reservation created earlier may have expired or changed owners.

1) Browse and search | 3,4
- The Event Service reads event, venue, and performer records from the database. The initial Search Service also queries that database.
- The deep dives add caches and Elasticsearch. Committed database changes must reach the search index.
- Seat availability changes more often than event descriptions. It needs a shorter refresh period and authoritative booking checks.

2) Book tickets | 5
- The initial Booking Service checks ticket availability and creates a booking within one PostgreSQL transaction.
- The database must reject a competing claim. Row locks or optimistic concurrency checks protect the ticket update.
- This initial design checks availability after the user enters payment details. The reservation deep dive improves that experience.
- Payment callbacks can repeat. An idempotent handler must return or retain the existing booking result without another purchase.

Deep Dives

1) Reservation expiry | 6
- A database transaction must not remain open while the customer completes checkout. Long locks block other work and occupy connections.
- One alternative stores a reserved state and expiration in PostgreSQL. A short transaction can reclaim an expired reservation.
- A cleanup job can remove expired state. Correctness must also check expiration during a new claim.
- Diagram 6 uses Redis ticket locks with a ten-minute lifetime. PostgreSQL still prevents duplicate purchases if a lock expires or fails.
- Final confirmation must check the current booking and ownership. A late payment for an invalid booking needs reconciliation or a refund.

2) Scale event views | 7
- A load balancer distributes requests across stateless Event Service instances.
- Redis or Memcached can store event metadata. Separate read capacity protects booking work from browsing spikes.
- Cache expiration and invalidation limit stale results. The Event Service can show live reservations using entries with expiration timestamps.

3) Handle high-demand onsales | 8
- SSE can send seat changes to connected browsers. This reduces repeated polling but cannot guarantee that a displayed seat remains available.
- A virtual waiting room admits customers at a rate that the Booking Service can support.
- The source stores admitted sessions in Redis with an expiration. The Booking Service checks admission before it accepts reservations.
- Queue position updates help waiting customers. A reconnect must preserve queue identity. Admission alone does not reserve a seat.

4) Improve search | 9
- Database indexes and full-text search can support the first design. Elasticsearch supports more complex text queries and spelling variations.
- Change data capture updates Elasticsearch from PostgreSQL. Search caches must include every relevant filter in their keys.
- A search result can become stale before checkout. CDN caching is suitable only when the same query returns equivalent public results.

Final Design | 10
- The Event Service serves cached event details. The Search Service uses Elasticsearch and suitable query caches.
- The Booking Service uses expiring Redis reservations and conditional PostgreSQL writes. Stripe callbacks update each booking idempotently.
- The waiting room controls admission during popular events. Seat updates improve the display while the booking database protects ownership.

@@ tinder
Understanding the Problem
- The application recommends profiles using preferences and distance. A match occurs when both users make a positive swipe.
- Discovery can tolerate some stale data. Swipe handling needs coordination so concurrent positive swipes do not lose a match.

Functional Requirements
- Users can create profiles, set preferences, and choose a maximum distance.
- Users can request a stack of eligible profiles.
- Users can swipe yes or no on each profile. Both users receive a notification when their positive swipes form a match.
- Photo uploads, chat after matching, and premium features are outside the initial scope.

Non-functional Requirements | 1
- The stack should load in less than 300 ms. The scenario assumes 20 million daily users and about 100 daily swipes each.
- Concurrent swipes must not lose a mutual match. A retry must not create a second match or duplicate visible notification.
- Geographic queries and swipe-history checks must scale without scanning every profile or historical swipe for each request.

Core Entities | 2
- UserProfile stores profile metadata and preferences. The current request supplies location because the user can move.
- Swipe records the initiating user, target user, decision, and time.
- Match connects two users. A canonical pair key can identify one match regardless of which user swiped last.
- CandidateStack is a temporary list of recommended profiles. The service refreshes it when necessary.

API
- POST /profile updates the authenticated user's preferences and maximum distance.
- GET /feed accepts current coordinates and returns another bounded stack. This recommendation flow does not require conventional page numbers.
- POST /swipe/:userId records a decision about the target profile. Authentication identifies the user making the swipe.
- The swipe response can report an immediate match. APNS or FCM notifies the user who swiped earlier.

High-Level Design

1) Profiles and candidate stacks | 3,4
- The Profile Service stores profile settings in the Profile DB. The initial stack query reads that database directly.
- The query filters candidates by preferences and location. The deep dive adds geographic indexes and a stack cache.
- The final candidate filter excludes profiles that do not meet current rules or have already received a swipe.
- A later design precomputes small stacks for active users. It refreshes them as users consume them or change preferences.

2) Swipes and matches | 5,6
- The Swipe Service persists the decision in Cassandra. It checks whether the target user already made a positive reverse swipe.
- A simple write and reverse-read sequence needs stronger coordination under concurrency. The deep dive adds atomic matching on a shared pair key.
- A canonical pair ID and unique match constraint make repeated detection safe. The same pair should not create another match.
- The second swiper sees the match in the response. APNS or FCM sends a push notification to the first swiper.

Deep Dives

1) Consistent low-latency swiping | 7
- A transactional store can protect a pair's swipe state and match decision when they share one transaction boundary.
- A sorted pair of user IDs sends both directions to the same partition. Partition placement alone does not make separate operations atomic.
- Cassandra lightweight transactions provide conditional operations within their supported scope. A normal batch cannot combine an arbitrary read and write transaction.
- The illustrated Redis design atomically records one decision and reads the reverse decision with a Lua script. Cassandra retains durable history.
- Redis failover can lose recent acknowledged writes. Durable capture, replay, and reconciliation are required before claiming failure-safe match guarantees.

2) Fast candidate generation | 8,9,10
- Elasticsearch can combine geographic and preference filters. Change data capture keeps its profile data aligned with the primary database.
- Periodic jobs precompute stacks in the Stack Cache. Those stacks can become stale after location or preference changes.
- The hybrid design serves cached candidates first. It queries Elasticsearch to replenish a low stack and applies current eligibility checks.
- Stack size, expiration, and active-user thresholds limit background work. Significant preference or location changes trigger a refresh.

3) Exclude previous swipes | 11,12
- A full history query becomes expensive for users with many swipes.
- The backend checks durable swipe history. A client-side Swipe Cache filters recent decisions that storage replicas may not yet expose.
- A Bloom filter can reject likely previous swipes with little memory. False positives can hide profiles that the user has never seen.
- Exact swipe records still determine matches. A Bloom filter cannot enumerate history and needs a rebuild after cache loss.

Final Design | 13
- The Profile DB, Elasticsearch, and Stack Cache support profile discovery and replenishment.
- The Swipe Service needs atomic matching and durable recovery. The Redis matching alternative appears in diagram 7.
- Push notifications inform matched users. Client-side swipe history and optional Bloom filters reduce repeated recommendations.

@@ dealing-with-contention
The Race Condition | 1
- A separate read, check, and write leaves time for another request to change the resource. Both requests can then claim the same item.
- Common examples include seats, inventory, bids, and driver assignments. Identify the exact resource that concurrent requests share.
- State the rule that must always hold. Enforce its check and update together at the authoritative store.

The Solution

1) Conditional writes
- Make a write conditional on current state. For example, decrement inventory only when enough units remain, or claim only an available seat.
- Check the affected-row count. Zero changed rows means the claim failed; the database may not raise an error for that result.
- A count protects total inventory, not a specific seat. Guard the seat's own row or enforce a unique seat identity.

2) Pessimistic locking | 2
- When application logic must read before deciding, lock the relevant rows first. Validate and update them in one short transaction.
- Another writer must wait or skip locked candidates. It cannot independently change the protected rows while the first transaction holds them.
- Acquire multiple locks in a consistent order. Handle deadlock or timeout errors with bounded retries of the complete transaction.
- Keep payment calls and customer checkout outside the transaction. Store a reservation with an expiry for a longer claim.

3) Optimistic concurrency control
- Optimistic concurrency reads a version with the data. The write succeeds only if that version still matches, then increments it.
- A failed version check means another writer changed the record. Reload current state and reconsider the operation before retrying.
- Optimistic checks work well when conflicts are rare. Under heavy contention, repeated failed work can cost more than a short lock.
- Use a version that changes on every update. A business value that returns to its previous value can hide an intervening change.

4) Isolation levels | 3
- Read committed prevents dirty reads but does not protect every rule spanning several statements or rows.
- Snapshot-style isolation can still allow write skew. Two transactions can update different rows and together violate a shared rule.
- Serializable isolation requires a result equivalent to some serial order. The database can abort conflicting transactions; the application must handle retries.
- Match isolation and constraints to the actual rule. Another option makes the conflict visible on one shared row that can be guarded.

5) Distributed locks
- A lease records who holds a resource and when the hold expires. Use it when the claim must outlive a short transaction.
- Redis can create a lease atomically with a TTL. A database can conditionally update owner and expiry fields on the resource row.
- A stalled holder can resume after its lease expires. Validate current ownership when applying effects; stricter designs may require fencing tokens.
- ZooKeeper and etcd provide coordination services with their own failure guarantees. External side effects still need idempotency and recovery.

Choosing the Right Approach
- Start with a conditional write when one predicate describes the rule. Use a transaction for related writes in the same database.
- Choose optimistic checks for rare conflicts. Choose short pessimistic transactions when application decisions and frequent conflicts make retries expensive.
- Use serializable isolation or a shared guard row for write skew. Add distributed coordination only when the required boundary demands it.
- Separate a short inventory claim from a longer payment workflow. A lease preserves the claim without holding a transaction open.

Common Deep Dives | 4,5
- Consistent lock order prevents circular waits. Keep lock scope short and retry transactions the database aborts after detecting a deadlock.
- A value can change from A to B and back to A. A monotonically increasing version reveals this ABA change.
- One hot resource still has a serial capacity limit. A queue can send its requests to one worker at a controlled rate.
- More application servers do not increase one row's exclusive write capacity. Split independent inventory or control admission when the product allows it.
- Make retries safe when responses disappear after commit. A retry must not repeat a completed charge or create another successful claim.

Conclusion | 6
- Describe the invariant, authoritative store, atomic operation, and conflict response together. Include crash recovery and expired ownership.
- Choose a primitive that protects the rule during concurrent requests and failures. Keep the protected data in one authoritative store where possible.

@@ multi-step-processes
The Problem | 1
- A workflow can call several services and wait on people or external systems. One database transaction cannot cover all those operations.
- A server can crash after an external action succeeds but before it records the result. An unsafe retry can repeat that action.

Solutions

1) Single-server primitives | 2,3
- The simplest API Server calls Payment, Inventory, Shipping, and Email Services in sequence. A crash can erase its in-memory progress.
- Save completed steps in an Order State DB. A callback can then reach another server, which loads the state and continues.
- Shared state alone does not restart stalled work. The application still needs ownership, retries, callback routing, and compensation.

2) Saga pattern
- A saga performs a sequence of local transactions. If a later step fails, compensating actions reverse the relevant earlier effects.
- Compensation is another operation, not a rollback of history. A refund creates a new financial event after an earlier charge.
- Store saga progress durably. Both forward actions and compensations must tolerate repeated attempts.
- Identify irreversible actions and unresolved results. Some failed compensations need reconciliation or human intervention.

3) Event-driven choreography | 4
- In choreography, workers consume events and publish the next outcomes. The sequence follows event subscriptions instead of one central coordinator.
- Kafka or Redis Streams can retain the event history. Workers resume from committed positions after failures and may process an event again.
- Correlation IDs connect related events across services. The log preserves evidence, but tracing a complex workflow still requires suitable tooling.
- Choreography fits moderately complex, loosely coupled flows. Changes in the middle require coordinated event-contract changes across neighboring workers.

4) Workflow orchestration | 5
- In orchestration, one workflow definition selects activities, retries, timers, and compensations. Temporal records the decisions and results durably.
- The Temporal Server schedules tasks and records history. Workflow Workers run workflow code; Activity Workers perform external operations.
- Workflow decisions must replay deterministically. On recovery, recorded activity results replace completed calls, while uncertain activities may need another attempt.
- Signals and durable timers support long waits without holding a worker thread or database transaction. A later event resumes the correct workflow.
- Temporal describes workflows in code. AWS Step Functions and Google Cloud Workflows use managed state machines, with different operational and programming tradeoffs.

When to Use | 6
- Use workflows for payment, fulfillment, reservations, and human approval. They fit processes with several steps and meaningful partial-failure handling.
- A simple database transaction or single queued task usually does not need a workflow engine. Each workflow adds persistence and scheduling overhead.
- Choose the engine after defining retries, compensation, and wait behavior. Be ready to explain its recovery model.

Common Deep Dives

1) Crashes and exactly-once effects
- Record each confirmed step durably. After a crash, a replacement must know what completed and what remains uncertain.
- An activity can finish externally while its completion report is lost. The engine may then attempt that activity again.
- Use stable idempotency keys or provider status lookup for repeated attempts. Retain uncertain in-progress outcomes for reconciliation.
- Durable orchestration does not make an arbitrary payment or email execute exactly once. The external effect needs its own protection.

2) Workflow changes
- Old workflow histories must remain compatible with the code that replays them. Version or patch behavior when changing the sequence.
- Keep old worker versions for existing workflows when needed. A migration must define how in-flight executions reach the new behavior.
- Include workflows waiting on timers and signals in deployment checks. Testing only new executions misses replay failures.

3) History size and external events
- Keep large data outside workflow history. Pass durable identifiers that an activity can use to retrieve the payload.
- Bound long-running histories with supported continuation mechanisms. Temporal Continue-as-New starts a new run with selected current state.
- Correlate callbacks with the workflow ID. Validate and deduplicate signals so repeated or late callbacks do not advance the wrong process.
- Use durable timeouts for external waits. Define reminder, cancellation, and human-resolution paths when the expected event does not arrive.

Conclusion
- A reliable workflow needs durable state and retry-safe actions. An in-memory function alone cannot provide crash recovery.
- Compensation, idempotency, compatible code changes, and reconciliation make cross-service workflows recoverable. The engine manages progress; activities still own their effects.

@@ scaling-reads
The Problem
- Queries slow down when they scan too much data or compete for limited resources. Joins and repeated aggregates can add further work.
- Identify the common queries and acceptable data age first. These requirements determine whether indexes, replicas, or caches will help.

The Solution

1) Optimize the existing database | 1,2,3
- Add indexes for frequent filters, joins, and sort orders. Inspect the query plan to confirm that the database uses them effectively.
- Composite index column order matters. An index beginning with status may help status queries but not a query on creation time alone.
- Indexes use storage and require updates during writes. Add useful indexes, then measure their read benefit and write cost.
- More memory can keep frequently used data resident. Faster storage or additional CPU can help when the corresponding resource is the bottleneck.
- Denormalization duplicates data to reduce joins. Materialized views precompute aggregates; both require a plan to update derived values.

2) Scale database reads horizontally | 4,5,6
- Read replicas distribute queries away from the primary database. Asynchronous replication can lag, so direct freshness-sensitive reads to an appropriate source.
- Replicas do not reduce the primary's write workload. Each replica can still require the full dataset.
- Sharding divides data across databases. It reduces each node's dataset but makes cross-shard queries and transactions more complex.
- Functional shards separate business domains; geographic shards place data near users. Choose boundaries that fit common queries and avoid concentrated traffic.

3) Application caching | 7
- Cache-aside first checks Redis or Memcached. On a miss, the application reads the database and stores the result in the cache.
- Store repeated, expensive results in a cache with a useful hit rate. Keys must distinguish every input that changes the returned data.
- Define expiry, invalidation, memory limits, and failure behavior. The permitted data age should guide the cache policy.
- The database normally remains authoritative. A cache hit provides the data under the chosen freshness rules, not automatic immediate consistency.

4) CDN and edge caching | 8
- A CDN serves shared content near users. Cache hits reduce both geographic delay and traffic to the origin server.
- Configure cache keys and response headers correctly. Public shared data fits CDN caching better than private per-user responses.
- Version immutable assets. Mutable content needs expiry or explicit invalidation, including a plan for propagation across edge locations.

When to Use
- Read scaling fits feeds, search, profiles, product pages, and dashboards with repeated queries. Estimate the high-volume endpoints before choosing infrastructure.
- A small system may only need efficient indexed queries. Add another distributed component when a measured requirement justifies it.
- Cached inventory displays can be advisory. Checkout must still validate and claim authoritative inventory before confirming a purchase.

Common Deep Dives

1) Growing datasets
- As data grows, inspect indexes, selectivity, and scanned rows. A full scan can explain slow lookups without any increase in query complexity.
- Use bounded pagination and limit reads to relevant partitions. Avoid repeatedly scanning unrelated history to return a small page.
- Precompute repeated aggregates in materialized views or rollups. Define how updates reach these derived results.

2) Hot keys and stampedes
- One hot cache key can overload its node. Replicate that value across keys on different nodes, then invalidate every copy when necessary.
- Coalesce simultaneous requests for the same entry. One loader can fetch the result while other local requests share its work.
- Early or scheduled refresh can reduce stampedes at expiry. Stagger refresh work and allow stale responses only within the product's policy.
- A cache failure can suddenly send all traffic to the database. Bound fallback concurrency instead of allowing unlimited simultaneous misses.

3) Invalidation races
- A slow reader can refill a cache with old data after a writer updates the database. Simple deletion does not remove every race.
- The source uses versioned keys: update the record and its version together. Then store the new version in the cache separately.
- Readers must obtain the correct current version. A stale cached version pointer can still select old data; versioned keys alone do not prevent that.
- TTL bounds entry lifetime rather than guaranteeing immediate freshness. Use an authoritative or coordinated read path when the latest state is required.

Conclusion
- Start with efficient queries. Add replicas, derived views, caching, or sharding according to the remaining bottleneck.
- Explain data freshness and cache failure behavior alongside the fast path. Every optimization needs a defined correctness boundary.

@@ scaling-writes
The Challenge | 1
- Each write can update durable data, indexes, and replicas. Shared invariants can also force writes to run in sequence.
- Find the busiest constrained component. Adding application servers does not remove a single hot row or storage bottleneck.

The Solution

1) Vertical scaling and write optimization
- Measure CPU, memory, disk, and network limits before adding distribution. Better hardware can provide useful capacity with less architectural complexity.
- Shorten transactions, reuse connections, and remove unnecessary write work. Batch operations when their ordering and durability rules permit it.
- B-tree and log-structured engines make different tradeoffs. Sequential writes can improve throughput but leave more read or compaction work.
- Cassandra, time-series stores, and column stores fit different workloads. Choose from required operations and durability, not a generic SQL-versus-NoSQL label.

2) Sharding and partitioning | 2,3
- Horizontal sharding spreads records across write owners. Redis Cluster, for example, maps hashed key slots to server nodes.
- Choose a key that spreads write traffic while keeping related reads local. A high number of possible keys alone does not ensure balance.
- A country key can overload populous regions. Hashing user IDs often distributes work better, but unusually active users still need attention.
- Vertical partitioning separates fields with different workloads. Post content, engagement counters, and analytics can use different stores or tables.
- Check how many shards each common read and write touches. Cross-shard operations add coordination, network calls, and failure cases.

3) Queues and load shedding | 4,5
- Kafka or SQS can buffer a short write burst. Workers drain accepted requests at a rate the database can sustain.
- A queue cannot fix permanent undercapacity. If arrivals remain faster than processing, both backlog size and completion delay keep growing.
- Queue acknowledgement means acceptance, not database completion. Provide a status path when callers need to know that the write finished.
- Shed or defer lower-priority writes before overload causes broader failure. For repeated location updates, a later update may replace an older one.

4) Batching and aggregation | 6,7,8,9
- Batching combines small writes to reduce network, transaction, and storage overhead. It adds a delay before the combined operation runs.
- Batch in an application or intermediate processor. Do not acknowledge volatile buffered data as durable unless a replayable source retains it.
- A Like Batcher combines increments per post. Hierarchical Write Processors can aggregate local changes before a Root Processor merges them.
- Broadcast Nodes then distribute the shared result to their clients. Retry and ordering rules must prevent repeated batches from duplicating effects.
- Larger batches improve efficiency only when work combines usefully. One like per post per window provides little aggregation benefit.

When to Use
- This pattern fits telemetry, click processing, search ingestion, feed updates, and live comments. Each can produce more writes than one component handles.
- Estimate normal and peak traffic. Identify whether storage I/O, CPU, network, lock contention, or one key causes the limit.
- Start with a simpler fix when it meets the requirement. Sharding and queues add failure modes and operational work.

Common Deep Dives

1) Resharding
- Reshard gradually while the system remains available. The source proposes copying records while writes reach both old and new locations.
- Dual writes can partially fail. Track and reconcile migration progress before moving read preference or write ownership permanently.
- Consistent hashing reduces how many keys move. It does not itself copy data or protect concurrent updates during migration.

2) Hot keys | 10
- More shards do not divide writes to one key. A viral post can overload even a shard dedicated to that post.
- Split an additive counter into subkeys and combine their values during reads. This trades lower write contention for more read work.
- Split only hot keys when useful. Readers and writers must agree on all active subkeys before the transition can preserve totals.
- Some operations cannot be split independently, such as claiming one specific seat. Keep an authoritative owner and control incoming demand.

Conclusion | 11
- Reduce work per component through local optimization, partitioning, queues, or aggregation. Choose only strategies compatible with the required semantics.
- Monitor queue age, partition load, retries, and storage or replication lag. Total throughput can hide one overloaded component.
- Explain the delay, freshness, and correctness cost of each scaling choice. Higher throughput alone does not establish a successful design.

@@ handling-large-blobs
The Problem | 1
- Large photos, videos, and documents consume application bandwidth and memory. Transfers can exceed request deadlines and overload relational storage.
- Separate permission checks and metadata from file transfer. Application servers manage access. Object storage receives and serves the bytes.

The Solution | 2
- Store file bytes in object storage. Store metadata in a database.
- Give the client temporary permission for a specific transfer. The client sends bytes directly to object storage.
- Use a CDN for frequent downloads. Use multipart uploads for large files or unreliable connections.

1) Direct upload | 3
- The client requests permission to upload a file. The request includes its expected size, type, and owner.
- The server validates the request. It creates pending metadata and signs the upload instructions with its local credentials.
- The client uploads directly to object storage. The backend verifies the completed object before it makes the file available.
- A signed URL permits a specific operation on a specific object. It does not give the client unrestricted storage credentials.

2) Direct download | 4
- The service authenticates the caller. It checks file permissions before it issues a signed download URL.
- The client downloads from object storage or a CDN. A CDN validates its own signed URL or cookie.
- Set the URL lifetime and cache policy to match the content's sensitivity. Define how permission changes affect existing URLs.
- A person with an issued URL can use it until it expires. An application permission change might not revoke it immediately.

3) Resumable uploads | 5
- Split the file into numbered parts. Keep the upload ID and the storage provider's confirmation for each part.
- After an interruption, upload only missing or failed parts. Then ask object storage to assemble the file.
- Limit parallel transfers and part size. These limits prevent excessive client memory use and network connections.
- Expire abandoned upload sessions. Remove incomplete parts to limit storage costs.

4) State synchronization | 6
- The database and object storage do not share one transaction. Track pending uploads separately from completed files.
- Verify a client completion message with a storage API or a trusted storage event.
- Storage events can repeat or arrive late. Make completion updates idempotent. Periodically check uploads that remain pending.
- A multipart event can describe only the completed object. Use the provider's multipart APIs to verify individual parts.

Cloud Provider Terminology
- Providers use different names for signed URLs, multipart uploads, object versions, and completion checks.
- Explain the required capability and its failure behavior. A product name alone does not explain the design.

Common Deep Dives
- If a transfer fails at 99%, resume from verified parts. Do not upload completed parts again.
- Check quotas, maximum file size, permitted content types, and session lifetime before granting access. Quarantine uploads until required scans pass.
- Store the owner, object key, size, checksum, version, and processing state in the database. Keep these records separate from file bytes.
- An ETag is not always a hash of the complete file. Its meaning depends on the provider and upload mode.

Metadata and Download Performance | 7
- Give each immutable object version a separate identity. This simplifies caching and prevents mixed content during replacement.
- Use range requests to resume downloads. A CDN serves popular content near users. Media variants reduce unnecessary transfer size.
- Run scans, thumbnail generation, and transcoding in background workers. Keep this work outside the metadata request.

Conclusion
- Direct signed transfers reduce application bandwidth use. The application still controls permissions, metadata, and completion checks.
- A complete design includes multipart recovery, cleanup, access control, and periodic checks for inconsistent state.

@@ managing-long-running-tasks
The Problem | 1
- Video processing, crawling, report generation, and large fanout can exceed request deadlines. Execution times can also vary widely.
- Synchronous execution keeps the client connection open. Slow tasks consume API capacity while the client waits.

The Solution | 2,3
- Save a job record. Put its reference in a queue. Return the job ID without waiting for execution.
- Separate workers execute the job. They save its status and results.
- Clients poll for status or receive a completion event. Accepting a job does not mean that the job has completed.

Trade-offs
- A queue holds incoming work during traffic peaks. Workers can scale separately from API servers.
- Retries allow recovery from failures. They also require progress tracking, duplicate handling, and monitoring.
- Queue capacity is finite. Limit incoming work and the number of waiting jobs.

How to Implement

1) Message queue | 4
- Choose a queue with suitable durability, ordering, and delivery behavior. Define visibility timeouts and handling for repeated failures.
- Put job IDs and storage references in messages. Keep large media files in object storage.
- A saved job must eventually reach the queue. An outbox or a recovery scan can close a failed publication gap.

2) Workers
- A worker claims a job and records the attempt. It executes within resource and time limits, then saves the result.
- Acknowledge delivery only after the required output is safely stored.
- Renew ownership while a long task runs. Conditional updates must prevent an old worker from replacing a newer result.
- Use separate worker pools when tasks need different hardware. GPU tasks and lightweight tasks should not require identical capacity.

3) End-to-end flow | 5
- The API validates the request and saves a pending job. It then ensures that the queue receives the job reference.
- Workers change job status from pending to running, then to completed or failed. Conditional updates protect these transitions.
- Completion notifications can fail or repeat. The status API returns the stored result when a client reconnects.
- Save progress at useful checkpoints. Avoid a database write for every small operation.

Common Deep Dives

1) Failure and repeated failure | 6
- Retry temporary failures with exponential backoff and jitter.
- Limit attempts. Move persistent failures to a dead-letter queue or inspection state. Keep their error details.
- A worker crash causes ownership to expire or the queue to deliver the job again. Resume from saved checkpoints where possible.

2) Duplicate work | 7
- A queue can deliver a task again after its side effect succeeds. At-least-once delivery does not prevent duplicate execution.
- Give each logical job a stable ID. Use idempotent output locations and the same idempotency key for repeated downstream requests.
- A started record does not prove that work completed. The first worker could have crashed before it produced a result.

3) Backpressure and mixed workloads | 8
- Scale workers using queue depth, waiting time, and resource use. Limit new jobs when the system cannot meet completion targets.
- Use separate queues or reserved capacity for urgent and bulk work. Long tasks must not block all short tasks.
- Limit requests to external services separately from worker count. More workers must not exceed a dependency's rate limit.

4) Dependencies
- Use a durable workflow or dependency graph for related jobs. Avoid workers that wait indefinitely for other workers.
- Start a stage only after its required predecessors complete. Repeated completion events must not start duplicate stages.
- Define cancellation, compensation, and failure handling for workflows that complete only some stages.

Conclusion | 9,10
- Keep durable job state and reliable queue publication. Use recoverable worker ownership and side effects that tolerate retries.
- Limit the backlog and report progress. These controls keep asynchronous work usable during overload or partial failure.

@@ redis
Overview
- Redis stores data structures in memory. Common uses include caches, counters, rankings, coordination, and messaging.
- Choose persistence, replication, eviction, and failure behavior for the intended use. Fast commands do not guarantee durable results.

Redis Basics | 1
- A key identifies a value. Values can be strings, hashes, lists, sets, sorted sets, streams, or geospatial indexes.
- A TTL expires a key. An eviction policy removes keys under memory pressure. These controls solve different problems.
- Redis executes commands one at a time. An atomic command or short script can combine a check with an update.
- Long scripts and large blocking operations delay other commands. Limit the work in each request.

Infrastructure Configurations | 2
- A standalone instance has one capacity limit and one failure boundary.
- Replicas provide copies for reads and failover. Replication is asynchronous, so promotion can lose recent acknowledged writes.
- Redis Cluster maps keys to 16,384 hash slots. Related keys need the same slot for most multi-key operations.
- RDB snapshots and AOF logging provide different recovery guarantees. The persistence settings determine the possible loss window and write cost.

Performance and Caching | 3
- Store values that the application reads repeatedly in the cache. The cache key must identify the correct request parameters and access scope.
- On a cache miss, read the database and populate the cache. Define expiry, invalidation, and protection against simultaneous misses.
- Size the cache for memory, value size, and network traffic. One popular key can limit capacity before average throughput does.
- Batch commands or use pipelining to reduce network round trips. Configure an eviction policy when Redis serves as a cache.

Distributed Locks
- A basic lease uses SET with NX, an expiry, and a unique owner token. Only one request can create the key.
- Release the lease only when the stored token matches. An atomic check-and-delete script prevents deletion of another owner's lease.
- Expiry does not stop a paused worker from resuming. The protected resource needs fencing or another check against stale operations.
- Asynchronous failover can lose a lock grant. Enforce critical invariants in the database or a suitable consensus system.

Leaderboards, Rate Limiting, and Proximity
- A sorted set stores members with scores. Updating a member's score changes its rank without creating a duplicate member.
- Ranked queries retrieve the leading members. Remove low-ranked entries when the application needs only a limited result set.
- A fixed-window limiter increments a counter. Set expiry only for the first request, and perform both operations atomically.
- For a sliding window, atomically remove old entries, count the remaining entries, and record permitted requests in a sorted set.
- Geospatial commands store coordinates and find nearby members. The application still checks location freshness and other search filters.

Streams and Pub/Sub | 4,5
- Streams retain entries with ordered IDs. Consumer groups track pending entries, acknowledgements, and ownership of delivered work.
- Pub/Sub sends messages to current subscribers. It does not retain missed messages for a disconnected subscriber.
- Stream recovery depends on retention and persistence. A Redis crash can lose recent entries under some persistence settings.
- A worker can claim an idle pending entry after another worker stops. Processing must tolerate repeated execution.
- Sharded Pub/Sub routes a channel to its owning node. A subscriber uses one connection per relevant node, not per channel.
- Use native Pub/Sub when its delivery model fits. A custom subscriber registry adds network requests, stale entries, and cleanup work.

Hot Keys | 6
- Sharding distributes different keys. Requests for one popular key still reach its owning primary.
- Local caches, duplicated keys, or configured replica reads can distribute read traffic. Replicas do not distribute writes to one key.
- Local and replicated copies can be stale. Define update and invalidation behavior for every extra copy.

When Not to Use and Summary
- Do not rely on an evicting cache as the only durable record. Persistence and failover settings can also permit data loss.
- Large cold datasets and complex relational queries may need another database. Clustered multi-key operations need careful key placement.
- Specify the data structure, access pattern, failure behavior, and memory policy. These choices explain Redis's role in the design.

@@ elasticsearch
Overview
- Elasticsearch provides distributed search and analytics over documents. Lucene indexes perform the underlying search work.
- An application often keeps authoritative records in another database. Elasticsearch holds a derived search view with indexing delay and rebuild procedures.

Basic Concepts | 1
- A document is a JSON record. An Elasticsearch index groups documents with related mappings and query behavior.
- Mappings define field types. Text fields support analyzed search. Keyword fields preserve exact values for filters, sorting, and aggregations.
- Select date, numeric, nested, and geographic field types for the required queries. Incorrect mappings can make those queries inefficient or impossible.
- A fundamental field-type change can require a new index and reindexing. Plan the transition before changing the data model.

Basic Use
- Create an index and define its mapping. Add documents with IDs that identify their logical records.
- A partial update still requires internal document reindexing. Frequent changes create additional writes, deletion markers, and merge work.
- Use match queries for analyzed text. Use exact filters for constraints that do not need relevance scoring.
- Use geo_point for coordinates and geo_shape for regions. Define whether a search uses distance, intersection, or a named boundary.
- Sort on suitable fields for price, recency, or popularity. Relevance uses a score. Add a stable tie-breaker when ordering must persist.

Pagination and Cursors
- from/size works for shallow pages. Deep offsets require shards to collect and discard many earlier results.
- search_after uses the previous page's final sort values. Keep the same sort order and a unique tie-breaker.
- A point-in-time context preserves a consistent view while documents change. Keep it with the pagination state.
- Close the point-in-time context when finished. Reserve scroll-style traversal for batch extraction where its behavior fits.

How It Works

1) Nodes and shards | 2,3
- Primary shards divide the documents. Replica shards provide additional search capacity and copies for failover.
- Coordinating nodes send queries to relevant shards. They merge shard results and retrieve the selected document fields.
- The elected master manages cluster state and shard allocation. Ingest nodes prepare documents. Data nodes store shards and execute search work.
- More shards permit more parallel work. They also increase coordination, memory use, and overhead for small shards.

2) Lucene segments | 4
- Lucene stores indexed data in immutable segments. A refresh makes recent changes searchable. A write acknowledgement does not imply immediate search visibility.
- An update replaces the logical document and marks the old version as deleted. Background merges consolidate segments and reclaim obsolete data.
- Frequent refreshes improve freshness but consume resources. Merges also need CPU, I/O, and temporary storage.

3) Search data structures | 5
- An inverted index maps terms to document postings. Stored positions support phrase queries where required.
- Doc values store fields in a column-oriented form. They support sorting and aggregations without reading every full source document.
- Reduce the candidate set before expensive scoring or sorting where possible. Selective terms can greatly reduce query work.
- A frequent term or broad query can return many candidates. Evenly distributed documents do not guarantee cheap queries.

In Your Interview
- Explain the search requirement first. Full-text ranking, geographic filters, or complex queries can justify a dedicated search engine.
- Connect database changes to indexing with reliable CDC or another recoverable publication mechanism.
- Track update versions and deletions. A delayed event must not restore an obsolete document.
- If stale permissions could expose restricted data, check current access before returning the content.
- Plan a rebuild and controlled index switch. Include changes that occur while the replacement index is loading.

Summary
- Elasticsearch combines specialized indexes with distributed execution. These features make complex search practical.
- The costs include extra storage, delayed search visibility, shard management, and continuous index maintenance.
- Use it when these trade-offs meet a real query requirement. A simpler query against the primary database may be sufficient.

@@ kafka
Overview
- Kafka is a distributed event log. It separates producers from consumers, retains events, and supports replay.
- A consumer group can distribute work between consumers. Separate groups can each process the same retained events.

A Motivating Example | 1,2,3,4,5
- Producers publish sports events. Consumers read those events and update the website.
- Use a match ID as the key to keep one match's events in one partition. Different partitions can run in parallel.
- Consumer groups distribute partitions between workers. Separate topics keep soccer events separate from basketball events.

Basic Terminology and Architecture
- A broker stores partition replicas and serves clients. A topic groups partitions for a logical event stream.
- Each partition is an ordered, append-only log. An offset identifies a record's position within that partition.
- Within one consumer group, each partition has at most one active consumer. Other groups maintain their own assignments and progress.
- Kafka preserves partition order. It does not automatically create one order across all partitions in a topic.

How Kafka Works | 6,7,8
- A record contains a value and can include a key, timestamp, and headers. The producer uses a partitioning strategy.
- The partition leader accepts writes. Followers copy the log. Acknowledgement and in-sync replica settings determine the write's failure guarantees.
- Consumers fetch records and track their positions. Each group commits its progress independently from producer writes.
- Committing before processing can skip unfinished work after a crash. Committing after processing can repeat work whose effects already succeeded.
- Reading a record does not delete it. Retention limits or compaction control how long log data remains available.

Scalability
- A group's partition count limits its parallelism. Consumers beyond the number of assigned partitions have no partition to process.
- Choose keys for both ordering and load distribution. A popular key can overload one partition.
- Batch and compress records to reduce network and storage overhead.
- Store large files in object storage. Put their locations in Kafka records instead of transferring the file bytes through Kafka.
- Adding partitions can change key routing. Plan the transition when events for a key must retain their order.

Fault Tolerance and Durability
- Replicas provide replacement leaders after broker failures. Recovery depends on the acknowledgement, replica, and election policies.
- Choose replication factor, acknowledgements, and minimum in-sync replicas for the permitted data loss. Kafka is not immune to outages.
- A consumer failure causes partition reassignment. The new consumer resumes from committed progress and can repeat unfinished attempts.
- Monitor consumer lag and retained capacity. A long outage must not exceed the retention needed for recovery.

Handling Retries and Errors | 9
- Idempotent production prevents certain duplicate appends after producer retries. It uses producer identity and sequencing.
- Consumer side effects still need idempotency or compatible transactions. Producer idempotence alone does not make the complete pipeline exactly once.
- Define a retry policy for temporary failures. Move repeatedly failing records to a retry topic or dead-letter topic when appropriate.
- A separate retry path can change processing order. Decide whether a failed record blocks its partition or leaves the main path.

When to Use and Summary
- Use Kafka for retained event pipelines, stream processing, and multiple independent consumers.
- A simpler work queue can provide easier delayed delivery, visibility timeouts, and per-message retries.
- Explain the partition key, consumer groups, offset commits, retention, and failure behavior. These choices determine how the pipeline operates.

@@ temporal
Overview
- Temporal coordinates durable workflows across process crashes, retries, long waits, and external events.
- Workflow code makes deterministic decisions. Activities perform external operations, such as database writes and network calls.

Building Durable Execution

1) Survive a crash | 1,2
- Temporal records workflow events and completed Activity results in durable history.
- After a worker failure, another worker replays that history to reconstruct workflow progress.
- Replay supplies recorded Activity results. It does not call the external service again for an already recorded completion.
- An Activity can repeat if its side effect succeeds before Temporal records completion. Make external effects safe to retry.

2) Predictable replay
- The same history must produce the same workflow decisions.
- Use workflow-safe time, randomness, and orchestration APIs. Put nondeterministic network or database operations in Activities.
- Deploy compatible workflow changes. Existing histories must remain replayable under the selected versioning strategy.

3) Wait and receive events | 3,4
- A durable timer lets a Workflow wait without occupying a worker for the entire delay.
- A Signal records external input in workflow history. It can resume a Workflow that is waiting for an event.
- Route events to the correct Workflow. Define how it handles duplicate, late, and unexpected input.

Temporal Under the Hood | 5
- Frontend Service accepts client and worker requests. History Service manages durable workflow state. Matching Service connects Task Queues to polling workers.
- Workflow Tasks run orchestration decisions. Activity Tasks run the business operations. Application workers execute both kinds of code.
- Workers can fail or scale separately from Temporal. Durable workflow state does not depend on one worker's memory.

State, Replay, and Workers | 6,7,8,9
- History Service stores Event History and Mutable State. It commits required internal tasks with state changes so later work remains recoverable.
- A Workflow Cache and Sticky Queue reduce repeated replay. After a cache loss, a worker reconstructs state from durable history.
- Task Queues direct work to compatible worker pools. Matching Service can partition queues to increase dispatch capacity.
- Heartbeats and timeouts detect stalled Activities. The retry policy determines when another attempt can start.
- Limit history growth. Keep large payloads in external storage and retain durable references in workflow state.

When to Use
- Use durable workflows for dependent business operations that need recovery. Examples include payments, reservations, fulfillment, and media-processing stages.
- Activities can retry with backoff. Workflow logic decides when to compensate, escalate, or stop after a terminal failure.
- Stored workflow state makes progress and waiting conditions observable, including waits that last several days.
- A durable queue and an idempotent worker can be enough for one independent job.

Limitations
- Temporal does not make an external system transactional. An email or charge still needs protection against repeated attempts.
- The application owns workflow determinism, compatible code changes, timeout policies, and history limits.
- Activities and external services must cooperate with cancellation. Cancellation does not undo side effects that already completed.
- Running Temporal and debugging workflows adds complexity. Use it when durable coordination justifies that cost.

Summary
- Durable history and deterministic replay reconstruct workflow progress after failure.
- Activities perform external work safely across retries. Timers and Signals represent waits without keeping a process active throughout.
- Choose Temporal when it replaces substantial workflow state, retry, and recovery logic. Asynchronous execution alone does not require it.

@@ api-gateway
What Is an API Gateway?
- An API Gateway is a shared entry point. It routes client requests to backend services.
- It applies common request policies. Clients do not need to know every internal service address.
- Routing is its main role. Add other responsibilities only when the application requires them.

Core Responsibilities and Request Flow | 1
- Validate the request and run middleware. Select a backend, forward the request, and return the response in the required format.
- Limit gateway work. A common entry point should not execute all application business logic.

- Translate protocols only when needed. Translation can simplify the client contract, but adds work and failure cases.

- Store reusable responses in the cache with correct keys, expiry, and access rules.

- Use regional gateways when geographic delay or availability requirements justify them.
- Configure proxy buffering and timeouts for streaming or WebSocket traffic. Drain connections carefully when an instance stops.
- Reject or limit excess requests before downstream services become overloaded.

- Managed gateways reduce operational work and integrate with cloud identity and monitoring. Account for service limits and usage charges.
- Self-hosted gateways give more control. The team must manage upgrades, capacity, availability, and configuration changes.
- Explain the required behavior when choosing a gateway. Listing product names does not explain the design.

- A gateway gives clients a stable interface to multiple services. It also centralizes common request policies.
- A simple application with one backend may not need another routing layer.

@@ cassandra
Overview
- Cassandra is a distributed wide-column database. It partitions and replicates data to support large workloads and high write availability.
- Design tables around known queries. Arbitrary joins and flexible cross-partition transactions are not its main strengths.

Data Model and Primary Key | 1
- The partition key determines which replica set stores a group of rows.
- Clustering columns order rows within that partition. They support bounded range queries in the required order.
- A composite partition key hashes its combined values. Clustering columns do not independently distribute rows between partitions.
- Limit partition size and traffic. Combining an entity ID with a time bucket can prevent indefinite partition growth.

Partitioning and Replication | 2,3,4
- Consistent hashing assigns token ranges to nodes. Virtual nodes spread a physical node's ownership across multiple ranges.
- Replication places copies on separate nodes. A topology-aware strategy also accounts for racks and data centers.
- Any contacted node can act as the coordinator. It forwards the request to the replicas that own the partition.
- Adding nodes changes ownership and requires data transfer. Rebalancing consumes capacity before the new distribution is ready.

Consistency and Routing | 5,6
- Each operation selects a consistency level. This determines how many replica responses it needs to succeed.
- Requiring more responses increases read/write overlap. It can also increase latency and reduce availability during failures.
- Overlapping quorums do not make arbitrary concurrent, multi-record operations serializable transactions.
- Lightweight transactions support conditional coordination for supported operations. Their additional coordination costs more than ordinary writes.

Storage Model | 7
- A replica appends a mutation to its commit log. It then updates the in-memory memtable.
- Flushing a memtable creates an immutable SSTable. Reads can combine data from memtables and several SSTables.
- Bloom filters identify files that might contain a key. Indexes help locate the relevant data within those files.
- Compaction merges SSTables and removes obsolete versions when safe. It consumes background CPU and storage I/O.
- Deletes create tombstones. Keep them long enough to prevent stale replicas from restoring deleted values.

Gossip and Fault Tolerance | 8
- Gossip spreads membership and failure information between nodes.
- Hinted handoff temporarily records writes for unavailable replicas. Repair or rebuilding is still necessary after longer gaps.
- Choose replication and consistency settings for the expected failures. Acknowledging one write does not mean every replica has received it.

Data Modeling
- Start with the required partition and range queries. Create tables that answer those queries directly.
- Duplicate data into query-specific tables where needed. Define how updates keep those copies consistent.
- For chat messages, partition by conversation and time bucket. Use an ordered message identifier as the clustering key.
- Limit active conversation partitions. Retrieve recent messages from the relevant buckets instead of scanning unrelated conversations.

Examples and Advanced Features | 9,10
- For ticket browsing, partition detailed seats by event and section. This matches the view that opens one venue section.
- A separate event_sections table stores section summaries by event. Browsing can tolerate lag; checkout must verify actual seat availability.
- TTL can expire time-limited records. Expiry and frequent deletion create tombstones that affect read and compaction work.
- Secondary indexes and materialized views support additional access patterns. They do not remove the need to control partition size and traffic.

When to Use and Limitations
- Cassandra fits large, predictable workloads with many writes and partition-local reads. Select consistency settings for each access path.
- Complex joins, ad hoc relational queries, and cross-partition invariants can fit another database better.
- Explain partition limits, replication, consistency levels, and repair. These choices determine how Cassandra supports the application.

@@ dynamodb
Overview
- DynamoDB is a managed key-value and document database. Efficient access depends on the primary keys and required query patterns.
- Managed scaling reduces operational work. It does not remove hot keys, query limits, or consistency decisions.

The Data Model | 1,2
- The partition key distributes items. An optional sort key orders items that share the same partition-key value.
- GetItem retrieves one complete primary key. Query retrieves one partition-key value, optionally restricted by sort-key conditions.
- Scan examines a broad set of items. Avoid it for frequent lookups when a key-based query can answer the request.
- Use sort-key prefixes or time ranges for known queries. Bound large item collections and highly active keys.

Secondary Indexes | 3,4
- A global secondary index supplies alternative partition and sort keys. It has additional capacity costs and eventually consistent reads.
- A local secondary index keeps the table's partition key with a different sort key. Define it when creating the table.
- Every index adds storage and write work. Project the fields that its queries need.
- Filters run after items are read. Discarded results can still consume read capacity, so filters do not replace selective key conditions.

Accessing Data
- Use conditional writes for version checks or claims on available items. DynamoDB checks the condition with the supported write operation.
- Atomic updates change counters without a client-side read-modify-write race. Retrying an uncertain increment can still repeat its effect.
- Transactions coordinate supported operations across items. Account for their limits and additional cost.
- Batch APIs reduce request overhead. Inspect partial failures and retry only unprocessed items where appropriate.
- Use continuation keys for pagination. One request does not return an unlimited item collection.

Consistency, Scalability, and Availability
- Choose eventual or strong reads where supported. Base tables and local secondary indexes support strong reads; global secondary indexes do not.
- Global Tables replicate across regions. Check the selected configuration's consistency behavior before promising immediate visibility in every region.
- Distribute traffic across partition keys. Avoid routing most writes to one tenant or one current-time bucket.
- Adaptive capacity helps uneven traffic. It does not give one hot item unlimited throughput.

Security and Capacity
- Use least-privilege IAM, encryption, and application permission checks. A valid database credential does not authorize every tenant's records.
- On-demand capacity follows usage. Provisioned capacity requires planning for expected traffic. Compare costs for the actual workload.
- Item size, indexes, read consistency, and access patterns affect consumed capacity. Returning fewer attributes does not necessarily reduce read capacity.
- Monitor throttling. Retry with backoff so retries do not increase overload.

DAX and Streams | 5
- DAX stores supported DynamoDB read results in its cache. Strongly consistent reads pass through to DynamoDB without using a cached result.
- The diagram is schematic. Direct DynamoDB writes do not automatically invalidate DAX results. Account for cache expiry and the write path.
- DynamoDB Streams expose item changes for search indexes, notifications, and other derived data.
- Consumers must tolerate repeated delivery and retain recovery progress. Stream retention is finite, so long outages can require a rebuild.
- TTL deletion is asynchronous. Check expiry in the application when an expired item must become invalid immediately.

When to Use and Limitations
- DynamoDB suits predictable key-based access at scale. Managed infrastructure reduces the database operations that the team must perform.
- Ad hoc joins, broad analytics, and changing query patterns can be awkward or expensive.
- Specify the primary keys, secondary-index queries, conditional writes, and hot-key controls before choosing the service.

@@ postgresql
Overview
- PostgreSQL is a relational database. It supports transactions, constraints, flexible queries, and several index types.
- It is a strong starting point when related records and critical updates fit within one database's transaction boundary.

Read Performance
- B-tree indexes support equality, range, and ordered queries. Choose composite index columns in the order needed by the access pattern.
- A unique constraint can enforce one review per user and business, including concurrent submissions.
- GIN indexes support suitable full-text, array, and JSONB queries. PostGIS adds spatial types and indexes for geographic queries.
- Use EXPLAIN and measured plans to inspect scans, joins, row estimates, and sorting. Verify which operation causes the delay.

Query Optimization
- A covering index can supply required columns without some table lookups. Visibility checks and query requirements still affect execution.
- A partial index covers a selected subset, such as active records. This can reduce index size and update work.
- Selective filters and cursor pagination avoid repeatedly scanning and discarding earlier pages.
- A connection pool such as PgBouncer limits database connection overhead. It does not repair an inefficient query or lock conflict.

Write Performance
- Writes change table data and indexes, produce WAL, and may wait for replication. Unnecessary indexes increase write cost.
- Keep transactions short. Batch operations when their latency and atomicity requirements allow it.
- Bulk loading and suitable upserts can reduce per-row request overhead.
- Table partitioning helps query pruning and data lifecycle management. Partitions on one primary do not create independent write servers.
- Monitor WAL, storage latency, checkpoints, autovacuum, and lock waits. Scale the measured bottleneck.

Replication and High Availability
- Read replicas distribute read traffic and provide failover candidates. Asynchronous replicas can lag behind the primary.
- Send freshness-sensitive reads to a path that meets their requirement. A recent write may not yet appear on a replica.
- Synchronous replication waits for the configured replica acknowledgement. This adds network delay and can reduce availability during replica failures.
- Failover must leave one writable primary. Prevent the old primary from accepting conflicting writes when it returns.
- Backups and WAL recovery complement replication. A replica can copy an accidental deletion or another unwanted write.

Transactions and Concurrent Operations
- A transaction commits related changes together. Database constraints reject changes that violate declared rules.
- A read followed by an unconditional update can still race. Default Read Committed isolation does not prevent every concurrency anomaly.
- Use conditional writes, unique constraints, row locks, or Serializable isolation for the specific invariant.
- Retry the complete transaction after a retryable serialization failure or deadlock. Limit attempts.
- Avoid holding row locks during user interaction or external network calls. Use explicit reservation state for longer claims.
- If a committed change must publish an external event, a transactional outbox can make the publication recoverable.
- Repeatable Read provides a stable transaction snapshot. PostgreSQL prevents phantom reads at this level, but serialization anomalies can remain.
- Serializable execution prevents serialization anomalies by rejecting some conflicting transactions. The application must handle those failures.

When to Use and Alternatives
- Use PostgreSQL for relational data, transactional workflows, flexible queries, and workloads that an indexed primary can serve.
- Add replicas or caches for read-heavy traffic. Introduce specialized search or analytics stores when their query capabilities are needed.
- Very high write traffic or multi-region write requirements can require sharding or another database. Explain the resulting coordination costs.
- Large data volume alone does not justify replacing PostgreSQL. Estimate the workload and identify the limiting operation.

SQL and ACID Essentials
- Tables store related records. Primary keys identify rows. Foreign keys enforce the relationships declared in the schema.
- Atomicity means all transaction changes succeed together or fail together. Consistency means preserving the declared data invariants.
- Isolation defines concurrent transaction behavior. Durability defines which committed changes survive failures under the selected settings.
- SELECT reads data. INSERT, UPDATE, and DELETE change it. Schema commands define structure; transaction commands define execution boundaries.

Summary
- Start with a suitable schema, explicit constraints, and indexes for real queries.
- Scale measured bottlenecks. Keep transaction, replication, and recovery guarantees clear as the architecture grows.

@@ flink
Overview | 1
- Flink runs distributed, stateful computations over event streams.
- Use it for continuous aggregations, joins, event-time windows, or pattern detection. A simple stateless consumer may need less infrastructure.

Basic Concepts | 2
- Sources read records and sinks write results. Operators transform, filter, group, join, or aggregate the streams between them.
- keyBy routes records with the same key to the corresponding keyed state.
- Parallel operator instances process different portions of the stream. Network exchanges redistribute records where the job graph requires it.
- One hot key can overload its operator instance even when other instances have spare capacity.

State
- Keyed state stores values for each logical key, such as a running count or recent event history.
- Operator state belongs to an operator instance. Its redistribution rules matter when parallelism changes.
- Limit state with expiry, window cleanup, or explicit lifecycle rules. An infinite input stream must not cause unlimited state growth.
- Keep large raw payloads in external storage when a reference is sufficient for processing.

Watermarks and Windows | 3
- Event time comes from the event's timestamp. Processing time is the time when the worker handles it.
- Watermarks estimate event-time progress. They help trigger windows; they do not prove that no older event can ever arrive.
- Tumbling windows do not overlap. Sliding windows overlap. Session windows group activity separated by an inactivity gap.
- Define allowed lateness and a correction or side-output policy. Very late events may need separate reconciliation.
- A stalled input partition can delay watermark progress. Handle idle inputs according to the source and correctness requirements.

Basic Use
- Define the job graph, sources, serializers, state, parallelism, and sinks. Then submit the job to the cluster.
- A dashboard can aggregate event counts and write the results to Redis or another serving database.
- Fraud detection can keep recent account state and evaluate event sequences. The job can send alerts to multiple sinks.
- Correct checkpoints preserve computation state. They do not correct an invalid aggregation rule.

How Flink Works | 4,5
- The JobManager schedules tasks and coordinates recovery. TaskManagers execute the parallel operators.
- Task slots allocate resources. Operator parallelism determines how many instances execute each operation.
- Network transfers, serialization, state access, and sink capacity can limit throughput.
- Slow downstream operators or sinks create backpressure. This pressure can reduce the upstream processing rate.

State Backends and Checkpoints
- The state backend controls active state storage and access. Choose it for the expected state size and latency.
- Checkpoints save recoverable operator state and source positions across the dataflow. Store recovery data durably.
- After a failure, restore a completed checkpoint. Replay input from the corresponding source positions.
- Exactly-once internal state recovery does not make an arbitrary external API call happen only once.
- End-to-end guarantees require replayable sources and compatible transactional or idempotent sinks.
- Savepoints support planned upgrades and migration. Preserve compatibility when changing the job's state model.

In Your Interview
- Propose Flink when continuous computation needs managed state or event-time behavior.
- Specify the partition key, state, windows, late-data policy, and sink updates.
- Explain recovery and hot-key controls. Monitor lag, checkpoint duration, backpressure, and state growth.
- Use a smaller queue worker when the application does not need Flink's state and time-processing capabilities.

Conclusion
- Flink combines parallel operators, managed state, and coordinated recovery.
- Correctness still depends on key choice, time handling, bounded state, and the external sink's guarantees.

@@ zookeeper
Overview
- ZooKeeper coordinates distributed processes with small replicated records, ordered writes, sessions, and change notifications.
- Use it for coordination metadata. It is not a general-purpose database for high-volume application data or message payloads.

A Motivating Example | 1,2,3,4,5
- One chat server knows its connected users. With multiple servers, it needs a shared way to find another user's server.
- Database lookups and all-to-all broadcasts add load and failure cases. ZooKeeper can hold membership information and notify interested servers.
- Keep high-volume message traffic outside ZooKeeper. Cached routing information still needs failure handling when membership changes.

ZooKeeper Basics | 6,7,8
- Znodes form a hierarchy. Each contains a small data value and metadata, including versions.
- Persistent znodes remain until deletion. Ephemeral znodes belong to a session. Sequential znodes receive ordered suffixes.
- An ensemble uses a leader and quorum replication to order updates. Clients connect to an ensemble server through a session.
- Watches notify clients of relevant changes. Clients reread state and renew one-shot watches. A watch is not a durable event log.

Key Capabilities

1) Configuration and service discovery
- Store small, versioned configuration records. Notify interested services when those values change.
- A service registers an ephemeral membership record. ZooKeeper removes it when its owning session expires.
- Membership caches can be stale. Callers still need connection-error handling and retries.

2) Leader election and locks
- Contenders create ephemeral sequential znodes. The lowest eligible sequence becomes leader or owns the lock.
- Each waiting contender watches its immediate predecessor. This avoids waking all contenders whenever ownership changes.
- Session expiry removes ephemeral ownership. It does not stop a paused application process from resuming later.
- Use fencing or version checks at the protected resource. Reject writes from an obsolete owner.

How ZooKeeper Works | 9
- ZAB orders updates through the ensemble leader. A quorum participates before a write can commit under the protocol.
- Individual servers can serve local reads. A read can lag a newer update unless the client uses the required synchronization contract.
- Ordered client operations and globally ordered writes do not make every arbitrary read immediately current.
- Sessions use heartbeats and timeouts. A temporary disconnection does not immediately mean that the session expired.
- Transaction logs and snapshots support recovery. Coordination writes require an available quorum.

Handling Failures
- After reconnection, verify the session and current ownership. Do not assume that a previous lock remains valid.
- A create request can succeed before its response is lost. Use identifiable records to reconcile an uncertain result.
- Keep coordination values and request rates small. Application payload traffic must not overload the ensemble.
- Spread an appropriate odd-sized voting ensemble across failure domains. Monitor latency, sessions, storage, and quorum health.

When to Use | 10,11
- ZooKeeper fits leader election, shard ownership, service membership, and other ordered infrastructure metadata.
- Smart routing reads the ownership map and directs clients to the responsible application servers.
- etcd, Consul, managed services, or database primitives can provide alternatives. Compare the guarantees required by the actual coordination problem.
- A database conditional write can be enough for a simple invariant. Add a coordination cluster only when its capabilities are needed.

Summary
- ZooKeeper supplies primitives for discovery, election, and locking. The application combines them into a complete protocol.
- Correct session handling, watch recovery, and fencing remain part of that protocol.
- Separate application data traffic from coordination. Identify exactly which metadata operation needs quorum agreement.
