Understanding the Problem
- Bitly maps a short URL to a longer URL. The short URL uses a domain we own, so opening it sends a request to our service before the browser visits the destination.
- The main challenges are generating unique short codes, making redirects fast, and staying available as traffic grows.

Functional Requirements
- Users submit a long URL and receive a short URL.
- Users can optionally choose a custom alias instead of a generated code.
- Users can optionally set an expiration date.
- Anyone opening a valid short URL is redirected to its original URL.
- Keep account management and click analytics outside the initial scope unless the interviewer asks to include them.

Non-functional Requirements
- Redirects should be fast, with a target below 100 ms for the service's redirect operation.
- Favor high availability: an outage should not make every shared link unusable.
- Each short code must identify one mapping. Two users must not receive the same code for different destinations.
- Plan for roughly 1 billion stored URLs and 100 million daily active users.
- Expect many more redirects than new links. Read traffic, especially traffic to popular links, drives most scaling decisions.

Core Entities
- Original URL: the destination the user wants to shorten.
- Short URL: our domain plus a short code that identifies the stored mapping.
- User: the creator of the link, if ownership is tracked. Full authentication is outside the initial scope.
- A mapping record contains short_code, long_url, created_at, and optional expires_at and creator_id. Make short_code the primary key. A custom alias occupies the same lookup role as a generated code.

API
- POST /urls creates a mapping. The request contains long_url and optional custom_alias and expiration_date fields.
- A successful create response contains short_url, such as https://short.ly/abc123. Return it after the mapping is saved.
- GET /{short_code} looks up the destination and returns a redirect with the long URL in the Location header.
- Return an error for an invalid URL or unavailable alias. Return 404 for an unknown code and 410 for an expired link.

High-Level Design

1) Create a short URL
- Start with a client, an application server, and a database. The client sends POST /urls to the server.
- Validate the long URL and any supplied alias or expiration date.
- If the user supplied an alias, reserve it. Otherwise, generate a code; explain the generation algorithm in the deep dive.
- Insert the code-to-URL mapping. Enforce uniqueness in the database so simultaneous requests cannot claim the same code.
- Return the complete short URL after the insert succeeds.
- Multiple short URLs may point to the same long URL, allowing different aliases and expiration dates. Deduplication is optional.

2) Redirect to the original URL
- The browser requests GET /abc123 from our short-link domain.
- The server looks up abc123 and checks whether the mapping has expired.
- For a valid mapping, return a redirect with Location set to the original URL. The browser follows that destination automatically.
- Prefer 302 when links may change or expire. Set explicit cache headers; 302 alone does not guarantee that a response will never be cached.
- A 301 means a permanent redirect and may let browsers skip our service on future visits, making changes, expiration, and click tracking harder to enforce.
- A background job can delete expired records. Also check expiration on reads, so a delayed cleanup job does not keep expired links working.

Deep Dives

1) Generate unique short codes
- Codes should be short, quick to generate, and unique. The tradeoffs involve coordination, collision handling, and predictability.
- Taking the first few characters of a long URL fails because many URLs share the same prefix.
- Hashing approach: hash the URL, encode the result, and keep a short prefix. The same input normally produces the same result unless a salt or nonce is included.
- Truncated hashes can collide. Enforce uniqueness in the database and retry with a different candidate, with a limit on retries. Random codes need the same collision handling.
- Counter approach: allocate a unique numeric ID and encode it in Base62, which uses a-z, A-Z, and 0-9.
- Six Base62 characters provide about 56.8 billion combinations, so a billion counter-generated IDs fit within six characters.
- A shared atomic counter, such as Redis INCR, gives concurrent writers different IDs. All writers must use a coordinated allocator or non-overlapping ranges.
- Sequential codes are predictable. Choose an unpredictable strategy if guessing links matters; do not treat a short code as strong access control.
- Custom aliases can collide with generated codes. Separate their namespaces or reserve all codes through the same uniqueness rule. Checking availability before insertion does not prevent a race.

2) Make redirects fast
- Index short_code, normally by making it the primary key. This avoids scanning the entire table for each redirect.
- Add Redis or another cache for frequently requested mappings. A cache hit avoids a database lookup.
- On a miss, read the database, populate the cache, and return the redirect. The database remains the durable source of truth.
- Cache capacity is limited. Use an eviction policy and expect misses during warm-up; the service must still work when a mapping is absent from the cache.
- Set cache TTLs no longer than the link's remaining lifetime. Invalidate mappings when links change or are deleted, and check expiration before redirecting.
- CDN or edge caching can serve popular redirects closer to users. It reduces latency and origin traffic but adds invalidation, expiration, cost, and operational complexity.

3) Scale and keep the system available
- Estimate traffic first. At 100 million daily users and five redirects each, reads average about 5,800 requests per second. A 100x peak assumption gives roughly 580,000 per second.
- At 500 bytes per mapping, a billion mappings require about 500 GB before additional index and replication overhead. Storage alone does not automatically require sharding.
- If 100,000 URLs are created per day, writes average about 1.2 per second. A familiar database such as PostgreSQL is a reasonable start; benchmark before adding shards.
- Scale stateless application servers behind a load balancer. Separate redirect and creation services when their capacity requirements differ.
- Use replication and failover for availability, and backups for recovery. Backups do not replace a running failover system. Account for replica lag when redirecting a newly created link.
- Reserve counter batches if requesting one ID per URL becomes expensive. INCRBY 1000 returns the upper end of a reserved range that a writer can consume locally.
- Assigned ranges must not overlap. A crashed writer may leave unused IDs; gaps are harmless because uniqueness matters more than continuity.
- Counter failover must not reuse allocated ranges. Preserve or safely recover allocator state, retain the database uniqueness constraint, and handle conflicts before returning a link.
- For multiple regions, allocate disjoint ID ranges to avoid coordinating every write across regions. Use regional caches while handling replication lag and expiration consistently.

Final Design
- Creation path: client -> load balancer or API gateway -> creation service -> unique ID allocator -> database. Return the short URL after the write succeeds.
- Redirect path: browser -> load balancer or API gateway -> redirect service -> cache. A miss falls back to the database and then fills the cache.
- The database owns durable mappings and enforces code uniqueness. The cache speeds up reads; it is not the only copy of the data.
- Both cached and database reads enforce expiration. Custom aliases use the same reliable uniqueness rules as generated codes.
- Add replicas, independent read/write scaling, counter batches, and optional edge caching as actual scale requires them.
- Explain the tradeoffs: counter coordination versus hash collisions, caching speed versus invalidation complexity, and a simple starting design versus more infrastructure for high traffic.
