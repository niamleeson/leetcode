Understanding the Problem
- Bitly connects a short URL to an original URL. The short URL uses a domain that the service owns. The browser first sends a request to this domain. Then the browser requests the original URL.
- The service needs unique short codes, fast redirects, and high availability as traffic increases.

Functional Requirements
- A user submits an original URL. The service returns a short URL.
- A user can select a custom alias instead of a generated short code.
- A user can set an expiration date for a short URL.
- The service redirects each valid short URL to its original URL.
- The initial design does not include account management or click analytics. The interviewer can request these features.

Non-functional Requirements
- The target response time for a redirect is less than 100 ms. This target excludes the time to load the destination website.
- The service needs high availability. A component failure must not stop all redirects.
- Each short code identifies only one mapping. The service must not use one short code for two different destinations.
- The design assumes 1 billion stored mappings and 100 million daily active users.
- The service receives many more redirect requests than creation requests. Read traffic determines most capacity needs. Popular links can cause large peaks in read traffic.

Core Entities
- Original URL: the destination address that the user wants to shorten.
- Short URL: the domain of the service and a short code. The short code identifies the stored mapping.
- User: the person who creates the short URL. The design can record this user as the owner. Full authentication is outside the initial scope.
- A mapping record contains short_code, long_url, and created_at. The optional fields are expires_at and creator_id. The primary key is short_code. A custom alias replaces the generated short code in this key.

API
- POST /urls creates a mapping. The request has a long_url field. It can also have custom_alias and expiration_date fields.
- The create response has short_url, for example https://short.ly/abc123. The service returns this response only after the database saves the mapping.
- GET /{short_code} requests the original URL. The service returns a redirect response. The Location header contains the original URL.
- The service rejects an invalid URL or an alias that already exists. The service returns 404 for an unknown short code. The service returns 410 for an expired short URL.

High-Level Design

1) Create a short URL
- The initial design has a client, a Primary Server, and a database. The client sends POST /urls to the Primary Server.
- The server validates the original URL, custom alias, and expiration date.
- If the request has a custom alias, the server uses it as the proposed short code. Otherwise, the server generates a short code. The deep dive explains code generation.
- The server inserts the mapping. A database uniqueness constraint prevents duplicate short codes, including conflicts between simultaneous requests.
- After the database saves the mapping, the server returns the complete short URL.
- Different short URLs can use the same original URL. Each short URL can have a different alias and expiration date. URL deduplication is optional.

2) Redirect to the original URL
- The browser sends GET /abc123 to the domain of the service.
- The server finds the mapping for abc123. The server validates its expiration date.
- For a valid mapping, the server returns a redirect with the original URL in the Location header. The browser then requests the original URL.
- The design uses 302 for URLs that can change or expire. The response must include explicit cache-control headers. A 302 response alone does not prevent browser caching.
- A 301 response is a permanent redirect. The browser can store this response and bypass the service on later visits. Thus, URL changes, expiration checks, and click analytics can fail.
- A background job deletes expired records. The service also validates expiration for each redirect. Thus, delays in the cleanup job do not extend the validity of a short URL.

Deep Dives

1) Generate unique short codes
- Short codes must be unique and quick to generate. The design must balance coordination, collision handling, and the risk of predictable codes.
- The first few characters of an original URL do not make a reliable short code. Many URLs start with the same characters.
- The hash method calculates a hash of the original URL. It encodes the result and keeps a short prefix. The same input gives the same result unless the algorithm includes a salt or nonce.
- Different URLs can produce the same truncated hash. The database rejects duplicate short codes. The service tries a different code, up to a retry limit. Random short codes need the same collision handling.
- The counter method assigns a unique numeric ID. The service encodes this ID in Base62. Base62 uses a-z, A-Z, and 0-9.
- Six Base62 characters allow approximately 56.8 billion values. Thus, 1 billion sequential IDs fit in six characters.
- A shared atomic counter, such as Redis INCR, gives different IDs to concurrent writers. All writers must use a coordinated allocator or ID ranges that do not overlap.
- A user can predict sequential short codes. If this is a risk, the design needs an unpredictable code generator. A short code does not provide strong access control.
- Custom aliases and generated short codes can have the same value. Separate namespaces or a shared uniqueness constraint prevent this conflict. An availability check before insertion does not reserve the code.

2) Make redirects fast
- The primary key on short_code provides a database index. This index finds a mapping without a scan of the entire table.
- Redis or another cache stores mappings that users request frequently. On a cache hit, the service gets the mapping without a database lookup.
- On a cache miss, the service reads the database. Then the service stores a copy in the cache. Then the service returns the redirect. The database keeps the durable copy.
- The cache has limited capacity. An eviction policy determines which entries to remove. During cache warm-up, many requests can miss the cache. A cache miss must still allow a database lookup.
- Each cache entry has a time to live (TTL). The TTL must not exceed the remaining lifetime of the short URL. If the service changes or deletes a URL, it removes the cache entry. The service validates expiration before each redirect.
- A content delivery network (CDN) can store redirect responses near users. Edge caching reduces response time and requests to the service. However, it adds cost and maintenance work. Cache updates and expiration rules also become more complex.

3) Scale and keep the system available
- At 100 million daily users and five redirects per user, the service receives approximately 5,800 requests per second. A peak of 100 times this average gives approximately 580,000 requests per second.
- At 500 bytes per mapping, 1 billion mappings use approximately 500 GB. Indexes and replicas need additional storage. This storage estimate alone does not require sharding. Sharding divides data between database servers.
- If users create 100,000 URLs each day, the service receives approximately 1.2 creation requests per second. PostgreSQL is one option for the initial design. Performance tests determine whether the system needs shards.
- A load balancer distributes requests across stateless application servers. The system can add servers as traffic increases. The Write Service and Read Service can scale separately when their capacity needs differ.
- Replication and failover keep the service available during failures. Backups restore lost data. A backup does not replace failover. A replica can lag behind the primary database. The redirect service must use a current copy for a new short URL.
- A creation server can reserve a batch of IDs to reduce requests to the allocator. INCRBY 1000 returns the upper limit of a reserved range. The server uses the IDs in this range locally.
- ID ranges must not overlap. A server failure can leave unused IDs. Gaps in the ID sequence do not cause duplicate short codes.
- After failover, the allocator must not assign an old range again. Recovery must preserve the allocator state. The database must still reject duplicate short codes. The service resolves any conflict before it returns a short URL.
- Each region can use a separate ID range. These ranges avoid coordination between regions for each write. Each region can use its own cache. The design must handle replication lag and apply the same expiration rules in each region.

Final Design
- Creation request: client -> API Gateway -> Write Service. The Write Service gets an ID from the Global Counter. It encodes the ID in Base62. Then it saves the mapping in the database. After the write succeeds, it returns the short URL.
- Redirect request: browser -> API Gateway -> Read Service. The Read Service looks for the mapping in the cache. On a cache miss, it reads the database. Then it stores a copy in the cache. For a valid mapping, it returns a 302 response.
- The database keeps durable mappings and prevents duplicate short codes. The cache makes reads faster. The database still keeps a copy of each mapping.
- The service validates expiration for results from the cache and the database. The same uniqueness constraint applies to custom aliases and generated short codes.
- The system can add replicas and separate read and write capacity as traffic increases. ID batches and edge caching are optional additions.
- The design must balance counter coordination against hash collisions. It must also balance faster reads against cache maintenance. Additional infrastructure must meet a measured capacity need.
