@@ bitly
1) Create a short URL >> Create and return a short link
- The client sends POST /urls with long_url. The request can include custom_alias and expiration_date. The gateway sends the request to the creation service.
- The service validates the original URL and expiration date. It rejects invalid input before it assigns an ID or writes a mapping.
- For a generated short code, the service gets a unique ID from the allocator. It encodes the ID in Base62. For a custom alias, the service uses the requested value as the short code.
- The service inserts short_code, long_url, and expiration data into the database. The uniqueness constraint rejects duplicate short codes. An availability check does not reserve a short code.
- If a generated short code already exists, the service tries another code. The service stops after the retry limit. If a custom alias already exists, the service returns an error.
- After the database confirms the write, the service returns the complete short URL. The database can then supply the mapping when the cache is empty. If the write fails, the service does not return a successful result.

2) Redirect to the original URL >> Resolve a short link through the cache and database
- The browser sends GET /abc123 to the domain of the service. The gateway sends the request to the redirect service.
- The service looks for abc123 in the cache. On a cache hit, it reads the original URL and expiration date together.
- On a cache miss, the service queries the database by short_code. If no record exists, the service returns 404. This ends the request.
- The service validates expiration for the result from the cache or database. If the mapping has expired, the service returns 410. This rule also applies before the cleanup job deletes the record.
- For a valid database result, the service can store a copy in the cache. Its TTL must not exceed the remaining lifetime of the short URL. If this cache write fails, the database mapping remains valid.
- The service returns a 302 response. The Location header contains the original URL. The response includes explicit cache-control headers.
- The browser receives the redirect response. Then it sends a separate request to the original URL. The short URL service does not download the destination page for the browser.

1) Generate unique short codes >> Allocate a batch of counter IDs
- A creation server requests a batch of IDs from the shared allocator. An atomic INCRBY 1000 operation can reserve this batch.
- The allocator increases the counter by 1,000 in one atomic operation. It returns the new value as the upper limit. The server owns the 1,000 IDs that end at this value.
- Each new mapping uses one unused ID from the range. The server encodes that ID in Base62 to make the proposed short code.
- During insertion, the database uniqueness constraint rejects a duplicate short code. This constraint also prevents conflicts with custom aliases.
- A server failure can leave unused IDs. A replacement must not reuse a range unless recovery proves that the replacement owns its unused IDs.

@@ cassandra
Storage Model >> Write a row and read the latest visible value
- The client sends a mutation with its primary key and selected consistency level to a coordinator node.
- The coordinator hashes the partition key, identifies replica owners, and forwards the mutation to the relevant replicas.
- Each participating replica records the mutation through its commit-log/memtable path under the configured durability policy.
- The coordinator acknowledges after the selected consistency level's required responses arrive; unavailable required replicas can make the operation fail or time out.
- Memtables later flush to SSTables and background compaction reorganizes those files; the write need not wait for a full compaction.
- A read coordinator contacts the replicas required by the read consistency level, combines their relevant versions according to Cassandra's conflict rules, and returns the resolved result.
- Read/write overlap improves the selected visibility guarantees, but concurrent multi-record invariants still need a justified conditional or transactional mechanism.

Data Modeling >> Retrieve one page of conversation messages
- The application derives the conversation/time-bucket partition and a clustering-key boundary from the page cursor.
- It issues a partition-bounded query for a limited range of message ordering keys.
- Cassandra routes the query to the replicas for that partition and reads the relevant memtable/SSTable data rather than scanning unrelated conversations.
- The application returns ordered messages and a cursor for the next range or older bucket.
- A very active conversation moves into additional bounded buckets according to the model instead of allowing one partition to grow forever.

@@ dynamodb
Accessing Data >> Claim an item with a conditional write
- The application authenticates the caller and constructs the exact partition/sort key and required state predicate.
- It submits a conditional PutItem or UpdateItem, such as version = expected_version or inventory >= requested_quantity.
- DynamoDB evaluates the predicate and write atomically for the supported operation; a failed condition does not apply the requested mutation.
- The application handles a successful response as the committed operation outcome or handles a condition failure by reloading and re-evaluating the business rule.
- On a timeout, it reconciles or uses supported idempotency/transaction tokens as applicable rather than assuming an increment or side effect definitely failed.
- Subsequent reads select the supported consistency mode needed for their contract; a global secondary index can lag that write.

DAX and Streams >> Update a derived view from table changes
- A committed table mutation produces a change record in the configured stream.
- A consumer reads records and maps each change to the required derived-view update or downstream event.
- It deduplicates or uses version-aware writes so replay cannot apply an old value over a new one.
- It persists the derived result before advancing recoverable processing progress.
- After a failure it resumes within the available retention window; an outage beyond retention needs a rebuild or other reconciliation source.

@@ postgresql
Transactions and Concurrent Operations >> Commit a correctness-sensitive transaction
- The service begins a transaction and establishes the required isolation level and retry policy.
- It obtains needed row locks or includes current-state/version predicates in the writes, then validates the business invariant against that protected state.
- It updates related rows and any outbox/audit records; uniqueness and other constraints can reject invalid results before successful commit.
- PostgreSQL commits according to the selected durability settings, including the required WAL flush and configured synchronous-replication acknowledgement conditions.
- Only after successful commit does the service acknowledge the business operation. A rollback, deadlock, or serialization failure returns an error or causes a bounded whole-transaction retry.
- Replicas apply WAL asynchronously or according to the selected synchronization mode, and background checkpoints persist dirty data pages separately from transaction commit.

Read Performance >> Execute an indexed read
- The application sends a parameterized query through its connection pool.
- PostgreSQL parses and plans the query, choosing scans, indexes, joins, and sorting based on available statistics and predicates.
- Execution reads candidate tuples and checks visibility under the transaction's snapshot, using suitable indexes to avoid unnecessary rows.
- The executor applies remaining filters and aggregation, orders or limits the result, and returns rows to the client.
- A query on a replica observes that replica's replay progress; the application routes freshness-sensitive reads to a path that satisfies their requirement.

@@ flink
Watermarks and Windows >> Aggregate an event-time window
- A source emits events with timestamps and progress information into the job.
- keyBy routes records with the same logical aggregation key to the responsible keyed operator state.
- The operator assigns each event to its window and updates bounded per-key/window state.
- Watermarks advance according to source/partition progress; when the configured trigger boundary is reached, the operator emits the window result.
- Late events follow allowed-lateness and correction or side-output rules, and eligible state is cleaned up only after those rules permit it.
- The sink publishes the result under its update/idempotency contract, so a corrected or replayed window does not become an accidental duplicate total.

State Backends and Checkpoints >> Checkpoint and recover a streaming job
- The checkpoint coordinator initiates a checkpoint, and sources establish recoverable input positions and inject the corresponding barriers.
- Operators follow the configured aligned or unaligned checkpoint protocol to snapshot state consistently with dataflow progress.
- Each task writes its checkpoint state durably and reports completion; compatible sinks stage or record output under their checkpoint protocol.
- The coordinator declares the checkpoint complete after the required participants succeed, enabling supported sink commits and retaining the recoverable boundary.
- After a failure, tasks restore state and source positions from a completed checkpoint and replay later input.
- End-to-end exactly-once effects require a compatible transactional or idempotent sink; an arbitrary external API call can still repeat.

@@ zookeeper
2) Leader election and locks >> Elect a leader with ephemeral sequential nodes
- Each contender establishes a session and creates an identifiable ephemeral sequential znode under the election path.
- It reads the contenders and orders them by sequence; the lowest eligible node becomes leader.
- A follower watches its immediate predecessor, then rereads state when notified instead of assuming a notification alone grants leadership.
- If the leader's session expires, its ephemeral node disappears and the next eligible contender can take ownership.
- The new leader uses an ownership epoch or fencing token with protected resources so the old paused process cannot continue making accepted stale writes.
- Reconnecting contenders verify session and current election state before acting; they do not assume a previous lease survived disconnection.

How ZooKeeper Works >> Commit a coordination write and react to it
- The client submits a version-checked coordination update through a connected server; the write is handled through the ensemble's leader.
- The leader orders the proposal and replicates it through the quorum protocol.
- Once the protocol's commit conditions are satisfied, the committed update is applied and the client receives its outcome.
- Interested clients receive applicable watch notifications, reread the znode state/version, and reestablish the required watch behavior.
- A client with an uncertain write response reconciles the identifiable state before blindly creating another ownership record; a freshness-sensitive read uses the appropriate synchronization contract.
