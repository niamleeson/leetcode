- The Workflow reaches the shipment Activity without a saved result. Temporal schedules that unfinished work.

3) Wait and receive events >> Resume after a durable timer | 3
- The Workflow requests a wait. History Service persists the timer and its deadline.
- The worker becomes available for other work. No worker must remain active for the full waiting period.
- When the deadline arrives, History Service records the timer firing and schedules a Workflow Task.
- A worker resumes the Workflow from history. The completed timer allows the next operation to run.

3) Wait and receive events >> Resume after a delivery Signal | 4
- The order Workflow waits for confirmation that the package was delivered.
- The carrier sends a webhook. The application Signals the correct Workflow with the delivery event.
- Temporal records the Signal in history and schedules workflow execution.
- A worker observes the recorded event during execution or replay. The Workflow can now schedule the review email Activity.

State, Replay, and Workers >> Persist a state change before dispatching its work | 6,7
- History Service receives an Activity completion and computes the resulting workflow state change.
- It commits Event History, Mutable State, and an internal Transfer Task together.
- A background processor reads the committed Transfer Task. It dispatches the required task to Matching Service.
- If History Service fails after the commit, another instance recovers the pending task. The state change does not lose its required follow-up work.

@@ cassandra
Consistency and Routing >> Route a request through a coordinator | 6
- The client sends a query and consistency level to a Cassandra node. That node becomes the coordinator for the request.
- The coordinator hashes the partition key and identifies its replica set.
- It sends the required read or write requests to those replicas.
- The coordinator waits for enough responses to satisfy the selected consistency level. It returns a result or reports failure.

Storage Model >> Store a mutation and flush it to disk | 7
- A mutation reaches a replica node.
- The node appends the mutation to its commit log under the configured durability policy.
- The node updates its in-memory memtable.
- Later, Cassandra flushes the memtable into an immutable SSTable when a size or time condition triggers a flush.
- After the relevant data is safely flushed, Cassandra can reclaim the corresponding commit-log data.
- Background compaction later merges SSTables. The original write does not wait for a complete compaction.

Gossip and Fault Tolerance >> Recover a missed write with hinted handoff | 8
- A coordinator receives a write for a replica set.
- One target replica is unavailable. The coordinator stores a temporary hint for the missed mutation when policy permits.
- Available replicas process the write. The chosen consistency level still determines whether the client request can succeed.
- When the unavailable replica returns, the coordinator sends the retained hint to it.
- The replica applies the missed mutation. Longer outages can require repair because hints have limited retention.

Data Modeling >> Retrieve a page of conversation messages
- The application derives the conversation and time-bucket partition from the requested page.
- It queries a limited range of message identifiers in the required clustering order.
- Cassandra reads the relevant memtable and SSTable data for that partition.
- The application returns the messages and a continuation boundary. It moves to an older bucket when needed.

@@ dynamodb
Accessing Data >> Claim an item with a conditional write
- The application identifies the complete item key. It defines a condition, such as sufficient inventory or an expected version.
- It submits the conditional write to DynamoDB.
- DynamoDB evaluates the condition and mutation atomically for that operation. A failed condition does not apply the requested change.
- The application returns success or handles the condition failure according to its business rule.
- After an uncertain timeout, it reconciles the result or uses a supported idempotency mechanism. It must not assume the write failed.

DAX and Streams >> Read through DAX | 5
- The application sends a supported read to DAX.
- If a valid cached result exists, DAX returns it.
- On a cache miss, DAX requests the data from DynamoDB.
- DynamoDB returns the data. DAX stores the eligible result in its cache and returns it to the application.
- DAX expires or evicts entries under its cache policy. Strongly consistent reads instead pass through without caching.

DAX and Streams >> Update a derived view from table changes
- A table mutation creates a record in its configured DynamoDB Stream.
- A consumer reads the change and computes the required update to the derived view.
- It applies the update with duplicate and version handling. A repeated old event must not replace a newer value.
- It saves recoverable progress after the result is safe.
- After a failure, it resumes within the retained stream window. An outage beyond retention requires another reconciliation source or a rebuild.

@@ postgresql
Transactions and Concurrent Operations >> Commit a correctness-sensitive transaction
- The service starts a transaction with the required isolation level.
- It locks the required rows or includes current-state conditions in its writes. It checks the business invariant against that protected state.
- It updates the related rows. Database constraints reject invalid results. Any required outbox record belongs in the same transaction.
- PostgreSQL commits under the selected durability policy. This includes the required WAL flush and configured synchronous replica acknowledgement.
- The service acknowledges success only after commit. It rolls back failures and retries the whole transaction when the error permits.
- Background work writes dirty data pages later. A transaction does not wait for a full checkpoint before it can commit.

Read Performance >> Execute an indexed read
- The application sends a parameterized query through its connection pool.
- PostgreSQL plans the query using its statistics, predicates, and available indexes.
- Execution reads candidate rows and checks visibility under the transaction's snapshot.
- The executor applies the remaining filters, joins, ordering, and limits. It returns the selected rows.
- If the query uses a replica, its result reflects that replica's progress. Route freshness-sensitive reads accordingly.

@@ flink
Basic Concepts >> Aggregate advertisement clicks in five-minute windows | 2
- The source reads click records from Kafka.
- keyBy groups records by advertisement ID. Each key reaches the operator instance that owns its state.
- The window operator assigns each event to its five-minute interval. It updates the count for that advertisement and window.
- The configured trigger emits the window result. For event-time windows, watermark progress and lateness policy control this boundary.
- The sink writes the aggregate to PostgreSQL. Replayed or corrected results must use the sink's defined update semantics.

How Flink Works >> Distribute a job across TaskManagers | 4
- The client submits the job graph to the JobManager.
- The JobManager constructs the execution plan and assigns tasks to available TaskManager slots.
- TaskManagers execute their assigned operators and exchange stream records as the graph requires.
- The JobManager monitors task health and coordinates checkpoints. It schedules recovery when tasks fail.

State Backends and Checkpoints >> Checkpoint and recover a streaming job
- The coordinator starts a checkpoint. Sources record recoverable positions and inject checkpoint barriers into the dataflow.
- Operators follow the selected checkpoint protocol to snapshot state consistently with stream progress.
- Tasks save checkpoint state durably and report completion. Compatible sinks also follow their checkpoint protocol.
- The coordinator completes the checkpoint after the required participants succeed.
- After a failure, tasks restore state from a completed checkpoint. Sources replay input from its saved positions.
- Replay can repeat external calls. End-to-end exactly-once effects require a compatible transactional or idempotent sink.

@@ zookeeper
ZooKeeper Basics >> Refresh a routing cache after a watched change | 8
- The chat server reads the relevant membership records and installs suitable watches.
- Another server changes the membership data, or an expired session removes its ephemeral records.
- ZooKeeper notifies clients with watches that cover the changed data or child list.
- The chat server rereads the current state and renews any one-shot watch. It updates its local routing cache.
- It routes later messages using that cache. Connection failures still require recovery if the cache has become stale.

2) Leader election and locks >> Elect a leader with ephemeral sequential nodes
- Each contender opens a session and creates an identifiable ephemeral sequential znode under the election path.
- It reads the contenders and compares their sequence numbers. The lowest eligible contender becomes leader.
- Other contenders watch their immediate predecessor. After a notification, they reread the election state before acting.
- If the leader's session expires, its znode disappears. The next eligible contender can take ownership.
- The new leader uses fencing or an ownership version at the protected resource. Old owners must not retain accepted write authority.
- Reconnecting contenders verify their session and current election state. A previous connection does not prove current ownership.

How ZooKeeper Works >> Commit a coordination write | 9
- The client submits a coordination update through its connected server. The ensemble leader handles the write proposal.
- The leader orders the update and sends the proposal to followers.
- A quorum of ensemble members records the proposal under the protocol.
- Once the commit conditions are met, the update commits and the client receives the result.
- If the response is lost, the client checks identifiable state before repeating an operation that could create another record.

When to Use >> Route a connection to the responsible chat server | 10
- The client requests a connection for a room or live stream through the API Gateway.
- The gateway reads the relevant server ownership and capacity information from ZooKeeper or its watched cache.
- It selects a server responsible for that room with available capacity.
- The client establishes the persistent connection to that chat server. Application messages then use the selected connection.
