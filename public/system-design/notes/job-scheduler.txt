Understanding the Problem
- The service accepts immediate, future, and recurring jobs. It starts each execution near its scheduled time.
- Scheduling determines when a job is ready. Execution assigns the work to a worker and handles its result or failure.

Functional Requirements
- Users can schedule a task now, at a future time, or on a recurring schedule.
- The system executes due jobs. Users can inspect each execution's status.
- Failed attempts follow a retry policy. The system retains execution history. Cancellation and rescheduling are optional extensions.

Non-functional Requirements
- The target is to start a job within two seconds of its scheduled time. This is a target, not an SQS guarantee.
- The scenario requires about 10,000 jobs per second. The service must tolerate scheduler and worker failures.
- Execution is at least once. A worker can complete an external operation before losing its acknowledgement. Tasks must handle retries safely.

Core Entities
- Task defines reusable work. Job identifies the task, user, parameters, and schedule.
- Schedule contains a date or recurring expression. Execution identifies one occurrence, due time, status, attempt count, and result.
- A lease can record the worker and an expiry time. A queue visibility timeout provides a related ownership mechanism.
- Keep recurring job definitions separate from execution records. A retry must not create another occurrence of the same schedule.

API
- POST /jobs accepts the task ID, schedule, and parameters. It returns a durable job identifier.
- GET /jobs returns the user's executions. It can filter by status and time range.
- Cancellation or rescheduling needs a defined rule for work that has already started. These operations are outside the initial scope.
- A stable submission identifier can prevent duplicate jobs after a request timeout.

High-Level Design

1) Schedule and dispatch
- The Schedule Service stores the job definition and its next execution before confirming acceptance.
- The initial Task Executor queries pending executions by due time. It loads the task parameters and runs the job.
- The precision deep dive adds a Watcher and a delayed queue. These components separate database polling from execution time.
- Keep queued messages small. Store large inputs separately and include their storage references in the job.

Process: Store and execute a job in the initial design
- 1. The client sends a task, schedule, and parameters to the Schedule Service.
- 2. The Schedule Service stores the job definition and the next pending execution in DynamoDB.
- 3. The Task Executor queries the relevant time bucket for pending executions that are due soon.
- 4. The executor loads the job parameters and starts the task at its scheduled time.
- 5. It records the result. A recurring definition produces a separate record for its next occurrence.

2) Monitor status
- Workers update execution status, such as pending, running, completed, retrying, or failed. Each transition includes a timestamp.
- A DynamoDB secondary index uses user ID and execution time. It supports ordered status queries without a full table scan.
- Logs and results include the execution ID and attempt number. This separates a scheduled occurrence from its retries.

Deep Dives

1) Scheduling precision
- Frequent scans of the entire job table create excessive load. Index or partition pending executions by scheduled time.
- The Watcher reads an upcoming window, such as five minutes. It places those executions in a queue before they are due.
- SQS delivery delay hides each message until near its due time. Workers poll continuously. Actual startup delay still needs measurement.
- A newly created job within the current window goes directly to the queue after durable storage. Otherwise, the Watcher could miss it.
- Redis sorted sets are another option. They require custom retry and recovery logic. Persisted due times remain authoritative after restart.

Process: Dispatch through a delayed queue
- 1. The Schedule Service persists the job and its next execution.
- 2. The Watcher queries its assigned time buckets for executions within the upcoming window.
- 3. The Watcher sends each execution to SQS with the appropriate delivery delay.
- 4. A newly created execution inside that window goes directly to SQS after storage. Stable execution IDs handle repeated dispatches.
- 5. Workers poll SQS. When a message becomes visible, a worker starts its task.
- 6. The worker stores the result before deleting the message. Measured queue and worker delay determines whether the timing target is met.

2) Throughput
- Partition job definitions by job ID. Add a shard suffix to time buckets so current-hour writes do not overload one partition.
- Watchers query the assigned time-bucket shards. Coordinate their ownership or deduplicate repeated dispatches.
- Add workers independently of schedulers. Separate queues can support different job types or priorities.
- Measure the age of the oldest due job and queue depth. Add capacity before a backlog breaks the timing target.
- Recurring jobs create the next execution with a stable occurrence ID. Retries must not create that occurrence twice.
- The source shows an optional queue before job creation. Add it only if direct service and database scaling are insufficient.

3) At-least-once execution
- After receipt, SQS hides a message for its visibility timeout. If the worker stops, the message becomes available again.
- A long-running worker extends visibility periodically. A timeout can still cause overlapping attempts, so task effects must be idempotent.
- Visible failures retry with increasing delay. Stop after the retry limit and retain the failed execution for inspection.
- A lost acknowledgement can repeat an external operation. Use downstream idempotency keys or a transaction that includes deduplication.
- Persist completion before deleting the queue message. A repeated delivery must recognize an already completed occurrence.
- A custom lease design needs conditional completion and ownership checks. A late worker must not overwrite a newer attempt's result.

Process: Recover a worker that stops responding
- 1. A worker receives an SQS message. SQS hides that message from other workers for the visibility timeout.
- 2. While the task runs, the worker periodically extends visibility.
- 3. If the worker stops renewing visibility, SQS makes the message available again.
- 4. Another worker receives the same execution. It checks for a completed result and uses the same downstream idempotency key.
- 5. The worker completes or safely repeats the task. It stores the result before deleting the message.
- 6. Repeated failures reach the retry limit. The system retains the failed execution or moves the message to a dead-letter queue.

Final Design
- Durable job and execution tables feed the Watcher. SQS delays eligible executions until near their due times.
- Workers execute tasks, update status, and delete completed messages. Visibility renewal and retries support worker recovery.
- The Query Service reads execution status. Stable occurrence IDs and idempotent task effects make repeated delivery safe.
