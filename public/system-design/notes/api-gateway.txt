What Is an API Gateway?
- An API Gateway is a shared entry point. It routes client requests to backend services.
- It applies common request policies. Clients do not need to know every internal service address.
- Routing is its main role. Add other responsibilities only when the application requires them.

Core Responsibilities and Request Flow
- Validate the request and run middleware. Select a backend, forward the request, and return the response in the required format.
- Limit gateway work. A common entry point should not execute all application business logic.

Process: Route one client request end to end
- 1. The client sends a request to the API Gateway.
- 2. The gateway validates the route, required headers, and request format. It rejects malformed requests.
- 3. It runs the configured middleware, such as authentication and rate limiting.
- 4. It routes the request to the appropriate backend. The diagram shows Business Service, Review Service, and Messaging Service as examples.
- 5. The selected backend performs its business checks and processes the request. It returns a response to the gateway.
- 6. The gateway applies required response transformations. It returns the result to the client and can cache eligible responses.

1) Request Validation
- Check the route, method, required headers, body format, and request-size limits.
- Reject malformed requests early. The service that owns the data still validates business rules.
- Gateway validation does not replace the backend's permission check for the requested resource.

2) Middleware
- Common middleware handles authentication, rate limits, TLS termination, logs, tracing, CORS, and timeouts.
- Validate identity with trusted configuration. Forward verified identity to services through a protected internal contract.
- Apply limits to the appropriate user, tenant, API key, or resource. One global rule may not fit all traffic.
- Exclude secrets and sensitive payloads from request logs.

3) Routing
- Match the request path, method, headers, or version to a backend service.
- Use service discovery and health information when selecting a backend instance.
- A load balancer distributes clients across gateways. The gateway can separately distribute requests across backend instances.

4) Backend Communication
- Forward requests over HTTP or another supported protocol. Reuse connections and enforce timeouts.
- Translate protocols only when needed. Translation can simplify the client contract, but adds work and failure cases.
- Retry only when the operation permits it. A timed-out payment request might already have charged the customer.

5) Response Transformation and Caching
- Transform response fields or headers when the client contract requires a different format.
- Store reusable responses in the cache with correct keys, expiry, and access rules.
- Keep personalized responses separate. A shared cache entry must not expose one user's data to another user.
- Expiry or invalidation limits stale results. Limit fallback traffic when a cache failure sends more requests to backend services.

Scaling an API Gateway
- Run stateless gateway instances behind a load balancer. Keep their routing rules and policies consistent.
- Use regional gateways when geographic delay or availability requirements justify them.
- Configure proxy buffering and timeouts for streaming or WebSocket traffic. Drain connections carefully when an instance stops.
- Reject or limit excess requests before downstream services become overloaded.

Managed and Self-Hosted Options
- Managed gateways reduce operational work and integrate with cloud identity and monitoring. Account for service limits and usage charges.
- Self-hosted gateways give more control. The team must manage upgrades, capacity, availability, and configuration changes.
- Explain the required behavior when choosing a gateway. Listing product names does not explain the design.

When to Propose One
- A gateway gives clients a stable interface to multiple services. It also centralizes common request policies.
- A simple application with one backend may not need another routing layer.
- Describe routing and required middleware briefly. Spend most design time on the application's difficult data and coordination problems.
