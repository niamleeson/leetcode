Understanding the Problem
- The system continuously identifies the most-viewed videos for a defined set of time windows.
- A large event stream drives the counts. Ranking requests must avoid scanning and sorting the entire video catalog each time.

Functional Requirements
- Clients can request the top K videos, with K limited to 1,000.
- Support all-time totals and completed tumbling windows of one hour, one day, and one month.
- Sliding windows and approximate results are extensions. Arbitrary historical intervals are outside the initial scope.

Non-functional Requirements
- The scenario uses about 70 billion views per day and billions of videos. Query responses should take tens of milliseconds.
- The initial contract requires exact counts with at most one minute of processing delay. Window boundaries and freshness must be explicit.
- Recovery must not permanently lose or count events twice. Checkpoints and downstream writes need compatible replay behavior.

Core Entities
- ViewEvent contains the video ID and event time. An event ID can identify repeated source events when deduplication is required.
- WindowCount holds a video's complete total for a specific window.
- RankingSnapshot contains the selected videos, counts, window boundaries, and processing position.

API
- The source assumes an existing Kafka view-event stream. A separate ingestion API is not required for this service.
- GET /views/top-k accepts a supported window and K. The response includes video IDs and view counts.
- Validate the window and K limit. Return freshness information so clients know which completed results they received.

High-Level Design

1) All-time and windowed counts
- The initial View Consumer reads Kafka events and increments per-video counters in PostgreSQL.
- The Top-K Service queries the largest counters. An index makes reads fast but adds work to each counter update.
- Hourly per-video rows support tumbling-window queries. Longer ranges require aggregation across those rows before ranking.
- Distinguish event time from arrival time. Delayed events need a defined cutoff or correction policy for published windows.

Process: Count views in the initial database design
- 1. The View Consumer reads a view event from Kafka.
- 2. It selects the PostgreSQL counter for the event's video ID.
- 3. It increments that counter. The query design uses the resulting totals to rank videos.
- 4. This initial path writes once per event. The ingestion deep dive adds partitioning and aggregation.

Process: Query an initial windowed ranking
- 1. The Top-K Service receives a supported time window and K.
- 2. It selects per-video rows whose event-time buckets belong to that window.
- 3. PostgreSQL sums each video's rows and orders the totals by count.
- 4. The service returns the first K entries. Large windows make this repeated aggregation expensive.

Deep Dives

1) Reduce repeated reads
- Store results in the cache by window and boundary. On a miss, the initial cache design computes the ranking from the database.
- A Top-K Cron can compute results before requests arrive. This removes slow database work from normal query responses.
- Store a top-1,000 list and return its first K entries. Do not cache every possible K separately.
- Monitor snapshot age. If precomputation fails, serve an explicitly older result or report that a fresh result is unavailable.

Process: Read a precomputed ranking
- 1. The Top-K Cron computes a ranking for each supported window before normal requests need it.
- 2. It writes a bounded ranking list and its window boundary to Redis.
- 3. The Top-K Service receives a request and reads the matching snapshot.
- 4. It returns the first K entries with freshness information. An unavailable or old snapshot follows the defined fallback policy.

2) Ingestion and writes
- Partition Kafka and database writes by video ID. Different consumers update different video subsets.
- Aggregate repeated views before writing totals. Flink can maintain window state and recover from checkpoints.
- Completed hourly windows reduce write volume, but publication must respect the one-minute delay budget after each window boundary.
- A viral video can overload one key. If partial counters split that key, combine them before the ranking stage.
- A checkpoint alone does not make every external write exactly once. Use idempotent totals or a sink with compatible commit behavior.

3) Efficient top K
- A heap or sorted structure maintains a small candidate set. It avoids a full sort for each request.
- Compute top K on each disjoint video partition. Merge those candidates to obtain the global top K.
- Each video's complete score must belong to one partition at this stage. Merge partial counts before selecting local candidates.
- Coarse aggregates reduce repeated summation. Dedicated window totals let the database index the exact values needed for ranking.
- Alternatively, Flink can keep counts and ranking state, then write snapshots directly to Redis. This removes the Views DB and Top-K Cron.
- Keep recoverable aggregate state. Rebuild a failed cache from a completed snapshot or replayable state, not guessed historical totals.

Process: Maintain ranking state in Flink
- 1. Flink reads Kafka events and assigns each event to its defined window.
- 2. It maintains recoverable per-video totals. Any split partial counts are combined before ranking.
- 3. Rankers select local candidates from complete scores. A merge stage calculates the global top K where partitions are used.
- 4. Flink writes the resulting snapshot to Redis with the window boundary and processing position.
- 5. The Top-K Service serves the requested prefix. Replay uses checkpoints and compatible sink behavior to avoid duplicate count effects.

4) Sliding windows
- A sliding window adds new views and removes views that leave its time range.
- Minute buckets let the processor add the newest contribution and subtract the expired one. All-time totals have no subtraction.
- Retain buckets for the largest window and allowed late events. Finer buckets increase precision and storage work.
- Define watermarks, lateness, and corrections. Coarse buckets approximate arbitrary boundaries unless the query contract aligns with them.
- Sliding totals can decrease. The ranking structure must recover newly eligible candidates when an earlier leader loses views.

Process: Advance a bucket-based sliding window
- 1. Flink groups new views into event-time buckets.
- 2. At the next boundary, the processor reads the oldest contribution that leaves the window.
- 3. It stores the newest bucket. It adds the new contribution and subtracts the expired contribution from each affected video total.
- 4. The ranking computation updates candidates from the revised complete totals. All-time counts have no expired contribution.
- 5. The system publishes a snapshot with its exact boundaries. Allowed late events update retained buckets according to the correction policy.

5) Approximation and specialized storage
- Count-Min Sketch estimates frequency with possible overestimation. It does not retain the item IDs needed to list the top videos.
- A separate heap or sorted set tracks candidate IDs. Approximation is allowed only after changing the initial exact-result contract.
- Redis can store sketches and candidates. Flink can keep both in checkpointed state. Their recovery paths have different costs.
- Explain the error bound and behavior near tied counts. Standard add-only sketches do not automatically solve window expiry.
- An analytical database can maintain rollups, but it still needs sufficient ingestion and aggregation capacity. Measure freshness and query delay.

Final Design
- Kafka feeds the Flink Application. Flink maintains recoverable window totals and calculates ranking candidates.
- Flink writes completed ranking snapshots to Redis. The Top-K Service returns the requested prefix through the API Gateway.
- Partition ownership, hot-key handling, checkpoint behavior, and explicit window rules determine correctness. Approximation remains a separate option.
