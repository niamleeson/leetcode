Understanding the Problem
- The service lists products that nearby distribution centers can deliver. Customers can order several items together.
- Availability depends on location and stock. A browsing result does not guarantee that the same stock will remain at checkout.

Functional Requirements
- Customers can query items that distribution centers can deliver to their location within one hour.
- Customers can place one order for several items. Availability combines stock from eligible distribution centers.
- Concurrent orders must not claim the same physical stock.
- Payments, driver routing, product search, cancellations, and returns are outside the initial scope.

Non-functional Requirements
- Availability requests should take less than 100 ms. They must scale separately from order writes.
- Orders require consistent stock updates. Checkout must check current inventory even when the browsing result came from a cache.
- The text assumes 10,000 distribution centers, 100,000 catalog items, and approximately 10 million daily orders. Order records must survive failures.

Core Entities
- Item describes a product type. Its identifier is the same across distribution centers.
- DistributionCenter contains the physical location and its delivery area.
- Inventory identifies physical stock at a distribution center. The quantity model groups this stock by center and item ID.
- Order and OrderItem record the customer, selected inventory, quantities, and delivery information.

API
- GET /v1/availability accepts the customer's coordinates and pagination parameters. It returns available items and quantities.
- POST /v1/order accepts the location and requested items. A production API can add an idempotency key for safe retries.
- The order response contains the committed order or an inventory conflict. The service checks delivery eligibility again during checkout.

High-Level Design

1) Find available items
- The Nearby Service first identifies distribution centers near the customer. The initial version uses geographic distance.
- The Availability Service reads inventory for those centers. It adds quantities across eligible centers and returns the combined result.
- An index on distribution center and item ID avoids a scan of all inventory.
- Product metadata changes less often than inventory quantities. Separate cache policies can reflect these different update rates.

Process: Determine deliverable inventory in the initial design
- 1. The customer sends a location and item filters through the API Gateway to the Availability Service.
- 2. The Availability Service asks the Nearby Service for eligible distribution centers.
- 3. The Nearby Service reads center locations. The initial design uses distance to select nearby centers.
- 4. The Availability Service queries inventory for the returned center IDs. It joins the item records for product details.
- 5. The service sums available quantities across those centers. It returns one page of results to the customer.

2) Place an order
- The Orders Service checks stock and records the order within one PostgreSQL transaction. The transaction also updates inventory.
- A serializable transaction, row locks, or conditional updates can protect stock. A separate application check cannot prevent concurrent claims.
- A multi-item order must fail as a unit if any item is unavailable. Consistent lock order reduces deadlock risk.
- Separate inventory and order databases require coordination and recovery after partial failure. One transactional database avoids that extra work.
- Payments are outside this article's scope. If added, slow payment calls must occur outside the short inventory transaction.

Process: Commit an order without overselling
- 1. The customer submits the requested items and delivery location to the Orders Service.
- 2. The service uses the Nearby Service to identify eligible distribution centers.
- 3. The Orders Service starts a short transaction on the PostgreSQL leader.
- 4. The transaction checks every required quantity. If any item is unavailable, the whole order fails.
- 5. If all items are available, the transaction updates inventory. It inserts the order and its item records.
- 6. PostgreSQL commits the transaction. Only then does the service return the accepted order.

Deep Dives

1) Incorporate traffic and driving time
- Geographic distance does not account for roads, rivers, or traffic. A nearby center can still exceed the delivery limit.
- A travel-time request for every center is expensive. The Nearby Service keeps an updated local copy of center locations.
- The service first filters centers by a generous geographic radius. It asks the Travel Time Service about only those candidates.
- Only centers within the delivery-time limit remain eligible. Any cached travel estimate needs an expiration that reflects traffic changes.

Process: Check driving time for nearby candidates
- 1. The Nearby Service periodically refreshes its local copy of distribution-center locations.
- 2. A request supplies the customer's location. The service selects centers within a generous geographic radius.
- 3. The service sends only these candidates to the Travel Time Service.
- 4. It removes centers that cannot meet the one-hour delivery limit. It returns the remaining center IDs.

2) Scale availability reads
- Redis can store availability results in a cache. On a miss, the Availability Service reads PostgreSQL and fills the cache.
- Cached quantities can be stale. The Orders Service still checks authoritative inventory and invalidates affected cache entries after a write.
- Read replicas serve browsing traffic. Regional partitions keep queries near the distribution centers they need.
- A practical cache key should group requests with the same eligible centers. Every arbitrary coordinate would provide poor cache reuse.
- A popular product or center can receive concentrated traffic. Capacity checks must include these local peaks.

Process: Read availability through Redis
- 1. The Availability Service obtains the eligible distribution-center IDs from the Nearby Service.
- 2. It checks Redis for a cached result for the selected centers and filters.
- 3. On a miss, it reads inventory and item records from PostgreSQL. Then it stores the result with a short expiration.
- 4. The service returns the result. A later checkout still checks the PostgreSQL leader before it changes stock.

Final Design
- The Nearby Service selects eligible centers. The Availability Service reads their inventory through the chosen cache or replica path.
- The Orders Service writes inventory and order records together on the PostgreSQL leader.
- A geographic filter reduces the number of calls to the Travel Time Service.
- Browsing can tolerate a short update delay. Checkout must still reject stock that another order has claimed.
