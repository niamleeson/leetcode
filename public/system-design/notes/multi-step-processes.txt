The Problem
- Business workflows often span several services and external systems, so one database transaction cannot cover every step.
- A process can crash after one side effect succeeds but before recording progress, leaving ambiguous state and unsafe retries.

Solutions


1) Single-server primitives
- Keep related writes in one short transaction when they share a database.
- A transactional outbox commits business state and a pending event together; a publisher retries delivery independently.
- The outbox closes the lost-publication gap but consumers still need deduplication because publication can repeat.

2) Saga pattern
- Represent a workflow as a sequence of local transactions with explicit compensation where later failure must reverse an earlier effect.
- Compensation is a new business operation, not a time machine: a refund is not the same as erasing a charge.
- Track progress durably and make forward steps and compensations retry-safe.
- Define which steps are reversible, which require manual resolution, and which outcomes are merely pending.

3) Event-driven choreography
- Services react to events and publish subsequent events, distributing workflow logic among participants.
- Choreography reduces central coupling for simple flows but makes end-to-end progress, failure ownership, and debugging harder as the workflow grows.
- Use correlation IDs and durable transition records so the workflow can be traced across services.
- Prevent cycles, duplicated reactions, and unbounded retries rather than assuming an event bus coordinates the whole process.

4) Workflow orchestration
- A coordinator records current state and directs activities, retries, timers, and compensation.
- Durable execution engines persist an event history and reconstruct workflow progress after a worker failure.
- Workflow decisions must replay deterministically; side-effecting I/O runs as activities with recorded results.
- Long waits use durable timers or external signals instead of holding a thread or transaction open.
- Managed state-machine systems and code-based workflow engines offer different programming and operational tradeoffs.

When to Use
- Use this pattern for payment flows, order fulfillment, reservations, onboarding, and other processes with multiple failure-prone steps.
- Avoid a workflow engine for a simple synchronous operation already covered by one database transaction.
- State the required recovery behavior before choosing a framework.

Common Deep Dives


1) Crashes and exactly-once effects
- Persist progress so a replacement worker can determine which steps are complete.
- An activity may execute more than once if its side effect succeeded but its completion acknowledgement was lost.
- Use stable business idempotency keys, transactional deduplication, or downstream status lookup to make retries safe.
- Durable orchestration does not automatically make external payments or emails execute exactly once.

2) Workflow changes
- Version workflow behavior so old histories can still replay under compatible code.
- Use explicit migrations or keep old worker versions for in-flight workflows when required.
- Test deployment behavior against workflows waiting on timers or external events, not only newly started workflows.

3) History size and external events
- Store large payloads outside workflow history and pass durable references.
- Bound history through checkpointing or continuation mechanisms supported by the engine.
- Correlate external callbacks to the correct workflow and deduplicate repeated or late events.
- Define timeouts and human intervention paths for workflows that cannot complete automatically.

Conclusion
- Treat a workflow as durable state plus retryable steps, not one long in-memory function.
- Explicit compensation, idempotency, versioning, and reconciliation make cross-service work recoverable.
