Understanding the Problem
- Merchants request payments from customers. The platform sends card transactions to external payment networks and reports their status.
- External networks can reply after a timeout. Keep an unknown outcome separate from failure so retries do not cause duplicate charges.

Functional Requirements
- Merchants can create payment requests. Customers can pay with credit or debit cards.
- Merchants can query the current payment status.
- Webhooks can send status changes to merchant servers. Refunds, subscriptions, saved cards, and merchant payouts are outside the initial scope.

Non-functional Requirements
- Retain transaction data and its change history. The system needs durability, auditability, and financial integrity.
- Protect customer payment details. Authenticate merchants before allowing them to create or inspect payments.
- The design targets more than 10,000 transactions per second at peak. Independent payments must scale without mixing their state transitions.

Core Entities
- Merchant contains the business identity, API credentials, and configuration. PaymentIntent records the amount, currency, customer, and overall payment state.
- Transaction records a money movement linked to one PaymentIntent. The example handles charges; one intent can have several attempts.
- Attempt records preserve each external request, reference ID, time, and outcome. Production ledgers can use separate entries for balance changes.
- The initial entity diagram lists Merchant, PaymentIntent, and Transaction. Hosted collection and token references reduce unnecessary exposure of card details.

API
- POST /payment-intents creates an intent with an amount and currency. Use a merchant-scoped idempotency key for retries.
- POST /payment-intents/{id}/transactions starts a transaction. Collect card details through the secure collection flow described in the security section.
- GET /payment-intents/{id} returns status and relevant errors. Optional webhook registration supplies a callback URL and subscribed event types.
- Repeated requests with the same merchant and idempotency key resolve to one payment. Reject incompatible parameters for an existing key.

High-Level Design

1) Create and execute payments
- The API Gateway authenticates the merchant. The Payment Service saves a created PaymentIntent and returns its ID; no charge occurs yet. The creation diagram names this component PaymentIntent Service.
- The Transaction Service saves a pending transaction. It submits the authorization request to the External Payment Network and records the response.
- Later network updates can change the transaction and PaymentIntent status. Authorization is not the same as completed settlement.
- Record each payment attempt before the external call. The transaction-safety deep dive adds reconciliation for uncertain outcomes.

Process: Create a payment intent
- 1. The merchant sends an amount and currency to the API Gateway.
- 2. The gateway authenticates the merchant and routes the request to the PaymentIntent Service.
- 3. The PaymentIntent Service saves a PaymentIntent with created status in the database.
- 4. The service returns the intent ID. Creating this record does not charge the customer.

Process: Submit a transaction to the payment network
- 1. The customer supplies payment details for the PaymentIntent. The security deep dive replaces merchant collection with hosted collection.
- 2. The Transaction Service creates a pending Transaction linked to that intent.
- 3. It submits the authorization request to the External Payment Network.
- 4. It records the initial approval or decline and updates the PaymentIntent state.
- 5. Later network updates change the stored transaction state as processing continues. A timeout requires reconciliation rather than an assumed failure.

2) Status updates
- The merchant requests the PaymentIntent through the API Gateway. The Payment Service reads the current record from the database.
- Return the stored status, related transaction details, and any error. Polling is sufficient for the initial design.
- A later webhook extension pushes changes to merchant servers. It uses committed database changes as its event source.
- A timeout does not establish failure. Keep an unresolved state until the payment network confirms the result.

Process: Read the current payment status
- 1. The merchant requests the PaymentIntent by ID through the API Gateway.
- 2. The gateway authenticates the merchant and routes the request to the Payment Service.
- 3. The service reads the current intent and related transaction details from the database.
- 4. It returns the stored status and any relevant error. The merchant can repeat this request while processing remains pending.

Deep Dives

1) Security
- A hosted iframe collects card details directly for the payment platform. The merchant server does not need to receive those details.
- The source adds application encryption before HTTPS transmission and protected server-side keys. These layers do not make compromised clients trustworthy.
- Authenticate requests with merchant credentials. Signed request data, a timestamp, and a nonce support tamper and replay checks.
- Keep secret keys on merchant servers. Limit access to sensitive payment services and exclude payment credentials from ordinary logs.

2) Durability and auditability
- Mutable status rows alone lose history. An append-only audit record can preserve each transition, but application code must write it reliably.
- Change Data Capture reads committed database changes and publishes them to Kafka. Key events by PaymentIntent to preserve per-payment order.
- Replicate the event stream and archive older events in S3. Monitor CDC progress and retention so a stalled consumer can recover.

3) Transaction safety
- A unique merchant/idempotency-key constraint prevents duplicate payment creation. Also handle retries at the external network and callback boundaries.
- Save the network name, reference ID, and intended operation before calling the network. Record success, explicit failure, or timeout afterward.
- The Reconciliation Worker consumes timeout events. It queries network status and compares settlement files with local attempts before updating records.
- Queue delivery guarantees do not guarantee one external charge. Use supported provider idempotency and preserve uncertain attempts for reconciliation.

Process: Resolve an uncertain external charge
- 1. The Transaction Service records the intended network operation and reference ID before sending the request.
- 2. The external call times out. The service records an unresolved attempt instead of declaring failure.
- 3. CDC publishes the committed attempt change to the Kafka Event Stream.
- 4. The Reconciliation Worker consumes the timeout event and queries the network using the recorded reference.
- 5. The worker also compares settlement files with local attempts when those files arrive.
- 6. It records the confirmed outcome once. Duplicate events or callbacks must not create another charge or state transition.

4) Scale and webhooks
- Partition Kafka by PaymentIntent for ordered events. Scale stateless services separately; database sharding by merchant is a later option.
- The Webhook Consumer reads CDC events from Kafka. It checks merchant subscriptions, signs matching payloads, and records each delivery attempt.
- Retry failed webhooks with backoff. Merchants verify signatures, handle duplicate events, and can query the current payment status.
- Archive old records and use read replicas where suitable. Isolate slow webhook destinations so unrelated payments can continue.

Process: Deliver a committed payment change
- 1. A payment status change commits in the database.
- 2. CDC publishes that change to the Kafka Event Stream.
- 3. The Webhook Consumer checks the merchant's subscribed events and callback URL.
- 4. It signs the payload, sends it to the merchant, and records the delivery result.
- 5. Failed deliveries retry with backoff and the same event identity.
- 6. The merchant verifies the signature, handles duplicates, and acknowledges receipt. It can query current status if events arrive out of order.

Final Design
- The Payment Service and Transaction Service keep current state in the database. Secure collection limits exposure of payment details.
- CDC feeds Kafka and S3 for durable history. The Reconciliation Worker resolves uncertain network results from recorded attempts.
- The Webhook Consumer sends committed changes to merchants. Per-payment ordering and idempotency support scale without assuming synchronous external outcomes.
