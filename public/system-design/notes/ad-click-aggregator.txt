Understanding the Problem
- The system records advertisement clicks and redirects users to advertisers. Advertisers query the recorded click totals.
- Redirects must remain fast. Separate click collection from aggregation so analytics work does not delay redirects.

Functional Requirements
- Users can click an ad and reach its configured destination.
- Advertisers can query click totals over time. The smallest requested interval is one minute.
- Count one click for each ad impression. Ad targeting, ad serving, and advanced fraud detection are outside the scope.

Non-functional Requirements
- The example has 10 million active ads and a peak of 10,000 clicks per second. Analytics queries should take less than one second.
- Retain accepted click events durably. The system must recover counts after a processor failure.
- Advertisers need recent totals. Precompute aggregates so each query does not scan all raw events.

Core Entities
- An Ad record identifies the advertiser and redirect URL. The Ad Placement Service supplies this metadata.
- A ClickEvent contains an event ID, ad ID, user ID when available, and timestamp.
- A MinuteAggregate contains an ad ID, minute timestamp, and click count. Retain raw events for reconciliation.

API and Data Flow
- The /click endpoint records a click and returns a 302 redirect. The browser then requests the advertiser's URL.
- A metrics endpoint accepts an ad ID and time range. It returns counts for the requested time intervals.
- The Click Processor uses the destination associated with the ad. The browser does not choose an arbitrary redirect destination.
- The data path is click collection, durable storage, aggregation, then analytics queries. Later designs add a separate raw archive.

High-Level Design

1) Click ingestion
- The browser sends the ad click to the Click Processor. The processor records the click before returning the redirect.
- A direct browser redirect with a separate tracking request is simpler. However, users can reach the destination without recording a click.
- Server redirects add a request to the path. Define what happens when recording fails; a fast redirect alone does not prove durability.

Process: Record a click before redirecting
- 1. The browser sends the ad click to the Click Processor.
- 2. The Click Processor obtains the redirect URL associated with the ad.
- 3. The processor records the click through the selected storage path. The next section compares those paths.
- 4. The processor returns a 302 response with the destination URL.
- 5. The browser follows the redirect to the advertiser.

2) Aggregation
- The basic design writes raw clicks to an analytics database. Queries count matching records, which becomes expensive as traffic grows.
- A batch design writes events to Cassandra. Scheduled Spark jobs aggregate them into an OLAP database, but results lag between jobs.
- A streaming design sends events through Kafka or Kinesis to Flink. Flink groups events by ad and event-time minute.
- Flink writes aggregates to the OLAP database. Watermarks and a late-event policy handle delayed events; frequent flushes expose provisional counts.

Process: Count raw events at query time
- 1. The Click Processor writes each event to the Analytics DB.
- 2. An advertiser requests counts for an ad and a time range.
- 3. The Analytics Service queries the matching raw events and groups them by time interval.
- 4. The service returns the counts. This scan becomes expensive as event history and query traffic grow.

Process: Build counts with scheduled batches
- 1. The Click Processor writes raw events to Cassandra.
- 2. The cron Scheduler starts a Spark job at the configured interval.
- 3. Spark reads the events and groups them by ad ID and minute.
- 4. Spark writes the aggregates to the OLAP DB.
- 5. The Analytics Service reads those aggregates for advertiser queries. Results remain stale until the next batch finishes.

Process: Maintain counts with stream processing
- 1. The Click Processor writes events to Kinesis or Kafka.
- 2. Flink reads the events and assigns them to ad ID and event-time windows.
- 3. Flink updates each window's count and handles delayed events under the configured policy.
- 4. Flink writes aggregates to the OLAP DB. Frequent flushes can expose provisional totals before a minute finishes.
- 5. The Analytics Service reads the stored totals for the advertiser.

Deep Dives

1) Scale ingestion and hot ads
- A load balancer distributes clicks across Click Processor instances. Partition the stream and Flink work by ad ID.
- A popular ad can overload one partition. Add a suffix to its partition key, then combine counts under the original ad ID.
- Batch aggregate updates to reduce database writes. Choose a flush interval that meets the required freshness.
- Monitor stream lag and available capacity. The OLAP database must combine partial counts without losing or repeating updates.

2) Durability and reconciliation
- Replicate the stream and retain events for recovery. The example uses seven days of retention; small windows can be replayed.
- Flink checkpoints preserve processing state. Recovery also needs a sink that handles replay without counting an event twice.
- Archive raw events in S3. Scheduled Spark jobs recompute totals, and a Reconciliation Worker compares them with streaming results.
- Correct affected OLAP records from the reconciled totals. Do not add the same historical count again during replay.

Process: Reconcile streaming totals with raw events
- 1. An independent stream consumer archives raw click events in S3.
- 2. A scheduled Spark job reads an archive interval and recomputes its totals.
- 3. The Reconciliation Worker compares those totals with the OLAP DB results.
- 4. The worker investigates differences and updates affected records with corrected totals.
- 5. Repeated reconciliation must replace or safely update those records. It must not add the same historical totals again.

3) Abuse and repeated clicks
- A user/ad pair is too broad for deduplication. The same user can legitimately see a new instance of the same ad.
- The Ad Placement Service generates a unique impression ID. It signs the impression ID and ad ID before sending the ad.
- The Click Processor verifies the signature and checks a Redis cache. It writes new clicks to the stream before caching their IDs. Reconciliation handles duplicates that survive a failure.

Process: Count one click for each impression
- 1. The Ad Placement Service creates an impression ID and signs it together with the ad ID.
- 2. The browser sends that identity and signature with the click.
- 3. The Click Processor verifies the signature and checks the Redis cache for a previously accepted impression.
- 4. For a new impression, the processor writes the click to the stream before adding its ID to the cache.
- 5. Reconciliation handles duplicates that survive a race or cache failure. Advanced fraud detection remains outside this design.

4) Query latency
- Query precomputed OLAP records by advertiser, ad, and time. This avoids repeated raw-event scans.
- Precompute daily or weekly totals for long queries. Keep minute totals available when advertisers need finer detail.
- Recent windows can be incomplete. Expose their freshness so advertisers know that the latest counts can change.

Final Design
- The Click Processor verifies impression IDs, records clicks, and redirects users. Kinesis or Kafka retains the accepted events.
- Flink maintains minute aggregates in the OLAP database. S3, Spark, and the Reconciliation Worker provide a separate correction path.
- The Analytics Service reads precomputed totals. Partitioning, impression deduplication, and reconciliation support scale and accurate counts.
