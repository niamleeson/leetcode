Overview
- Elasticsearch provides distributed search and analytics over documents. Lucene indexes perform the underlying search work.
- An application often keeps authoritative records in another database. Elasticsearch holds a derived search view with indexing delay and rebuild procedures.

Basic Concepts
- A document is a JSON record. An Elasticsearch index groups documents with related mappings and query behavior.
- Mappings define field types. Text fields support analyzed search. Keyword fields preserve exact values for filters, sorting, and aggregations.
- Select date, numeric, nested, and geographic field types for the required queries. Incorrect mappings can make those queries inefficient or impossible.
- A fundamental field-type change can require a new index and reindexing. Plan the transition before changing the data model.

Basic Use
- Create an index and define its mapping. Add documents with IDs that identify their logical records.
- A partial update still requires internal document reindexing. Frequent changes create additional writes, deletion markers, and merge work.
- Use match queries for analyzed text. Use exact filters for constraints that do not need relevance scoring.
- Use geo_point for coordinates and geo_shape for regions. Define whether a search uses distance, intersection, or a named boundary.
- Sort on suitable fields for price, recency, or popularity. Relevance uses a score. Add a stable tie-breaker when ordering must persist.

Pagination and Cursors
- from/size works for shallow pages. Deep offsets require shards to collect and discard many earlier results.
- search_after uses the previous page's final sort values. Keep the same sort order and a unique tie-breaker.
- A point-in-time context preserves a consistent view while documents change. Keep it with the pagination state.
- Close the point-in-time context when finished. Reserve scroll-style traversal for batch extraction where its behavior fits.

Process: Continue a search with a stable view
- 1. The client opens a point-in-time context. It sends the first query with a stable sort order.
- 2. The client keeps the final hit's sort values and the returned point-in-time identifier.
- 3. For the next page, it sends the same query and sort with those values in search_after.
- 4. Elasticsearch returns results after that boundary in the retained view. The client closes the context when traversal ends.

How It Works

1) Nodes and shards
- Primary shards divide the documents. Replica shards provide additional search capacity and copies for failover.
- Coordinating nodes send queries to relevant shards. They merge shard results and retrieve the selected document fields.
- The elected master manages cluster state and shard allocation. Ingest nodes prepare documents. Data nodes store shards and execute search work.
- More shards permit more parallel work. They also increase coordination, memory use, and overhead for small shards.

Process: Index a document, then run a distributed search
- 1. The client sends a document to the ingest node.
- 2. The ingest pipeline processes the document. It forwards the write to the appropriate data node.
- 3. The write reaches the primary shard and its configured replicas. The indexing request returns after its acknowledgement conditions are met.
- 4. A refresh makes the new indexed state searchable. This is a separate visibility boundary from the write acknowledgement.
- 5. The client sends a search request to a coordinating node.
- 6. The coordinating node queries the relevant shard copies. Each shard returns its matching candidates and ranking information.
- 7. The coordinating node merges the partial results. It fetches the selected source fields where needed.
- 8. It returns the final ordered results to the client.

2) Lucene segments
- Lucene stores indexed data in immutable segments. A refresh makes recent changes searchable. A write acknowledgement does not imply immediate search visibility.
- An update replaces the logical document and marks the old version as deleted. Background merges consolidate segments and reclaim obsolete data.
- Frequent refreshes improve freshness but consume resources. Merges also need CPU, I/O, and temporary storage.

Process: Replace a document in immutable segments
- 1. Lucene indexes the new version of the document. It marks the previous version as deleted instead of editing its segment.
- 2. A refresh exposes the new searchable state. Searches exclude the deleted version.
- 3. Later, a background merge creates a consolidated segment from existing segments.
- 4. The merge can remove obsolete document data. It is separate from the refresh that made the update visible.

3) Search data structures
- An inverted index maps terms to document postings. Stored positions support phrase queries where required.
- Doc values store fields in a column-oriented form. They support sorting and aggregations without reading every full source document.
- Reduce the candidate set before expensive scoring or sorting where possible. Selective terms can greatly reduce query work.
- A frequent term or broad query can return many candidates. Evenly distributed documents do not guarantee cheap queries.

In Your Interview
- Explain the search requirement first. Full-text ranking, geographic filters, or complex queries can justify a dedicated search engine.
- Connect database changes to indexing with reliable CDC or another recoverable publication mechanism.
- Track update versions and deletions. A delayed event must not restore an obsolete document.
- If stale permissions could expose restricted data, check current access before returning the content.
- Plan a rebuild and controlled index switch. Include changes that occur while the replacement index is loading.

Summary
- Elasticsearch combines specialized indexes with distributed execution. These features make complex search practical.
- The costs include extra storage, delayed search visibility, shard management, and continuous index maintenance.
- Use it when these trade-offs meet a real query requirement. A simpler query against the primary database may be sufficient.
