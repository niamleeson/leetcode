Understanding the Problem
- Players find an opponent of similar skill, play chess, and view rankings. This example uses three-minute blitz without added time.
- The Game Service owns the board, move order, clocks, and result. Client displays must follow that authoritative state.

Functional Requirements
- Players can request an opponent of similar rating and start a game.
- Players can send moves and receive board and clock updates in real time.
- Players can view the global leaderboard and their own rank. Spectators, chat, tournaments, and engine detection are outside the scope.

Non-functional Requirements
- Moves should reach the opponent in less than 200 ms. Prefer consistent game state over availability when the owner is unreachable.
- The example has 10 million registered players and 500,000 concurrent games. Each game needs two connections, for one million total.
- Prevent duplicate matches and moves. Clients must not decide whether a move is legal or how much time remains.

Core Entities
- Player stores identity and rating. MatchRequest records the player's rating and whether the player is waiting or matched.
- Game stores the two players, board, turn, remaining clock times, and result.
- Move records the game, player, squares, move number, and time. Its history lets a replacement server rebuild the board.
- Player records also contain ratings and win/loss totals. A later Redis leaderboard derives its scores from these durable records.

API
- POST /matchmaking creates a request. The service obtains player identity and rating from trusted server records; clients poll request status.
- A WebSocket at /games/{gameId} carries moves and acknowledgements. The expected move number prevents applying a retry as a new move.
- On connection or recovery, the Game Service sends the current board, move number, and both clocks.
- Leaderboard endpoints return a page of players or one player's rank. Define the ordering of equal ratings.

High-Level Design

1) Match players
- The Matchmaking Service writes a pending request in PostgreSQL. It searches for another pending player within an acceptable rating range.
- Create the Game and mark both requests matched in one transaction. The contention deep dive adds row locks around candidate selection.
- Clients poll until their requests contain a game ID. Widen the rating range as they wait, and eventually expire unmatched requests.

Process: Pair two waiting players
- 1. The Player Client requests a match through the API Gateway.
- 2. The Matchmaking Service reads the player's trusted rating and stores a pending MatchRequest in PostgreSQL.
- 3. It finds another pending player within the permitted rating range.
- 4. A short transaction claims the two requests, creates the Game, and marks both requests matched with the same game ID.
- 5. Clients poll their request status and receive the game ID. The contention section explains the row locks that protect this claim.

2) Run games
- Both players initially connect to one Game Service instance. It keeps the board in memory and processes moves sequentially.
- The Game Service verifies membership, turn, move legality, and remaining time. It rejects invalid moves without changing the board.
- Save each valid move and the updated Game record in one PostgreSQL transaction. Only after commit, acknowledge and broadcast the result.
- Recover the board from stored moves and game state after failure. A client's local board cannot replace the authoritative record.

Process: Accept and broadcast a chess move
- 1. Both clients connect to the same Game Service instance and receive the current board and clocks.
- 2. A player submits a move and expected move number over the WebSocket.
- 3. The Game Service checks membership, turn, legal movement, and the server-owned clock.
- 4. It saves the valid move and updated Game record in one PostgreSQL transaction.
- 5. After commit, it updates the in-memory board and sends the accepted move and clocks to both clients.
- 6. A stale or duplicate request cannot advance the turn again. Reconnecting clients fetch the server's current state.

3) Rankings
- When a game ends, the Game Service calculates both rating changes from the result and starting ratings.
- Save the final result and both player ratings in one transaction. The basic leaderboard queries the Players table by rating.
- A rating index makes the top page cheap to read. A player's rank still requires counting all higher-rated players.

Process: Update ratings and read the basic leaderboard
- 1. The Game Service determines the final game result.
- 2. It computes both players' rating changes from that result and their starting ratings.
- 3. One PostgreSQL transaction saves the final result and both rating updates.
- 4. A leaderboard request reads the Players table in rating order.
- 5. A personal-rank request counts higher-ranked players. The deep dive replaces this expensive count with a Redis ranking structure.

Deep Dives

1) Matchmaking consistency
- Lock pending MatchRequests inside a PostgreSQL transaction. SELECT FOR UPDATE SKIP LOCKED avoids selecting an opponent that another matcher holds.
- Recheck the requesting player's status under its lock. Before commit, failures roll back the game and both request changes.
- If PostgreSQL matchmaking becomes a bottleneck, Redis can hold the waiting pool. An atomic script claims both players, but cross-store failures still need recovery.

2) Game-server scale
- A Session Router maps each game ID to one Game Service instance. Consistent hashing limits reassignment when the server fleet changes.
- ZooKeeper supplies the current server list through registrations and heartbeats. Routers must use a consistent view of that list.
- An alternative shares state in PostgreSQL and sends moves through Redis Pub/Sub. Version checks serialize concurrent updates; Pub/Sub alone cannot recover missed moves.
- The final design keeps one in-memory owner for each game. Recover persisted state when routing changes or the owner fails.

Process: Route both players to one game owner
- 1. Game Service instances register with ZooKeeper and send heartbeats.
- 2. The Session Router builds its consistent hash ring from the available server list.
- 3. It maps both clients' common game ID to the same Game Service instance.
- 4. That instance owns the active board and clocks and processes moves sequentially.
- 5. If membership changes, affected clients reconnect to the new owner, which recovers persisted state before play continues.

Process: Process a move with shared state instead
- 1. In this alternative, clients can connect to different Game Service instances.
- 2. The receiving instance loads the current board, clocks, and version from shared state.
- 3. It validates the move and commits it in PostgreSQL only if the expected version still matches.
- 4. After commit, it publishes the accepted move through Redis Pub/Sub for that game.
- 5. The opponent's Game Service forwards the update through its client connection.
- 6. Clients detect missing move numbers and reload state. Redis Pub/Sub cannot replay a message missed during disconnection.

3) Fair clocks
- The server owns each player's remaining time. Local client timers only provide a smooth display.
- WebSocket pings measure round-trip delay. Credit a bounded recent median delay per move; the cap limits deliberate delay manipulation.
- The server also detects time expiry without waiting for another move. Regional servers reduce delay before clock compensation is necessary.

4) Leaderboard scale
- A Redis sorted set supports fast top ranges and exact rank positions. PostgreSQL remains the durable rating source.
- Commit both player ratings with the final result, then update Redis. Retry failed updates or rebuild the set from PostgreSQL.
- Define ties explicitly; the example uses player IDs to break equal scores. Approximate rating buckets are an alternative if exact rank is unnecessary.

Process: Refresh the derived Redis leaderboard
- 1. The Game Service commits a final result and both new player ratings in PostgreSQL.
- 2. It updates the corresponding scores in the Redis Leaderboard sorted set.
- 3. Top-player and personal-rank requests read this derived set, using the chosen tie-breaker.
- 4. If an update fails, retry it or rebuild the set from PostgreSQL. The durable ratings remain authoritative while Redis catches up.

Final Design
- PostgreSQL transactions protect matchmaking and game results. The Session Router sends both players to the same Game Service instance.
- The Game Service saves moves before sending updates and controls both clocks. ZooKeeper supplies the fleet membership used for routing.
- PostgreSQL stores durable ratings, and Redis serves the leaderboard. Reconnects recover server state instead of trusting a client's board.
