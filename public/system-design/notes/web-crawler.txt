Understanding the Problem
- The crawler follows links from seed URLs. It extracts text and stores that text for later processing.
- Crawling is a controlled traversal across many sites. It must limit work and respect each site's capacity.

Functional Requirements
- Accept seed URLs and fetch eligible linked pages.
- Extract and store text from fetched HTML. Extract links to continue the crawl.
- Avoid duplicate work and follow site crawl policies. Dynamic rendering, login-only pages, and non-text processing are outside the initial scope.

Non-functional Requirements
- The scenario targets about 10 billion pages within five days. This requires substantial parallel work across different sites.
- Recover from failures without losing crawl progress. Respect robots rules and avoid overloading individual hosts.
- Bound retries, crawl depth, response sizes, and concurrency. Slow hosts and crawler traps must not consume unlimited resources.

Core Entities
- URLTask contains the normalized URL, host, depth, priority, next eligible time, and attempt state.
- CrawlResult contains status, fetch time, content hash, and storage locations for raw HTML and extracted text.
- HostPolicy contains robots rules, request limits, and the next allowed request time.
- URL metadata and content fingerprints identify earlier discoveries and repeated content.

API and Data Flow
- The control interface accepts seeds and crawl configuration. It exposes progress rather than a user-facing page API.
- Crawlers resolve DNS, fetch HTML, extract text and links, store results, and add eligible discoveries to the frontier.
- Large HTML and text bodies belong in object storage. Queue messages contain identifiers or storage references.

High-Level Design
- The initial Frontier Queue contains seed URLs. A Crawler takes a URL and resolves its host through DNS.
- The crawler fetches the page, extracts text, and writes the text to S3. It adds discovered links to the frontier.
- Normalize URLs and check duplicate-discovery state before adding more work. Limit link depth and accepted URL schemes.
- The fault-tolerance deep dive separates fetching from parsing. This allows either stage to retry without repeating all prior work.
- Apply timeouts, redirect limits, and response-size limits. Restrict worker access to private infrastructure when URLs come from untrusted pages.

Process: Crawl and extract in the initial design
- 1. The Frontier Queue supplies a seed URL to the Crawler.
- 2. The Crawler resolves the hostname through DNS and fetches the webpage.
- 3. It extracts the text and saves that text in S3.
- 4. It extracts links and adds eligible new URLs to the Frontier Queue.
- 5. The crawler repeats this sequence. Later sections add durable stage boundaries and shared host limits.

Deep Dives

1) Fault tolerance and progress
- The fetch stage stores raw HTML in S3 and records its location in the URL Metadata DB.
- A separate Parsing Queue supplies HTML references to Parsing Workers. They store extracted text and discover more URLs.
- SQS visibility timeouts return unfinished tasks after a worker failure. Delete a message only after required output or downstream work is recoverable.
- Stable task and output identifiers make a repeated attempt safe. Persist visited and in-progress state outside worker memory.
- Increase retry delay after temporary failures. Move repeatedly failing tasks to a dead-letter queue instead of retrying forever.
- A Bloom filter saves memory but can report unseen content as already present. Use an exact index when that coverage loss is unacceptable.

Process: Fetch and parse through recoverable stages
- 1. A Crawler receives a URL from the SQS Frontier Queue.
- 2. It resolves the host and fetches the page under the applicable limits.
- 3. It stores raw HTML in S3 and its reference in the URL Metadata DB.
- 4. It makes parsing work recoverable before deleting the fetch message. The Parsing Queue carries the URL or storage identifier.
- 5. A Parsing Worker reads the HTML and checks duplicate content. It stores extracted text and enqueues eligible discovered URLs.
- 6. The worker deletes the parsing message after its required outputs are recoverable. Failed tasks retry with delay or enter the dead-letter queue.

2) Politeness
- Fetch each host's robots.txt rules and store them in the cache. Check disallowed paths and apply the chosen policy for crawl-delay directives.
- Coordinate request limits across all crawlers for that host. Separate per-worker limits do not enforce a shared host budget.
- A host-oriented frontier or shared rate limiter can schedule requests. An atomic claim prevents two workers from granting the same slot.
- Defer an already received SQS message by changing its visibility timeout. A new-message delivery delay does not change an in-flight message.
- Back off after throttling or repeated errors. Add random delay to avoid simultaneous retries. Identify the crawler and bound infinite URL spaces.

Process: Coordinate a host's next request
- 1. The worker obtains cached robots rules for the URL's host. It refreshes them according to the selected policy.
- 2. It rejects a disallowed URL and records that terminal result.
- 3. For an allowed URL, it checks the shared host delay and rate budget. An atomic claim reserves the next permitted request slot.
- 4. If the host is not eligible, the worker defers the task rather than sending immediately.
- 5. After the request, it updates host timing and health. Throttling or repeated failures increase delay for that host.

3) Throughput and scale
- Ten billion pages in five days requires about 23,150 successful pages per second. Add capacity for failed requests, retries, and variation.
- Distribute work across hosts while preserving each host's request limits. A single busy host cannot use all available crawl capacity.
- Use asynchronous I/O or bounded concurrent requests to overlap network waits. Scale Parsing Workers independently from network fetchers.
- Store DNS results in a cache and measure resolver capacity. DNS delay can limit throughput even when fetch bandwidth is available.
- Deduplicate normalized URLs before fetching. After fetching, compare content hashes so identical pages need not repeat expensive parsing.
- Limit crawl depth by link hops from a seed. Monitor successful fetches, host errors, queue age, storage throughput, and duplicate rates.

Final Design
- A durable SQS frontier feeds bounded Crawlers. Shared host rules, a rate limiter, and DNS caching control the fetch path.
- S3 retains raw HTML and extracted text. The URL Metadata DB stores progress, content hashes, and crawl depth.
- A separate Parsing Queue supports recoverable extraction. Visibility renewal, idempotent output, and coordinated host limits keep parallel crawling controlled.
