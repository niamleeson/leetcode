Overview
- Redis stores data structures in memory. Common uses include caches, counters, rankings, coordination, and messaging.
- Choose persistence, replication, eviction, and failure behavior for the intended use. Fast commands do not guarantee durable results.

Redis Basics
- A key identifies a value. Values can be strings, hashes, lists, sets, sorted sets, streams, or geospatial indexes.
- A TTL expires a key. An eviction policy removes keys under memory pressure. These controls solve different problems.
- Redis executes commands one at a time. An atomic command or short script can combine a check with an update.
- Long scripts and large blocking operations delay other commands. Limit the work in each request.

Infrastructure Configurations
- A standalone instance has one capacity limit and one failure boundary.
- Replicas provide copies for reads and failover. Replication is asynchronous, so promotion can lose recent acknowledged writes.
- Redis Cluster maps keys to 16,384 hash slots. Related keys need the same slot for most multi-key operations.
- RDB snapshots and AOF logging provide different recovery guarantees. The persistence settings determine the possible loss window and write cost.

Process: Route a key operation to its owning node
- 1. The client obtains the cluster's slot-to-node map.
- 2. It calculates the key's hash slot. It sends the command to the node that owns that slot.
- 3. The node executes the command against its in-memory data. Mutations also follow the configured persistence and replication paths.
- 4. The node returns the result. A normal acknowledgement does not prove that every replica or disk has received the write.
- 5. If ownership changed, Redis returns a routing response such as MOVED. The client refreshes its map and contacts the correct node.

Performance and Caching
- Store values that the application reads repeatedly in the cache. The cache key must identify the correct request parameters and access scope.
- On a cache miss, read the database and populate the cache. Define expiry, invalidation, and protection against simultaneous misses.
- Size the cache for memory, value size, and network traffic. One popular key can limit capacity before average throughput does.
- Batch commands or use pipelining to reduce network round trips. Configure an eviction policy when Redis serves as a cache.

Process: Read a value through the cache
- 1. The service requests the value from Redis.
- 2. If a valid cached value exists, the service uses it to answer the request.
- 3. If the key is missing or expired, the service queries the database.
- 4. The service stores the retrieved value in Redis with the chosen expiry. It returns the result to the caller.

Distributed Locks
- A basic lease uses SET with NX, an expiry, and a unique owner token. Only one request can create the key.
- Release the lease only when the stored token matches. An atomic check-and-delete script prevents deletion of another owner's lease.
- Expiry does not stop a paused worker from resuming. The protected resource needs fencing or another check against stale operations.
- Asynchronous failover can lose a lock grant. Enforce critical invariants in the database or a suitable consensus system.

Leaderboards, Rate Limiting, and Proximity
- A sorted set stores members with scores. Updating a member's score changes its rank without creating a duplicate member.
- Ranked queries retrieve the leading members. Remove low-ranked entries when the application needs only a limited result set.
- A fixed-window limiter increments a counter. Set expiry only for the first request, and perform both operations atomically.
- For a sliding window, atomically remove old entries, count the remaining entries, and record permitted requests in a sorted set.
- Geospatial commands store coordinates and find nearby members. The application still checks location freshness and other search filters.

Streams and Pub/Sub
- Streams retain entries with ordered IDs. Consumer groups track pending entries, acknowledgements, and ownership of delivered work.
- Pub/Sub sends messages to current subscribers. It does not retain missed messages for a disconnected subscriber.
- Stream recovery depends on retention and persistence. A Redis crash can lose recent entries under some persistence settings.
- A worker can claim an idle pending entry after another worker stops. Processing must tolerate repeated execution.
- Sharded Pub/Sub routes a channel to its owning node. A subscriber uses one connection per relevant node, not per channel.
- Use native Pub/Sub when its delivery model fits. A custom subscriber registry adds network requests, stale entries, and cleanup work.

Process: Consume a Redis Stream job with recovery
- 1. A producer appends an entry to the stream. Redis assigns a stream ID.
- 2. A worker reads through its consumer group. The group records the delivered entry as pending for that worker.
- 3. The worker performs the job. Its side effects must tolerate another attempt with the same logical job ID.
- 4. After the result is safe, the worker acknowledges the entry. This removes pending delivery state, not necessarily the retained entry.
- 5. If the worker stops, another worker claims sufficiently idle pending entries. It resumes processing under the same job identity.

Process: Deliver a live Pub/Sub message
- 1. A subscriber subscribes to channels on their owning Redis nodes. Several channels can share one node connection.
- 2. The publisher sends a message to the node that owns the channel.
- 3. Redis sends the message to subscribers that are currently connected to that channel.
- 4. A disconnected subscriber misses the message. Use Streams or another retained log when later recovery is required.

Hot Keys
- Sharding distributes different keys. Requests for one popular key still reach its owning primary.
- Local caches, duplicated keys, or configured replica reads can distribute read traffic. Replicas do not distribute writes to one key.
- Local and replicated copies can be stale. Define update and invalidation behavior for every extra copy.

When Not to Use and Summary
- Do not rely on an evicting cache as the only durable record. Persistence and failover settings can also permit data loss.
- Large cold datasets and complex relational queries may need another database. Clustered multi-key operations need careful key placement.
- Specify the data structure, access pattern, failure behavior, and memory policy. These choices explain Redis's role in the design.
