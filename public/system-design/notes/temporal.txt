Overview
- Temporal coordinates durable workflows that survive process crashes, waits, retries, and external events.
- It separates deterministic workflow decisions from activities that perform network calls or other side effects.

Building Durable Execution


1) Survive a crash
- Record workflow events and completed activity results in durable history.
- After a worker restart, replay the workflow against that history to reconstruct progress.
- Completed activity results are supplied from history rather than blindly repeating the same decision path's external calls.
- An activity can still repeat if its side effect completed before its result was recorded; its business effects must be idempotent.

2) Predictable replay
- Workflow code must make the same decisions for the same history.
- Use workflow-safe time, randomness, and orchestration APIs; ordinary nondeterministic I/O belongs in activities.
- Deploy code changes with compatible versioning so old histories do not become impossible to replay.

3) Wait and receive events
- Durable timers let a workflow sleep without keeping a worker thread occupied for the whole delay.
- Signals or other supported interaction mechanisms deliver external events to a waiting workflow.
- Correlate incoming events with the correct workflow and handle duplicate, late, or unexpected events explicitly.

Temporal Under the Hood
- The service stores workflow history and schedules tasks; application workers poll task queues and execute workflow or activity code.
- Workflow tasks advance orchestration decisions, while activity tasks perform the actual business work.
- Workers can fail or scale independently because durable workflow state is not confined to their memory.

State, Replay, and Workers
- History records decisions and results needed for replay, rather than serializing arbitrary application memory.
- Worker caches or sticky execution reduce repeated replay work, but durable history remains the recovery basis.
- Task queues route work to compatible worker pools and allow independent scaling by workload.
- Heartbeats and timeouts help detect failed or stalled long-running activities.
- Bound history growth and keep large payloads in external storage with durable references.

When to Use
- Use durable workflows for payments, reservations, fulfillment, scheduled multi-step processes, and other work needing explicit recovery.
- Activities can retry with backoff, while workflow logic decides compensation or escalation after terminal failure.
- A workflow's state makes progress and waiting conditions observable across long business processes.
- Simple one-step jobs may only need a durable queue and idempotent worker.

Limitations
- Temporal does not make an external system transactional or guarantee that an email or charge happens exactly once.
- Workflow determinism, code versioning, activity timeout policy, and history size are application design responsibilities.
- Cancellation must be cooperatively handled by activities and external services; it does not erase already completed side effects.
- Service operation and workflow debugging add complexity that should be justified by the recovery requirements.

Summary
- Durable history plus deterministic replay reconstructs workflow progress.
- Retry-safe activities perform side effects, and timers/signals represent waits without long-held processes.
- Choose Temporal when this durable coordination replaces substantial custom recovery logic, not merely because a task runs asynchronously.
