Understanding the Problem
- Build reliable private and group messaging with real-time delivery, offline recovery, and media attachments.
- A live connection is only a delivery path. Durable messages and delivery state must survive connection and server failures.

Functional Requirements
- Create group chats with up to 100 participants and send or receive messages.
- Deliver messages missed while offline, retaining them for up to 30 days in the interview scope.
- Support media attachments and multiple devices per user.

Non-functional Requirements
- Keep online delivery latency low while scaling to a very large number of persistent connections.
- Avoid losing acknowledged messages; accept retries and deduplicate them rather than assuming networks deliver exactly once.
- Preserve a defined ordering within each conversation, with durable recovery after disconnection.

Core Entities
- User, Chat, and ChatMember identify participants and membership permissions.
- Message includes message ID, chat ID, sender, sequence or ordering key, body, and timestamp.
- Device and delivery cursor track which messages each connected device has received.
- Attachment stores metadata and a reference to bytes in object storage.

API
- Use ordinary authenticated requests for chat creation, membership changes, and upload authorization.
- Establish a WebSocket for bidirectional message events, acknowledgements, and delivery updates.
- Send a client-generated message ID so retries can resolve to the same stored message.
- Reconnect with a durable cursor and fetch messages after that position rather than relying only on live events.

High-Level Design

1) Chats and message delivery
- Verify chat membership before accepting a message, then persist it before acknowledging durable acceptance.
- Route live events to the servers holding recipients' active connections.
- Keep undelivered messages or per-device cursors so offline recipients can catch up later.
- Distinguish server acceptance, device delivery, and read receipts; they are different states.

Process: Send a message and acknowledge delivery
- 1. The sender transmits a message over its authenticated connection with a chat ID and stable client message ID.
- 2. The chat service checks membership and assigns the ordering information required by the conversation model.
- 3. It persists the accepted message or recipient-delivery record before acknowledging durable acceptance to the sender.
- 4. The routing or pub/sub layer forwards the event to connection servers holding recipients' active device sessions.
- 5. Those servers send the message to their local devices. Offline devices retain a recoverable backlog or cursor gap in durable storage.
- 6. Each device deduplicates by message ID, stores or displays the message in order, and acknowledges its own delivery position.
- 7. Delivery or read receipts are separate updates; one device's acknowledgement does not prove every device or user has read the message.

2) Media attachments
- Storing media in the message database or relaying all bytes through chat servers makes storage and bandwidth expensive.
- Upload directly to object storage using signed instructions, then send an authorized attachment reference in the message.
- Downloads use signed URLs or equivalent access checks; protect private attachments even when served through a CDN.

Process: Send a media attachment
- 1. The sender requests an authorized upload session and uploads the attachment directly to object storage.
- 2. The backend verifies completion and produces an attachment reference with the required access metadata.
- 3. The sender submits a normal chat message containing that reference; message acceptance follows the durable message flow.
- 4. The recipient receives the reference, requests authorized access, and downloads the media directly from storage or a CDN.
- 5. Attachment upload failure prevents publication of a ready attachment; chat servers do not need to buffer the large file during message fanout.

Deep Dives

1) Connection routing at scale
- Stateless HTTP load balancing does not tell a sender which server owns a recipient's persistent connection.
- Consistent hashing can assign users to chat servers, but membership changes and failover require reconnect and routing coordination.
- Pub/sub lets connection servers subscribe to relevant users or conversations and receive events for their local clients.
- A Kafka topic per user creates excessive coordination overhead; choose partitioned durable streams and a separate live fanout layer where appropriate.
- Partitioning by chat preserves conversation locality; partitioning by user can simplify device delivery. Explain the fanout and subscription costs of the chosen model.

2) Multiple devices
- Track sessions and delivery progress per device, not just per user.
- Fan out to all active devices and retain enough history for an inactive device to resume.
- Acknowledgement from one device must not incorrectly imply every device received the message.

3) Failures, retries, and ordering
- Heartbeats detect dead connections sooner than relying on TCP timeouts alone.
- Retry unacknowledged messages with bounded backoff and stable IDs; clients and servers deduplicate repeated delivery.
- Use per-chat sequence numbers or a defined ordering policy, and recover gaps from durable storage.
- Treat pub/sub as a latency optimization when it is nondurable; missed live events must be recoverable from message history.
- Expire retained messages according to policy and explain what happens when a device reconnects beyond the retention window.

Process: Reconnect and recover missed messages
- 1. The client detects a broken connection through an error or missed heartbeat and reconnects with backoff.
- 2. It authenticates again and sends the last durably applied conversation or device cursor.
- 3. The server queries retained messages after that cursor and coordinates the handoff to live updates so no gap is skipped.
- 4. The client merges replay with any already received events, deduplicates IDs, and applies messages according to the ordering key.
- 5. It advances its cursor after successful local application and resumes acknowledgements. A cursor outside retention follows an explicit history-unavailable recovery path.

Final Design
- Durable chat/message storage owns membership, ordering, and recovery state.
- A horizontally scaled connection tier and routing or pub/sub layer deliver live events.
- Object storage handles attachments, while device cursors, acknowledgements, and idempotent retries make delivery reliable.
