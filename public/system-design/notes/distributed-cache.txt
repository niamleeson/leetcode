Understanding the Problem
- The task is to build the cache itself. It stores key-value pairs in memory across several machines.
- Confirm whether an authoritative store can rebuild lost data. The answer determines the required persistence and consistency guarantees.

Functional Requirements
- Clients can set, retrieve, and delete key-value pairs.
- Each entry can have an expiration time. A full cache removes entries according to the required LRU policy.
- The distributed design assigns keys to nodes and gives clients a way to locate those nodes.

Non-functional Requirements
- Get and set operations should take less than 10 ms. The scenario stores 1 TB and handles 100,000 peak requests per second.
- The cache scales across machines and remains available through individual node failures.
- The article accepts eventual consistency and excludes restart durability. A stricter cache contract would require additional coordination or persistence.

Core Entities
- CacheEntry contains the key, value, expiration time, and data needed for eviction.
- Cache Node owns a range of keys. The chosen replication model keeps additional copies on other nodes.
- A client or proxy uses the ownership map to route each operation.

API
- get(key) returns a value or a miss. set(key, value, ttl) creates or replaces an entry.
- delete(key) removes the entry. Deleting a missing key can safely have no further effect.
- The API defines key and value size limits. An expired entry must return a miss, even before background cleanup removes it.

High-Level Design

1) In-memory operations
- A hash table provides average constant-time key lookup and insertion.
- The first design keeps values on one Cache Node. Small allocations and limited copying reduce request overhead.
- Concurrent writes must preserve the hash table and associated metadata. A simple single-threaded loop or suitable locks can protect them.

Process: Execute an operation on one Cache Node
- 1. The client sends a get, set, or delete request to the Cache Node.
- 2. The node finds the key in its in-memory hash table.
- 3. A get returns the value or a miss. A set creates or replaces the value. A delete removes the entry.
- 4. The node returns the operation result. Expiration and eviction are added in the next design stage.

2) TTL and eviction
- A read checks expiration before returning a value. A Janitor removes expired entries that no client reads again.
- The LRU design combines a hash table with a doubly linked list. Each access moves the entry toward the most-recent end.
- A full cache removes the least-recent entry from both structures. Approximate eviction is an alternative only if the requirement permits it.
- Expiration removes an entry because its lifetime ended. Eviction can remove an unexpired entry because memory is full.

Process: Read an entry and maintain LRU state
- 1. The Cache Node looks up the entry in its hash table.
- 2. If the entry is absent, the node returns a miss.
- 3. If the entry has expired, the node removes it from the hash table and linked list. It returns a miss.
- 4. Otherwise, the node moves the linked-list entry to the most-recent end. It returns the value.
- 5. A new write that exceeds capacity removes the least-recent entry. The Janitor separately removes expired entries during cleanup.

Deep Dives

1) Availability and replication
- Replicas retain additional copies. The cluster needs a defined method to select a new owner after a failure.
- Synchronous replication waits for required replicas before acknowledgment. It adds latency and can block writes when a replica is unavailable.
- Asynchronous replication acknowledges the primary first. A replica can be stale, and failover can lose changes that did not reach it.
- Peer-to-peer replication lets several nodes accept writes. It requires conflict handling. For reconstructible data, controlled misses can be simpler than strong consistency.

Process: Replicate a write asynchronously
- 1. The client sends a write to the leader for that key range.
- 2. The leader applies the value and expiration changes in memory.
- 3. It acknowledges the write without waiting for every replica.
- 4. It forwards the change to its replicas. A lagging replica can temporarily return an older value if reads are permitted there.
- 5. If the leader fails before replication completes, the replacement may lack that write. The cache contract must permit or prevent this loss.

2) Distribution and growth
- Modulo hashing moves many keys when the node count changes. Consistent hashing remaps only affected key ranges.
- Virtual nodes can improve balance and represent unequal machine capacity. The routing map must identify their physical owners.
- A membership change updates routing and transfers affected entries. Clients need bounded retries while ownership changes.

Process: Locate a key on the hash ring
- 1. The client hashes the key into a position on the current ring.
- 2. It moves clockwise to the first owning node position.
- 3. It sends the request to that node. The node executes the operation on its local cache.
- 4. When membership changes, the cluster transfers affected ranges and publishes updated routing. Unaffected ranges retain their owners.

3) Hot keys
- One popular key can overload a node even when key counts are evenly distributed.
- A dedicated Hot Key Cache or replicated hot values spreads reads. Each extra copy also needs updates and invalidation.
- Batched increments or separate counter shards can reduce hot writes when the operation permits later aggregation.
- Arbitrary writes to one ordered value cannot scale merely by adding unrelated shards. The data's update semantics determine possible splitting.

Process: Distribute reads across copies of a hot value
- 1. Monitoring identifies a key with excessive read traffic.
- 2. The system creates several suffixed copies. Consistent hashing places them on different cache nodes.
- 3. A reader selects one copy, which spreads read traffic across those nodes.
- 4. A write updates or invalidates every copy under the chosen freshness policy.
- 5. When traffic falls, the system can remove extra copies. This method adds write work and suits mostly-read values.

4) Performance and recovery
- Clients reuse connections and batch suitable operations. Compact serialization and fewer network round trips reduce overhead.
- Request and value size limits prevent one large transfer from occupying a node for too long.
- Measure tail latency, hit rate, evictions, replication delay, and migration load. Rate-limit cache refill traffic after a failure.

Final Design
- Each Cache Node combines a hash table, expiration checks, a Janitor, and LRU bookkeeping.
- Consistent hashing routes keys. The illustrated design uses asynchronous primary-replica groups for availability.
- Read replicas distribute hot reads. Splittable hot writes can use suffixed keys and batching. Backing-store protection limits recovery load.
