Understanding the Problem
- Build a conversational AI product around model inference, durable chat history, and streamed responses.
- Model training is outside this design; the focus is scheduling expensive inference and delivering recoverable user interactions.

Functional Requirements
- Submit a prompt and receive a generated response.
- View past chats and continue a conversation with context from prior turns.
- Stream output, recover after reconnecting, and cancel an active generation.

Non-functional Requirements
- Minimize time to first token while keeping GPU utilization efficient.
- Persist messages and generation state and avoid starting duplicate costly runs after retries.
- Enforce fairness and tier-aware quotas under demand exceeding inference capacity.

Core Entities
- Conversation and Message store ownership, ordering, content, and relevant model metadata.
- Run stores generation state, request ID, model, usage, cancellation, and completion status.
- StreamEvent records ordered output chunks or lifecycle events for resumable delivery.
- QueueEntry carries scheduling priority and estimated resource cost.

API
- Create or select a conversation, then submit a message using an idempotency key.
- Return a run ID and stream endpoint; query run status separately from the live connection.
- Fetch paginated conversation history and reconnect to a run using the last event cursor.
- Cancel a specific run with an authenticated request; cancellation must propagate beyond the browser connection.

High-Level Design

1) Submit and generate
- Persist the user message and run before enqueueing generation work reliably.
- Assemble the model context with permissions and token limits, then schedule inference on an appropriate worker.
- Stream generated output and persist the final assistant message and terminal run state.
- Keep a lost browser connection from automatically creating another generation on reconnect.

Process: Submit a prompt and generate a response
- Step 1: The client sends conversation ID, prompt, and an idempotency key to the authenticated chat API.
- Step 2: The API validates ownership and quota, then persists the user message and a new run with recoverable scheduling state.
- Step 3: It returns the run ID so the client can connect to that run's output stream; repeated submission with the same key resolves to the existing run.
- Step 4: The context builder reads committed history and applies token-budget and summarization rules before submitting inference work.
- Step 5: The scheduler admits the run to an available compatible GPU worker or batch according to capacity and priority.
- Step 6: The worker generates ordered output chunks and appends them to the chosen replayable stream; connection servers forward those chunks to subscribed clients.
- Step 7: On completion, the system persists the final assistant message and terminal run state before exposing final completion. Failure and cancellation remain explicit terminal outcomes.

2) History
- Store messages in conversation order and fetch them with stable pagination.
- Record incomplete, failed, cancelled, and completed runs explicitly instead of pretending every partial response is final.
- Context assembly reads committed conversation state and applies the selected truncation or summarization policy.

Deep Dives

1) Token streaming
- SSE fits one-way token delivery while ordinary HTTP handles prompt submission and cancellation.
- WebSockets support richer bidirectional interactions but require additional connection lifecycle handling.
- Flush small chunks with sequencing and terminal events; proxy buffering must not delay the whole response until completion.

2) Reconnect and deploy recovery
- Separate generation workers from connection servers so a gateway restart does not terminate the underlying run.
- Redis Pub/Sub is useful for live events but cannot replay messages missed while disconnected.
- A bounded durable stream such as Redis Streams can retain ordered chunks and resume after a cursor.
- Persist final output separately and define retention limits; clients older than the replay window fetch the saved result or current snapshot.

Process: Resume an interrupted output stream
- Step 1: The browser loses its SSE or WebSocket connection while the run continues independently of the connection server.
- Step 2: It reconnects using the same run ID and its last applied event cursor instead of resubmitting the prompt.
- Step 3: The gateway authenticates access and replays retained events after the cursor from the run's stream.
- Step 4: The client deduplicates any overlap, appends events in sequence, and continues receiving newly generated chunks.
- Step 5: If replay retention has expired, the client fetches persisted final output or the supported current snapshot rather than inventing missing tokens or starting another paid run.

3) GPU scheduling
- A queue absorbs bursts and separates admission from inference capacity.
- Continuous batching groups active sequences efficiently, adding and removing requests as they start or finish.
- Bound queue wait, token budgets, and GPU memory use; large contexts and long outputs cost more than short requests.
- Apply backpressure before the queue becomes an unlimited promise of future GPU work.

4) Fairness and context cost
- Use per-user and cost-aware quotas rather than only a flat request count.
- Weighted priorities can improve paid-tier service while preserving capacity for other users.
- Prefix caching reuses identical context work; rolling summaries reduce context length but can omit details.
- Retain recent turns and important state deliberately, and separate summary storage from the original durable conversation.
- Cancellation must stop scheduling or generation and release GPU/KV-cache resources; closing SSE alone does not guarantee that.

Process: Cancel a running generation
- Step 1: The client sends an authenticated cancellation request for a specific run; closing the browser stream alone is not the cancellation operation.
- Step 2: The control plane records cancellation state and removes queued work or signals the current inference owner.
- Step 3: The worker cooperatively stops generation and releases the run's scheduling and KV-cache resources when safe.
- Step 4: The system commits the terminal cancelled state and usage/partial-output policy, then notifies connected clients.
- Step 5: A completion racing cancellation is resolved by the run's conditional state-transition rules so the run does not acquire conflicting terminal outcomes.

Final Design
- Durable conversations and run state feed a quota-aware inference queue.
- GPU workers generate independently of the connection tier, with replayable stream events supporting reconnects.
- Explicit run lifecycle, bounded context, and cost-aware scheduling connect a responsive UI to finite inference capacity.
