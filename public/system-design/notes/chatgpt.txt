Understanding the Problem
- Users send prompts, receive model responses, and return to saved conversations. The design covers the serving system around the model.
- Treat the model as a black box. Training, tools, multimodal input, message editing, and chat sharing are outside this example.

Functional Requirements
- Users can submit a text prompt and receive a generated response.
- Users can view past chats and continue a conversation with its earlier context.
- The deep dives add token streaming, reconnect recovery, and an explicit operation to cancel a generation.

Non-functional Requirements
- Target about 500 ms to the first token. The example assumes a peak of 20,000 prompts per second and 120,000 concurrent streams.
- Prefer availability for chat state and recover interrupted connections. Save the final assistant message; durable storage of every token is outside the scope.
- GPU capacity is limited. Allocate it fairly across users and subscription tiers, especially when demand exceeds available workers.

Core Entities
- User stores identity and tier. Chat groups ordered Message records, each with a role, content, and token count.
- A later Run entity identifies one generation attempt. It records the chat, message, model, status, and token usage.
- Redis Streams temporarily retain ordered token deltas for reconnects. PostgreSQL keeps completed messages as the durable history.
- A queue entry carries the run ID, assembled prompt, and estimated token cost. Later scheduling adds tier priority.

API
- POST /chats creates a chat. POST /chats/{id}/messages submits a prompt; the basic version returns the completed response.
- The streaming version returns a run ID promptly. GET /runs/{id}/stream opens the separate SSE response.
- List chats and messages with cursor pagination. Check chat ownership using the authenticated session before returning history.
- POST /runs/{id}/cancel explicitly stops a run. Closing the browser connection does not cancel generation.

High-Level Design

1) Submit and generate
- The API Gateway forwards a prompt to the Chat Service. The Chat Service first stores the user message in PostgreSQL.
- The basic Chat Service calls the Inference Service synchronously. The model returns the complete response after generation finishes.
- The Chat Service saves the assistant message and returns it. This first design can leave the user waiting through the whole generation.
- Keep the inexpensive Chat Service separate from GPU workers. Streaming, queues, and recovery are later improvements, absent from this baseline diagram.

Process: Generate a response in the baseline design
- 1. The Web Client posts a prompt through the API Gateway to the Chat Service.
- 2. The Chat Service writes the user message to PostgreSQL.
- 3. It calls the Inference Service synchronously with the prompt.
- 4. The Inference Service returns the complete generated response.
- 5. The Chat Service saves the assistant message and returns it to the client. Streaming and queues are later improvements.

2) History
- The Chat Service lists chats by recent activity. It loads one chat's messages in pages instead of returning an entire long history.
- For a follow-up prompt, read previous messages in order and preserve each role. Append the new user message to that context.
- Send the assembled context to the Inference Service and save its reply. Full-history prompts eventually exceed cost or context limits.

Process: Continue a saved conversation
- 1. The Web Client selects a chat and requests its messages through the Chat Service.
- 2. The Chat Service loads that chat's messages from PostgreSQL with cursor pagination.
- 3. For a new turn, the service orders prior messages by creation time and preserves their roles.
- 4. It appends the new prompt and sends the assembled context to the Inference Service.
- 5. It saves the new assistant response so the next turn can include it.

Deep Dives

1) Token streaming
- Polling delays token delivery and creates many empty requests. SSE gives the browser one open HTTP response for server-to-client updates.
- WebSockets also support streaming, but their bidirectional channel is unnecessary for this one-way output. Separate HTTP requests handle control operations.
- Initially, the Inference Service streams tokens to the Chat Service over gRPC. The Chat Service forwards each delta through SSE.

Process: Forward tokens through gRPC and SSE
- 1. The Chat Service saves the prompt and creates a Run, then returns its run ID.
- 2. The client opens an SSE request for that run.
- 3. The Chat Service sends the assembled prompt to an Inference Service worker.
- 4. The worker streams generated token deltas back over gRPC.
- 5. The Chat Service forwards each delta through SSE as it arrives. It does not wait for the whole response.

2) Reconnect and deploy recovery
- Separate generation from the Chat Service instance holding the client connection. A deploy can then replace that instance without restarting inference.
- Redis Pub/Sub separates publishers from subscribers but retains no missed messages. Tokens emitted during a reconnect gap would disappear.
- Redis Streams retain recent deltas with entry IDs. A replacement Chat Service reads after the client's last-seen ID and continues live delivery.
- Limit stream length and lifetime to bound memory. The worker saves the final message in PostgreSQL; an expired replay window needs a history fetch.

Process: Resume delivery from a Redis Stream
- 1. The inference worker appends token deltas to the Redis Stream for the run ID.
- 2. A Chat Service instance reads stream entries and forwards their IDs and deltas through SSE.
- 3. After a disconnection, the client reconnects with the same run ID and last applied entry ID.
- 4. The new Chat Service instance reads retained entries after that cursor, then continues with live entries.
- 5. The client ignores repeated entry IDs. If the replay window has expired, it fetches the saved result or supported current state.
- 6. At completion, the worker saves the full assistant message and terminal Run state in PostgreSQL.

3) GPU scheduling
- A request queue absorbs bursts. Inference workers pull requests only when they have capacity.
- Continuous batching advances several sequences together. When one finishes, the worker removes it and admits another queued request.
- Limit queue depth, wait time, token cost, and GPU memory use. A long prompt costs more than a short request.
- Reject or defer work when capacity is exhausted. An unlimited queue only turns overload into an unlimited wait.

Process: Admit work to a continuous GPU batch
- 1. The Chat Service checks admission limits and submits an accepted prompt with its run ID and estimated token cost.
- 2. The Request Queue holds the work until an Inference Service worker has capacity.
- 3. The worker adds the request to its active batch.
- 4. Each decoding pass advances the active sequences, and the worker appends output deltas to their Redis Streams.
- 5. When a sequence finishes or stops, the worker releases its slot and pulls another eligible request.

4) Fairness and context cost
- The Chat Service meters tokens after assembling context. It debits input tokens, reserves maximum output, and returns unused output budget afterward.
- Per-user limits prevent one user from taking all capacity. A Priority Queue favors paid tiers while reserving some capacity for free users.
- Prefix caching reuses model state for unchanged context. It reduces repeated input work but does not increase the model's context limit.
- Keep recent turns intact and summarize older turns. Summaries can omit details; update them less often to preserve a reusable prefix.
- Cancellation records the run state and signals the worker. The worker checks between batches, stops the sequence, and releases its resources.

Process: Cancel an active generation
- 1. The client sends POST /runs/{runId}/cancel. Closing SSE is not this cancellation operation.
- 2. The Chat Service records cancellation and publishes a control signal for the run.
- 3. The inference worker checks that signal between token batches.
- 4. It stops the sequence and releases its batch and model-state resources.
- 5. The final run state and usage follow the cancellation policy. Concurrent completion must not produce contradictory terminal states.

Final Design
- PostgreSQL stores chats, messages, and runs. The Chat Service applies token budgets and sends accepted work to the Priority Queue.
- Inference workers generate in continuous batches and append deltas to Redis Streams. Any Chat Service instance can resume SSE delivery.
- Prefix caching and bounded summaries control context cost. Explicit cancellation frees worker capacity without treating a disconnected client as a stopped run.
