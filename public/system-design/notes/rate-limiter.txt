Understanding the Problem
- The limiter decides whether a request fits a configurable user, API-key, IP-address, or resource allowance.
- Each decision occurs before expensive downstream work. The design must define what happens when shared accounting state is unavailable.

Functional Requirements
- The limiter identifies the requester, selects applicable rules, updates usage, and returns allow or deny.
- Operators can change rules without deploying application code.
- A rejected request receives HTTP 429 and useful information about when to retry.

Non-functional Requirements
- Each check should add less than 10 ms. The scenario assumes one million requests per second and 100 million daily users.
- Gateway instances share accounting state. Each instance must not independently grant the full global allowance.
- The scenario permits some distributed enforcement delay. Exact global limits require stronger coordination than this availability-oriented design.

Core Entities
- Rule defines its scope, capacity, time interval or refill rate, and applicable endpoints.
- ClientKey identifies a trusted user, API key, or network source. The key also identifies the relevant rule or resource.
- BucketState stores the counters, tokens, and timestamps needed by the selected algorithm.

API
- isRequestAllowed(clientId, ruleId) returns a decision, remaining allowance, and reset or retry information.
- Rule-management operations update configuration separately from per-request usage accounting.
- The gateway validates identity before choosing the key. An arbitrary forwarded-IP header must not establish a trusted source address.

High-Level Design

1) Identify and route requests
- In-process limiters are fast but see only local traffic. A separate Rate Limiter Service shares state but adds a network dependency.
- The chosen design places enforcement in the API Gateway. User IDs and API keys are more specific than shared NAT addresses.
- All applicable scopes must permit the request. A user allowance does not override an exhausted IP or endpoint limit.

Process: Enforce limits at the API Gateway
- 1. The client sends a request to the API Gateway.
- 2. The gateway validates its user identity, API key, or trusted source address.
- 3. It selects all applicable rules and obtains the allow or deny decision.
- 4. If every required rule permits the request, the gateway forwards it to the backend. Otherwise, it returns the rejection response.

2) Choose an algorithm
- A fixed window counts requests within one interval. Requests near adjacent window boundaries can create a large combined burst.
- A sliding-window log stores request timestamps. It gives accurate moving-window counts but uses more memory and processing.
- A token bucket adds tokens at a fixed rate up to its capacity. Each allowed request consumes tokens, which permits bounded bursts.
- A sliding-window counter estimates recent usage from current and previous counters. It uses less state but assumes a distribution within each window.
- The entire read, refill, check, and deduction must be atomic. A Redis script protects this sequence from concurrent requests.

Process: Decide a request with a token bucket
- 1. The gateway identifies the client and applicable bucket rule.
- 2. One atomic Redis script reads the bucket's token count and last-refill timestamp.
- 3. The script calculates elapsed time. It adds the corresponding tokens without exceeding bucket capacity.
- 4. If enough tokens remain, the script deducts the request cost. It stores the new count and timestamp together.
- 5. Otherwise, the script returns a denial and the time needed for sufficient refill.
- 6. The gateway forwards an allowed request or returns HTTP 429. A Redis failure follows the explicit outage policy.

3) Reject clearly
- The gateway returns HTTP 429 immediately when quota is exhausted. Retry-After reflects the algorithm's next useful retry time.
- Remaining-quota and reset headers help clients behave correctly. The server still makes the authoritative decision.
- Clients should retry with bounded backoff and jitter. The limiter does not queue unlimited excess interactive requests.

Deep Dives

1) Throughput
- Partition bucket state by client and rule so unrelated clients update different Redis shards.
- Short scripts reduce blocked time on each shard. Expiration removes inactive bucket state.
- The illustrated design checks shared state per request. Optional local token allocations reduce calls but require bounded grants and overshoot accounting.

Process: Route a bucket check to its owning shard
- 1. The API Gateway derives the client-and-rule key from the authenticated request and current configuration.
- 2. The Redis client determines the shard or hash slot that owns that key.
- 3. The owning Redis primary executes the atomic token-bucket check. Other gateways use the same key and ownership mapping.
- 4. Redis returns the decision. The gateway forwards the request or returns HTTP 429 with retry information.

2) Availability
- Fail-open behavior preserves access while Redis is unavailable. It can expose the backend to overload precisely when protection is needed most.
- Fail-closed behavior rejects requests that the limiter cannot verify. The source chooses this policy to protect the downstream system.
- The chosen outage policy must be explicit for each endpoint. A conservative local fallback is another option with weaker global enforcement.
- Redis replicas support failover, but asynchronous replication can lose recent deductions. The design must not promise exact limits across that failure.

3) Latency and hot keys
- Connection reuse removes repeated setup work. Nearby Redis instances reduce network delay. Gateways cache rule definitions locally.
- A single abusive or very active client can overload one bucket shard. Blocking, client batching, or explicitly bounded local grants can reduce pressure.
- More shards do not split one atomic counter. Legitimate users behind a shared IP need suitable limits and authenticated user-level rules.

4) Dynamic rules
- A configuration store publishes rule changes. Gateways can poll it or use ZooKeeper or Etcd notifications to refresh local rules.
- Each rule update needs a defined transition for existing bucket state. Version tracking detects gateways that still use old limits.
- Monitor rejections, decision latency, Redis errors, and configuration delay. Reconnect and refresh after a missed configuration notification.

Process: Refresh a rule through configuration notifications
- 1. An operator saves a validated rule update in the configuration store.
- 2. ZooKeeper or Etcd notifies connected gateways that the rule changed.
- 3. Each gateway reads the current version and replaces its local rule configuration.
- 4. New checks apply that version and the defined existing-bucket transition policy.
- 5. A reconnected gateway refreshes configuration before it resumes normal enforcement. Monitoring identifies gateways that remain behind.

Final Design
- The API Gateway validates identity and reads locally cached rules. It sends atomic checks to the Redis shard that owns each bucket.
- Token-bucket capacity controls bursts. The refill rate controls sustained allowed traffic.
- Replicas, an explicit outage policy, and reliable rule refresh make behavior predictable during normal traffic and failures.
