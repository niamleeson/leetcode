Understanding the Problem
- Track runs and rides from mobile GPS samples, then expose completed activities and athlete comparisons.
- The phone must remain useful without connectivity; cloud synchronization should not interrupt recording.

Functional Requirements
- Start, pause, stop, and save an activity.
- Show route, distance, and elapsed time during recording.
- View personal and friends' completed activities; consider live sharing and leaderboards as deep dives.

Non-functional Requirements
- Support offline recording and recover uploads without losing or duplicating samples.
- Scale to around 10 million concurrent activities in the interview scenario.
- Keep live tracking responsive and completed activities durable while controlling battery and network usage.

Core Entities
- User and Activity identify the athlete, activity type, start/end times, and summary metrics.
- LocationSample includes activity ID, sequence, coordinates, timestamp, and optional sensor measurements.
- Segment and LeaderboardEntry represent a defined route and an athlete's qualifying performance.

API
- Create an activity and obtain an ID; update its recording state and finalize it when complete.
- Upload batches of ordered samples with a retry-safe batch or sample identifier.
- Fetch activity details and a cursor-paginated list of visible activities.
- Subscribe to an authorized live activity and query segment rankings when those features are enabled.

High-Level Design

1) Record and display activity
- Record samples locally and calculate immediate distance/time feedback on the device.
- Upload samples asynchronously in batches, retaining unsent data until acknowledged.
- The server stores raw samples separately from derived summaries and validates activity ownership.
- Preserve sample timestamps so delayed uploads do not distort the route or duration.

Process: Record and synchronize an activity
- 1. The user starts an activity; the phone creates a local activity identity and persists recording state before collecting samples.
- 2. GPS samples receive timestamps and sequence numbers, are stored locally, and update the displayed route, distance, and time immediately.
- 3. When connected, the client creates or resolves the remote activity ID and sends batches of unacknowledged samples.
- 4. The ingestion service verifies ownership and stores or durably queues samples with deduplication keys, then acknowledges accepted batches.
- 5. The phone marks only acknowledged batches as synchronized; after disconnecting it continues recording and retries the rest later.
- 6. On stop, the client uploads remaining samples and requests finalization. The backend verifies required data before publishing a completed activity.

2) Read completed activities
- Finalization triggers processing to calculate summaries and prepare route data for efficient reads.
- Store summary fields in a queryable database and larger route payloads in suitable durable storage.
- Check activity visibility before serving routes or sharing location information with friends.

Process: Process and read a completed route
- 1. A finalized activity event queues summary and route-processing work.
- 2. Workers read the ordered samples, account for pauses, and derive distance, duration, display geometry, and any segment results.
- 3. They persist the derived data before marking that processing stage complete; repeated attempts replace or deduplicate the same activity version.
- 4. The reader requests activity details, and the service checks visibility before returning summary and route references.
- 5. The client renders the summary and fetches the appropriate route resolution; leaderboard updates follow from validated segment results asynchronously.

Deep Dives

1) Offline operation
- Persist the recording on the device so an app restart does not erase an ongoing activity.
- Reconnect by resending unacknowledged batches; deduplicate with activity/sample sequence identifiers.
- Handle pause/resume intervals explicitly rather than treating every gap in uploaded samples as continuous movement.
- Finalize only after all required batches arrive, or expose an incomplete state that can reconcile later.

2) High write volume
- Reduce per-sample overhead with batching and partition writes by activity or athlete plus time.
- Buffer bursts in a durable queue and process raw samples independently from the synchronous API.
- Avoid one global hot partition and monitor lag before accepting more work than the pipeline can retain.
- Downsample historical route data for display while keeping the fidelity required for metrics.

3) Live sharing
- Push recent locations to authorized viewers using SSE or WebSockets.
- Separate the ephemeral live position from durable activity history; reconnecting viewers can fetch the latest snapshot.
- Tune reporting frequency to balance freshness, battery drain, and server load.

4) Leaderboards
- Identify qualifying segment traversals and calculate performance from validated samples.
- Maintain a sorted ranking structure for fast top results and an athlete's rank.
- Keep durable performance records so cached rankings can be rebuilt; define ties and whether only personal bests count.

Final Design
- Local recording feeds a batched, retry-safe ingestion pipeline and durable activity storage.
- Background processors derive summaries and rankings; cached reads serve completed activities.
- Live location delivery is a separate authorized path, allowing recording and recovery to work even when live sharing fails.
