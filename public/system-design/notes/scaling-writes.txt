The Challenge
- Each write can update durable data, indexes, and replicas. Shared invariants can also force writes to run in sequence.
- Find the busiest constrained component. Adding application servers does not remove a single hot row or storage bottleneck.

The Solution

1) Vertical scaling and write optimization
- Measure CPU, memory, disk, and network limits before adding distribution. Better hardware can provide useful capacity with less architectural complexity.
- Shorten transactions, reuse connections, and remove unnecessary write work. Batch operations when their ordering and durability rules permit it.
- B-tree and log-structured engines make different tradeoffs. Sequential writes can improve throughput but leave more read or compaction work.
- Cassandra, time-series stores, and column stores fit different workloads. Choose from required operations and durability, not a generic SQL-versus-NoSQL label.

2) Sharding and partitioning
- Horizontal sharding spreads records across write owners. Redis Cluster, for example, maps hashed key slots to server nodes.
- Choose a key that spreads write traffic while keeping related reads local. A high number of possible keys alone does not ensure balance.
- A country key can overload populous regions. Hashing user IDs often distributes work better, but unusually active users still need attention.
- Vertical partitioning separates fields with different workloads. Post content, engagement counters, and analytics can use different stores or tables.
- Check how many shards each common read and write touches. Cross-shard operations add coordination, network calls, and failure cases.

Process: Route a Redis Cluster write to its slot owner
- 1. The Redis Client obtains the cluster's key-slot ownership map.
- 2. It hashes the requested key to determine the slot.
- 3. It sends the write to the server that owns that slot.
- 4. It refreshes routing information when ownership changes or the cluster redirects the request.

3) Queues and load shedding
- Kafka or SQS can buffer a short write burst. Workers drain accepted requests at a rate the database can sustain.
- A queue cannot fix permanent undercapacity. If arrivals remain faster than processing, both backlog size and completion delay keep growing.
- Queue acknowledgement means acceptance, not database completion. Provide a status path when callers need to know that the write finished.
- Shed or defer lower-priority writes before overload causes broader failure. For repeated location updates, a later update may replace an older one.

Process: Accept a burst and drain the write queue
- 1. The App Server validates the request and submits accepted work to the Write Queue.
- 2. It waits for the required queue acknowledgement before confirming acceptance to the caller.
- 3. A Worker reads the queued request and writes the result to the database.
- 4. It acknowledges progress only after the required output is safe.
- 5. The caller checks completion separately when needed. Queue age must remain bounded by capacity and admission policy.

4) Batching and aggregation
- Batching combines small writes to reduce network, transaction, and storage overhead. It adds a delay before the combined operation runs.
- Batch in an application or intermediate processor. Do not acknowledge volatile buffered data as durable unless a replayable source retains it.
- A Like Batcher combines increments per post. Hierarchical Write Processors can aggregate local changes before a Root Processor merges them.
- Broadcast Nodes then distribute the shared result to their clients. Retry and ordering rules must prevent repeated batches from duplicating effects.
- Larger batches improve efficiency only when work combines usefully. One like per post per window provides little aggregation benefit.

Process: Combine like events before database writes
- 1. Kafka receives individual like events.
- 2. The Like Batcher groups events by post during a chosen window.
- 3. It emits combined like-count changes into the downstream Kafka topic.
- 4. A consumer applies those changes to the Likes DB with the required retry protection.
- 5. The window trades fewer writes for delayed visibility. Sparse posts may gain little from this batch.

Process: Aggregate updates through a processing hierarchy
- 1. Clients send comments and likes to Write Processors selected by the relevant comment ID.
- 2. Each Write Processor combines local changes over a short window.
- 3. The Root Processor merges the batches into a shared update.
- 4. Broadcast Nodes receive that update and forward it to their assigned clients.
- 5. Each layer handles less traffic than a single all-to-all processor, at the cost of additional delay.

When to Use
- This pattern fits telemetry, click processing, search ingestion, feed updates, and live comments. Each can produce more writes than one component handles.
- Estimate normal and peak traffic. Identify whether storage I/O, CPU, network, lock contention, or one key causes the limit.
- Start with a simpler fix when it meets the requirement. Sharding and queues add failure modes and operational work.

Common Deep Dives

1) Resharding
- Reshard gradually while the system remains available. The source proposes copying records while writes reach both old and new locations.
- Dual writes can partially fail. Track and reconcile migration progress before moving read preference or write ownership permanently.
- Consistent hashing reduces how many keys move. It does not itself copy data or protect concurrent updates during migration.

Process: Migrate records while writes continue
- 1. The system selects the destination shards and records the migration boundaries.
- 2. It copies existing records while routing new changes to both old and new locations under the chosen migration protocol.
- 3. It tracks partial write failures and reconciles the destination until it reaches the required state.
- 4. Reads prefer the verified destination as ownership transitions. Stale routes need explicit forwarding or rejection behavior.
- 5. Retire the old copy only after validation and the rollback policy permit it. Dual writes alone do not guarantee a lossless migration.

2) Hot keys
- More shards do not divide writes to one key. A viral post can overload even a shard dedicated to that post.
- Split an additive counter into subkeys and combine their values during reads. This trades lower write contention for more read work.
- Split only hot keys when useful. Readers and writers must agree on all active subkeys before the transition can preserve totals.
- Some operations cannot be split independently, such as claiming one specific seat. Keep an authoritative owner and control incoming demand.

Process: Split an additive counter across subkeys
- 1. Writers and readers agree on the subkeys used for the logical counter.
- 2. Each writer chooses one subkey and applies its increment there.
- 3. A reader fetches all active subkeys and combines their values.
- 4. A dynamic split updates routing before new subkeys receive writes. Retried increments still need protection against duplicate application.

Conclusion
- Reduce work per component through local optimization, partitioning, queues, or aggregation. Choose only strategies compatible with the required semantics.
- Monitor queue age, partition load, retries, and storage or replication lag. Total throughput can hide one overloaded component.
- Explain the delay, freshness, and correctness cost of each scaling choice. Higher throughput alone does not establish a successful design.
