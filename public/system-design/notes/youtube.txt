Understanding the Problem
- The service accepts video uploads and supports playback. It processes each upload into formats for different devices and network conditions.
- The Video Service manages metadata. Object storage keeps media bytes. Processing workers create playable outputs. A CDN delivers popular media.

Functional Requirements
- Users can upload videos and inspect processing status.
- Users can watch a published video in a format that their device supports.
- Uploads must support large files and interrupted transfers. Recommendations, comments, search, and channel management are outside the core scope.

Non-functional Requirements
- Playback must start quickly with little buffering, including on slow networks. The design favors availability.
- Keep durable originals and recover from upload or worker failures. The service must support videos larger than 10 GB.
- The scenario has about one million uploads and 100 million views each day. Scale storage, processing, and delivery separately.

Core Entities
- User identifies an uploader or viewer. Video contains the media bytes. VideoMetadata stores the owner, title, status, and storage references.
- An upload session tracks each numbered part and whether storage has confirmed it.
- A processing job identifies the source, requested output format, attempts, and completion state.
- A primary manifest lists available formats. Each media manifest lists playable segments for one format.

API
- POST /presigned_url accepts video metadata. It returns signed instructions for a direct upload to object storage.
- The server verifies upload completion before it starts processing. A status request distinguishes uploaded content from playable content.
- GET /videos/{videoId} returns metadata and the manifest location. The client retrieves media from storage or the CDN.
- Use stable upload and video identifiers for retries. Duplicate completion notifications must not publish conflicting outputs.

Background: Video Streaming
- A codec compresses and decompresses video. A container packages video, audio, and metadata. Devices support different combinations.
- Bitrate measures data transferred per second. Adaptive bitrate streaming lets the player select a suitable format for each segment.
- Manifests identify the available formats and segments. One large original file alone does not provide adaptive playback.

High-Level Design

1) Upload and process
- The client uploads directly to object storage with a presigned URL. This avoids sending large files through application servers.
- The initial design stores the original. A later design creates several complete video formats. The improved design creates playable segments.
- After upload completion, the Video Processing Service splits the original into segments. It converts segments into the required formats.
- Workers store completed outputs before the service marks them ready. A published manifest must not reference missing segments.

Process: Upload the original video directly
- 1. The client sends video metadata to the Video Service through the API Gateway.
- 2. The Video Service stores the metadata and obtains a presigned upload URL.
- 3. The service returns the URL to the client. The client uploads the original directly to S3.
- 4. Completion verification starts the later processing stage. An uploaded original is not yet a playable set of video formats.

2) Playback
- The Video Service returns metadata and the manifest location. The client downloads segments from storage in the initial design.
- The client starts with a suitable format. It can change format at segment boundaries when bandwidth or buffer conditions change.
- A later CDN addition stores manifests and segments near viewers. This reduces geographic delay and requests to object storage.
- Private-video support would require authorized media requests, such as signed URLs. The source focuses on the upload and playback paths.

Process: Start and adapt playback from object storage
- 1. The client requests video metadata from the Video Service.
- 2. The service returns the manifest location. The client downloads the manifest from S3.
- 3. The client chooses a format for its device and network conditions. It downloads the first segment.
- 4. The client plays that segment and downloads later segments in the background.
- 5. At a segment boundary, the client can select another format. The CDN is an addition in the final design.

Deep Dives

1) Adaptive bitrate processing
- A task graph starts with video splitting. Segment transcoding, audio processing, and transcript generation can then run on separate workers.
- Workers run independent tasks in parallel. Dependent tasks wait for their required inputs. An orchestrator such as Temporal manages this order.
- Workers store temporary and final files in S3. Tasks pass storage references instead of transferring large files between workers.
- The service builds manifests after the required outputs exist. Stable output identifiers make retries safe.
- An internal queue can absorb upload bursts. Add workers when queued work or processing delay grows.

Process: Produce segments and manifests
- 1. The Video Processing Service receives the completed original's storage reference.
- 2. The Video Splitter divides the original into playable segments. It stores intermediate files in S3.
- 3. Workers transcode independent segments in parallel. Other tasks process audio and generate transcripts where required.
- 4. Dependent tasks wait for their inputs. Workers store completed outputs in S3.
- 5. The service builds media and primary manifests that reference the completed outputs.
- 6. The service stores the manifest locations in video metadata. It then marks the required processing complete.

2) Resumable uploads
- The client splits a large original into parts. Metadata records the part identifiers, fingerprints, and confirmed upload status.
- S3 returns a part number and ETag after a part upload. The client sends these values to the backend for verification.
- On reconnect, the client requests upload progress. It sends only missing parts and then completes the multipart upload.
- An object-level completion event starts processing. It does not report every uploaded part. Verify completion and handle duplicate notifications safely.
- Expire abandoned upload sessions and incomplete parts. Apply upload size limits before allowing unlimited storage use.

Process: Resume an interrupted upload
- 1. The client divides the original into numbered parts. The backend records the planned parts and their upload status.
- 2. The client uploads a part to S3. S3 returns the part number and ETag.
- 3. The client reports those values to the backend. The backend verifies the part with S3 before updating progress.
- 4. After an interruption, the client requests progress. It uploads the missing parts and completes the multipart upload.
- 5. The backend verifies the complete object. An object-level event starts processing; part progress does not depend on that event.

3) Scale storage and delivery
- Partition the Cassandra metadata database by video ID. Add Video Service instances behind a load balancer.
- Store frequently requested video metadata in a cache. This reduces pressure on a popular video's database partition.
- Store the formats needed for supported devices. Each additional format increases processing and storage cost.
- A CDN stores popular manifests and segments near viewers. Keep durable originals for later processing.
- Monitor processing delay, startup time, buffering, and CDN hit rate separately. These signals identify different capacity problems.

Final Design
- Direct multipart uploads store originals in S3. The Video Service manages metadata and verified upload progress.
- The Video Processing Service runs the task graph. It stores segments and manifests before marking the video ready.
- A metadata cache accelerates popular lookups. The CDN serves completed manifests and segments near viewers.
- Stable job identities and separate metadata, processing, and delivery capacity support recovery and growth.
