Understanding the Problem
- Users list items in timed auctions. A bid must exceed the current highest bid to be accepted.
- Bid acceptance needs strong consistency. Auction descriptions can tolerate delayed updates. The server determines the auction state and end time.

Functional Requirements
- Users can create an auction with an item, a starting price, and an end time.
- Users can submit bids and view the current highest bid.
- The system shows bid updates. The highest accepted bidder wins when the auction ends.

Non-functional Requirements
- The system orders competing bids for each auction. It must keep a durable record of each bid outcome.
- The scenario has 10 million concurrent auctions. Bid responses and updates must remain fast.
- Retries and process failures must not lose bids. They must not reopen a closed auction or accept an outdated bid.

Core Entities
- Auction contains the seller, item ID, starting price, end time, state, and highest bid. A version supports conditional updates.
- Item contains its name, description, and image URLs. A separate item record supports a later auction for the same item.
- Bid contains the auction ID, bidder, amount, time, and accepted or rejected status. A request ID can identify retries.
- User identifies the seller or bidder. Payment and settlement can use a separate workflow.

API
- POST /auctions creates an auction and its item record. The service validates the dates and starting price.
- POST /auctions/{auctionId}/bids submits a bid. A stable request ID can prevent duplicate processing after a timeout.
- GET /auctions/{auctionId} returns auction and item details. Live updates deliver later changes to the highest bid.
- A response must distinguish a received bid from an accepted bid. Bid history is an optional extension to the core API.

High-Level Design

1) Create and view auctions
- The API Gateway sends auction requests to the Auction Service. The service validates and stores auction and item data.
- The server controls time and auction state. The countdown on the client is only a display.
- The initial view returns a snapshot. Polling refreshes the highest bid. Later sections replace frequent polling with pushed updates.

Process: Create an auction
- 1. The client sends the item, starting price, and end time to the API Gateway.
- 2. The API Gateway routes the request to the Auction Service.
- 3. The Auction Service validates the request. It stores the auction and item records in the database.
- 4. The service returns the created auction to the client.

Process: View an auction
- 1. The client requests an auction by its ID.
- 2. The API Gateway routes the request to the Auction Service.
- 3. The Auction Service reads auction and item details from the database. It returns the current highest bid with the response.
- 4. The client polls for later changes in this initial design.

2) Accept bids
- The Bid Service checks whether a bid exceeds the current highest bid. It stores the accepted or rejected result.
- Keep bid history. Replacing only the highest price would remove evidence needed for audits and disputes.
- The initial read followed by a write has a race condition. The consistency deep dive adds an atomic update.
- The acceptance rule must also reject closed auctions and bids after the server's deadline.

Process: Submit a bid in the initial design
- 1. The client submits a bid through the API Gateway.
- 2. The API Gateway routes the request to the Bid Service.
- 3. The Bid Service reads the highest bid from the database. It compares the new amount with that value.
- 4. The service stores the bid with an accepted or rejected status. It returns the result to the client.
- 5. This initial sequence has a race condition. The next deep dive adds concurrency control.

Deep Dives

1) Strong consistency
- Locking existing bid rows does not prevent new bid inserts. Lock one auction row instead, for a short transaction.
- Redis can compare and update a cached maximum atomically. However, a cache update and a database write can fail separately.
- Keep the maximum bid on the auction row to use one database transaction. Store the bid result in that transaction.
- Optimistic concurrency uses the previous maximum or version as a condition. On conflict, read the current value and validate again.
- A queue can order bids for each auction. A queued bid is not yet an accepted bid.
- A unique request ID lets a retry return the original outcome after a lost response.

Process: Accept a bid with an auction-row transaction
- 1. The Bid Service starts a transaction. It locks the auction row or reads its version for an optimistic update.
- 2. It compares the bid with the current maximum. The acceptance rule also checks auction state and the server's deadline.
- 3. For a valid higher bid, it updates the auction maximum. It stores the bid outcome in the same transaction.
- 4. The service commits the transaction before confirming acceptance. A version conflict requires a new read and validation.
- 5. A retried request uses its stable ID to recover the original outcome.

2) Durability and closing
- A producer writes incoming bids to Kafka before the system confirms receipt. Partition by auction ID to keep their order.
- The Bid Service consumes queued bids and stores their outcomes. A failed consumer can retry a retained message.
- Configure persistence and replication for the required durability. Confirm acceptance only after the database commits the outcome.
- Closing must use the same consistency boundary as acceptance. A delayed closing job must not permit bids after the deadline.
- Define how the deadline applies to queued bids. Server receipt time and processing time can differ during a queue delay.

Process: Retain and process bids through Kafka
- 1. The client sends a bid through the API Gateway. The gateway routes it to a producer.
- 2. The producer writes the bid to Kafka with the auction ID as its partition key.
- 3. Kafka confirms the write. The client can now receive confirmation of receipt, but acceptance is still pending.
- 4. The Bid Service consumes the bid. It validates the bid and commits the outcome in the database.
- 5. A failed consumer retries the retained message. A stable request ID prevents a second application of the same bid.

3) Real-time updates
- The source design uses SSE to send highest-bid updates from the server to clients. WebSockets are another option.
- Each server keeps its local client connections. Shared publish-subscribe channels deliver updates to the other relevant servers.
- On reconnect, the client fetches the current auction state. An event cursor can support recovery where the event system retains history.
- Compare event versions or ordering information. An old or duplicate event must not reduce the displayed highest bid.

Process: Push the current highest bid
- 1. The client opens an SSE connection when it views the auction.
- 2. The Bid Service commits an accepted bid and the new highest value.
- 3. The server sends the updated value to its connected viewers. The final design uses publish-subscribe channels between server instances.
- 4. The client applies the update only if it is newer than its displayed state.

4) Scale
- Partition Kafka and the database by auction ID. This keeps each auction's ordered operations together.
- The source estimates about 15,000 bids per second at peak. Measure actual capacity before deciding the number of database shards.
- Add Bid Service and Auction Service instances independently. A popular auction remains a hot key despite partitioning.
- Keep the serialized bid operation short. Store stable item details in a cache, separate from the changing bid state.

Final Design
- The Auction Service manages auction details. Kafka retains incoming bids. The Bid Service commits bid outcomes in the database.
- A maximum on each auction row supports consistent acceptance. The database retains the complete bid history.
- Shared publish-subscribe channels connect Bid Service instances. Each instance pushes updates to its connected clients through SSE.
- Stable request IDs, atomic closure, and durable recovery records protect retries, deadlines, and failures.
