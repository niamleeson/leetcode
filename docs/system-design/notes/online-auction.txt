Understanding the Problem
- Build timed auctions where only a bid higher than the current highest bid is accepted.
- Bid acceptance and auction closure are correctness-sensitive state transitions, even if auction browsing is eventually consistent.

Functional Requirements
- Create an auction with item information, starting price, and end time.
- Place bids and inspect the current highest bid.
- Show bid updates and determine a winner after the auction closes.

Non-functional Requirements
- Serialize competing bids for the same auction and preserve durable bid history.
- Keep bid feedback and live updates responsive while supporting many concurrent auctions.
- Recover safely from retries and process failures without reopening a completed auction or accepting a stale bid.

Core Entities
- Auction includes seller, item, end time, state, highest bid, and version.
- Bid includes auction ID, bidder, amount, request ID, and authoritative acceptance time.
- User identifies the authenticated seller or bidder; settlement can be a separate workflow.

API
- Create an auction with validated timing and price parameters.
- Submit a bid with auction ID, amount, and idempotency key.
- Fetch auction details and bid history; subscribe to live bid updates.
- Return whether a bid was accepted, distinguishing that result from merely receiving the request.

High-Level Design


1) Create and view auctions
- Persist auction metadata and serve read-heavy descriptions through cacheable views.
- The server owns the clock and auction state; client countdowns are only a display.
- Live notifications update the UI, but the authoritative bid path still checks the database.

2) Accept bids
- Atomically check that the auction is open, its deadline has not passed, and the bid exceeds the current highest value.
- Write the accepted bid and update auction state within the same consistency boundary.
- A separate read followed by an unconditional write allows lower or competing bids to overwrite each other.

Deep Dives


1) Strong consistency
- Row locking or optimistic version checks can serialize updates for a single auction.
- Optimistic conflicts need retries that re-evaluate the current highest price and deadline, rather than blindly repeating an old update.
- A per-auction ordered processing stream is an alternative, but the system must distinguish queued bids from accepted bids.
- Use a unique request ID so retrying after a lost response returns the original outcome.

2) Durability and closing
- Persist accepted bids before acknowledging them, with replication and recovery appropriate to the durability requirement.
- Closing the auction must compete atomically with bids; late requests must not be accepted after closure.
- Use authoritative server time and an explicit rule for bids racing the deadline.
- Background closing jobs may be delayed, so a stale open flag alone must not allow bids after the end time.

3) Real-time updates
- Publish accepted bid events to viewers through SSE or WebSockets.
- Fan out from shared channels to connection servers rather than opening a separate database poll for every viewer.
- On reconnect, fetch the latest auction snapshot and resume events from a cursor when available.
- Duplicated or out-of-order notifications must not move the displayed highest bid backward.

4) Scale
- Partition by auction ID so unrelated auctions proceed independently.
- A single popular auction is still a hot key; isolate it, control admission, and keep its serialized write path short.
- Cache static item data separately from rapidly changing bid state.

Final Design
- A durable transactional auction/bid store decides acceptance and winners.
- Caches and live event fanout scale the viewing experience independently.
- Idempotent requests, atomic closure, and recovery records preserve correctness around deadlines and failures.
