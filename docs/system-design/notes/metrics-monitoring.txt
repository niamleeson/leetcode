Understanding the Problem
- The platform collects service metrics, serves dashboards, evaluates alert rules, and sends notifications.
- Each metric name and unique label set defines a series. High sample rates and many series both increase cost.

Functional Requirements
- Services can submit metrics. Users can query them by label, time range, and aggregation for dashboards.
- Users can define alert thresholds and the duration required before an alert fires.
- Users receive notifications through configured channels. Logs, distributed traces, and machine-learning anomaly detection are outside the scope.

Non-functional Requirements
- The example monitors 500,000 servers at five million samples per second. Dashboard queries should return within seconds over long ranges.
- Alerts should fire within one minute of metric emission. The design accepts eventual consistency for dashboards and handles late samples.
- The platform must remain available during spikes and failures. Limits must prevent uncontrolled growth in the number of series.

Core Entities
- A Metric has a name, value, timestamp, and labels. Each Label is a key-value pair used for filtering.
- A Series contains timestamp/value pairs for one metric name and label set. Each distinct combination creates another series.
- An Alert Rule contains a query, threshold, duration, and notification targets. A Dashboard groups query panels.
- Retention and rollup settings define which resolutions remain available. Alert state distinguishes an ongoing incident from a new transition.

API and Data Flow
- POST /metrics/ingest accepts sample batches. Agents collect and buffer samples before the Ingestion Service validates them.
- GET /metrics/query accepts a query, start time, end time, and step size. It returns timestamps and values for display.
- POST /alerts/rules stores alert definitions. Rule changes are much less frequent than sample ingestion.
- The path is agents, ingestion, Kafka, storage, queries, alert evaluation, then notification delivery.

High-Level Design

1) Ingestion
- Direct writes from every server overwhelm central storage. Agents collect and batch samples locally to reduce request volume.
- The Ingestion Service validates batches and publishes them to Kafka. Ingestion Consumers write samples to storage at their own pace.
- Partition by metric series and time. Kafka retention and agent buffers support retries, but recovery capacity must exceed ongoing traffic.

Process: Collect, buffer, and store metric batches
- 1. Each Agent collects local samples and groups them into batches.
- 2. The Agent sends a batch to the Ingestion Service.
- 3. The Ingestion Service validates the batch and publishes accepted samples to Kafka.
- 4. Ingestion Consumers read their assigned partitions and write samples to storage.
- 5. Consumers advance progress after the required writes succeed. Retries must not create duplicate sample effects.

2) Dashboards
- Use a Time-Series DB such as InfluxDB, TimescaleDB, or VictoriaMetrics. Time partitions, compression, and series indexes support the workload.
- The Query Service selects a resolution suitable for the requested chart. Long queries can read rollups instead of every raw sample.
- Keep query processing separate from ingestion. Redis can store repeated dashboard results in a cache when the freshness requirement permits it.

Process: Read a dashboard from time-series storage
- 1. The Dashboard requests a query, time range, and display step from the Query Service.
- 2. The Query Service selects the relevant series and time partitions.
- 3. It chooses raw samples or available rollups that can answer the requested calculation.
- 4. The Time-Series DB returns the selected data.
- 5. The Query Service combines the results and returns bounded chart points to the Dashboard.

3) Alerts and notifications
- The Alert Service reads rules from an Alerts DB and periodically queries stored metrics. This polling design meets the initial latency target.
- A rule can require the threshold to remain exceeded for a duration. Define how missing or late data affects that condition.
- The Notification Service tracks firing and resolved states. It groups related alerts, applies silences, and retries delivery to external channels.

Process: Evaluate a rule and deliver its state transition
- 1. The Alert Service reads enabled rules from the Alerts DB.
- 2. It periodically queries the Time-Series DB and evaluates each rule's threshold and duration.
- 3. A breached or resolved condition produces an alert event for the Notification Service.
- 4. The Notification Service checks its stored alert state and suppresses repeated notifications for the same ongoing condition.
- 5. It groups related alerts and sends them to configured channels such as Slack or PagerDuty.
- 6. Failed delivery attempts retry independently of rule evaluation.

Deep Dives

1) Long-range queries
- Retain recent raw samples and older rollups at coarser resolutions. Select retention periods from the product's query requirements.
- Rollups lose detail. Preserve sums and counts for weighted averages; percentiles need histograms or suitable sketches, not averages alone.
- Split long queries into recent and historical ranges. Query recent data for freshness and use cached historical results where valid.
- Precompute common dashboard queries. Data corrections and backfills must invalidate affected cache entries.

2) Low-latency alerts
- More frequent polling reduces detection delay but adds database queries. Keep alert work from blocking behind expensive dashboard requests.
- Flink can read Kafka as a second consumer and evaluate rolling windows. Checkpoint its state and handle late data and rule changes.
- Streaming evaluation is an optional deep dive for tighter latency. Measure collection, ingestion, and evaluation delays separately.

Process: Evaluate an urgent alert from the stream
- 1. Flink reads the same Kafka metrics stream as the storage consumers.
- 2. It updates window state for the relevant metric series.
- 3. It evaluates the configured rule against that window, including the required duration.
- 4. When the rule fires, Flink sends an alert event to the notification path.
- 5. Checkpoints preserve evaluation state after a worker failure. The scheduled Alert Service can continue handling less urgent rules.

3) Availability and cardinality
- Replicate Kafka and storage, retry agent uploads, and retain alert events before external delivery. Independent monitoring must detect failures in this platform.
- Avoid unrestricted labels such as request IDs. New combinations create more series even when each sample is small.
- Store allowed labels and series caps in a Policy DB. A Redis Cardinality Tracker checks new series before ingestion publishes them.
- Reject samples that exceed policy and record the rejection count. During prolonged overload, make any deliberate data loss visible.

Process: Enforce a metric's series limit
- 1. The Ingestion Service loads the metric policy from the Policy DB.
- 2. It filters labels under that policy and computes the resulting series identity.
- 3. The Redis Cardinality Tracker checks whether that series already exists.
- 4. For a new series, the service checks its metric's allowed series count before accepting it.
- 5. It publishes accepted samples to Kafka. Rejected samples increment a visible rejection metric and can trigger an alert.

Final Design
- Agents and Kafka buffer ingestion before consumers write the Time-Series DB. Retention and rollups control storage cost.
- The Query Service uses rollups and Redis. The Alert Service handles scheduled rules; optional Flink consumers handle urgent streaming rules.
- The Notification Service deduplicates and delivers alerts. Cardinality limits, recovery state, and independent health checks keep the platform useful during incidents.
