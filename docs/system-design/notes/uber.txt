Understanding the Problem
- The service matches riders with nearby available drivers. It then tracks acceptance, pickup, and trip completion.
- Driver locations change frequently and can tolerate some delay. Driver assignment requires stronger consistency.

Functional Requirements
- A rider can request a fare estimate from a pickup point and destination.
- The rider can accept the estimate and request a nearby driver.
- A driver can accept or reject the offer. After acceptance, the driver receives pickup and destination details.

Non-functional Requirements
- Matching should complete or fail within one minute. Location data must be fresh enough to select useful candidates.
- A driver must not receive incompatible assignments. A ride must not commit to multiple drivers.
- The scenario includes surges of 100,000 requests from one location. Retain requests and recover from worker or connection failures.

Core Entities
- Rider and Driver contain their identities, relevant profile information, and availability state.
- Fare stores the route inputs, quoted price, and estimated time. The server retrieves it by its identifier.
- DriverLocation stores recent coordinates and the last accepted update time.
- Ride stores the rider, fare, route, assigned driver, and lifecycle state. An offer records its driver, token, and deadline.

API
- POST /fare requests an estimate for a pickup point and destination. The response includes the stored fare ID.
- POST /rides accepts a fare ID. A stable request ID can prevent duplicate rides after a timeout.
- POST /drivers/location updates coordinates. The server obtains the driver ID from the authenticated session.
- PATCH /rides/{rideId} accepts or rejects an offer. An offer token prevents a late response from applying to a newer offer.
- Clients can request current ride state after reconnecting. Notifications alone do not prove the current assignment.

High-Level Design

1) Estimate and request
- The Ride Service requests route distance and travel time from the Mapping Service. It applies pricing and stores the Fare.
- A confirmed fare ID creates a requested Ride in the database. The Ride Service then starts matching.
- An estimate does not reserve a driver. The reliable-matching deep dive adds a queue to protect the later workflow.

Process: Estimate a fare
- 1. The Rider Client sends pickup and destination coordinates through the API Gateway.
- 2. The Ride Service requests distance and travel time from the Mapping Service.
- 3. The Ride Service calculates the fare. It stores the Fare record in the database.
- 4. The service returns the estimate and fare ID. No driver is reserved at this point.

Process: Create a ride from the stored fare
- 1. The rider confirms the fare and sends its ID through the API Gateway.
- 2. The Ride Service validates the request and retrieves the stored fare.
- 3. It creates a Ride with requested status. It then starts the matching flow.
- 4. The client receives the ride ID and waits for status updates. The later queue protects matching work after this stage.

2) Match and accept
- The Location Service supplies nearby available drivers. The Ride Matching Service ranks candidates by proximity and other selection rules.
- The Notification Service sends the offer to a driver through APNs or FCM. A rejection moves to the next candidate.
- The Ride Service records acceptance and returns pickup details. The consistency deep dive protects this transition against competing requests.
- A delayed acceptance must match the current offer and deadline. It must not replace a newer assignment.

Process: Offer a ride in the initial design
- 1. The Ride Matching Service asks the Location Service for nearby available drivers.
- 2. It ranks the candidates and selects the next driver.
- 3. The Notification Service sends the offer through APNs or FCM.
- 4. The Driver Client accepts or rejects the offer through the API Gateway.
- 5. The Ride Service records acceptance and returns pickup details. A rejection moves the matching flow to another candidate.
- 6. This initial flow needs the reservation checks in the consistency deep dive to prevent competing assignments.

Deep Dives

1) Location ingestion and proximity
- Redis stores current driver locations and supports geographic queries. Keep this high-volume state separate from durable trip records.
- Geographic partitioning limits each search. Include neighboring cells or shards when a rider is near a boundary.
- Record the last update time and exclude old samples. A cleanup process removes stale locations from the geographic index.
- Redis location state can recover from new driver updates. Ride and assignment records still need durable storage.

Process: Refresh a driver's searchable location
- 1. The Driver Client sends coordinates through its authenticated session.
- 2. The Location Service validates the sample and rejects an update older than the accepted position.
- 3. It updates the driver's position and last-update information in Redis.
- 4. A nearby-driver query searches the relevant geographic area. It excludes stale locations and unavailable drivers.
- 5. The matching workflow still claims a driver separately. A search result is not an assignment.

2) Manage update volume
- The Driver Client adjusts its update interval using movement and activity. A stationary driver can report less often.
- Coalesce repeated positions where only the newest sample matters. Reject updates that are older than the accepted position.
- Keep a location freshness target. Reduced update volume must not leave matching dependent on obsolete coordinates.

3) Prevent double assignment
- Atomically claim a driver before sending an offer. The source uses a Redis lock with a short acceptance timeout.
- A lock expiry alone does not stop an old worker. Final assignment must also check current ownership and driver availability.
- Commit the ride and driver states within the chosen consistency boundary. Only the current offer can release its reservation.
- A rejection or timeout permits another candidate. An old acceptance must fail its token or version check.

Process: Reserve and confirm a driver
- 1. The Ride Matching Service attempts a short reservation for the selected driver in Redis.
- 2. If the claim succeeds, it sends an offer with a unique token and deadline.
- 3. The driver accepts that specific offer. The service rechecks the deadline, token, and current driver state.
- 4. The service commits the assignment conditionally. A stale worker or expired offer cannot replace a newer assignment.
- 5. A rejection or timeout releases only the current reservation. The workflow can then try another candidate.

4) Reliable matching and timeouts
- The Match Queue retains requested rides until processing completes. Queue-based recovery protects against sudden demand and worker failure.
- Partition work geographically and scale matching workers independently. Prevent a slow request from blocking all later requests.
- Keep offer deadlines in durable state. A delayed task checks the current offer before retrying or releasing a driver.
- Temporal or Step Functions can manage retries and timeouts as an alternative workflow implementation. They are not shown in the source diagram.
- Retry within a bounded matching policy. Expand the candidate search where useful, then report failure when the policy ends.
- Client notifications describe a change. A reconnecting client still fetches authoritative ride state.

Process: Recover queued matching work
- 1. The Ride Service persists the requested ride and places recoverable matching work in the Match Queue.
- 2. A matching worker receives the ride ID and checks its current state.
- 3. The worker continues candidate selection and offer handling. It records the result before acknowledging completed work.
- 4. A failed worker leaves unfinished work available for retry. The next attempt resumes from durable ride and offer state.
- 5. A delayed timeout handler checks the current offer before releasing a reservation or selecting another driver.

Final Design
- The Ride Service stores fares and rides. Redis location data supplies candidates to the Ride Matching Service.
- The Match Queue protects pending work. Short driver reservations and conditional assignment prevent conflicting matches.
- The Notification Service sends driver offers. Durable ride state and timeout handling connect matching, acceptance, pickup, and completion.
