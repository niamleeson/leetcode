Understanding the Problem
- Build a media-sharing application with uploads, follows, and a chronological feed.
- Media delivery and feed generation have different bottlenecks and should scale separately.

Functional Requirements
- Create posts with photos or videos and a caption.
- Follow other users and fetch recent posts from followed accounts.
- Page through the feed using stable ordering.
- Ranking, messaging, and other social features are outside the core chronological-feed scope.

Non-functional Requirements
- Target feed responses below 500 ms and support roughly 500 million daily active users in the interview scenario.
- Support photos up to 8 MB and videos up to 4 GB without routing their bytes through application servers.
- Favor availability with eventual feed propagation while preserving durable posts and access controls.

Core Entities
- User identifies the account and profile.
- Post stores author, caption, creation time, media references, and processing state.
- Follow stores a directed follower-to-followee edge with indexes for both access directions.
- FeedEntry stores a recipient, post ID, and ordering key when feeds are precomputed.

API
- Create an upload session and then publish a post referencing verified uploaded media.
- Follow or unfollow an account with an authenticated request.
- Fetch the feed with a cursor and limit, returning post summaries and media URLs.
- Use a timestamp plus stable ID as the cursor so simultaneous posts do not create ambiguous boundaries.

High-Level Design

1) Publish posts
- Upload media directly to object storage using signed URLs; store lightweight post metadata in the database.
- Process videos and image variants asynchronously, then transition the post to a viewable state.
- Publish a durable post-created event to drive feed updates and other downstream work.

Process: Publish media and fan out the post
- Step 1: The client requests authorized upload instructions, transfers media directly to object storage, and submits the post metadata and media reference.
- Step 2: The service validates ownership and upload completion, then persists a pending post and schedules any required media processing.
- Step 3: Workers generate the required image or video variants and persist their outputs before making the post eligible for display.
- Step 4: A committed post-ready event reaches feed workers through a reliable event pipeline.
- Step 5: For an ordinary author, workers add the post ID to active followers' derived feed lists in retry-safe batches. Celebrity posts can remain on the read-time path.
- Step 6: The publish API or status endpoint exposes the committed post state; asynchronous fanout may continue after publication is acknowledged.

2) Follow users
- Store follow edges separately from posts and user records.
- Index by follower to find followed authors and by author to enumerate recipients during fanout.
- Handle repeated follow/unfollow requests idempotently and apply visibility rules when serving a feed.

3) Read the chronological feed
- The simplest approach fetches recent posts from followed authors and merges them by creation time.
- Fetch post IDs first, then hydrate post metadata in batches and return CDN URLs for media.
- Cursor pagination avoids expensive offsets and reduces duplication as new posts arrive.

Process: Read a hybrid feed page
- Step 1: The client requests a page with its cursor; the feed service authenticates the reader and determines applicable visibility rules.
- Step 2: It reads precomputed post IDs for ordinary followed accounts and recent posts for followed celebrity accounts.
- Step 3: The service merges candidates by stable chronological ordering, removes duplicates, and applies deletion and visibility checks.
- Step 4: It batch-fetches post metadata, filling post-cache misses from durable storage.
- Step 5: The API returns a bounded page, media URLs, and the last ordering key as the next cursor.
- Step 6: The client fetches images or video segments from the CDN independently of the feed metadata request.

Deep Dives

1) Feed latency and fanout
- Fanout on read avoids write amplification but makes reads expensive for users following many accounts.
- Fanout on write asynchronously inserts each new post ID into followers' feed lists, making common reads cheap.
- A celebrity's follower count can make write fanout excessive. Keep those posts on a read-time path and merge them with precomputed entries.
- Workers process fanout in bounded batches with retries and deduplication; a post ID should not appear twice after a retry.
- Cache feed IDs separately from shared post objects to avoid copying full post content into every recipient's cache.
- Limit feed history and rebuild or backfill inactive users instead of maintaining unlimited lists for everyone.

2) Fast media rendering
- Direct object-storage delivery is durable but can be slow for distant users; a CDN puts popular bytes closer to viewers.
- Generate appropriately sized thumbnails, image formats, and video variants rather than sending full-resolution media to every device.
- Use asynchronous processing and publish readiness state; clients should not receive links to outputs that have not been generated.
- Signed URLs and access checks remain necessary for private content even when a CDN serves the bytes.

3) Scale the system
- Partition posts and follow data around their dominant access patterns, and isolate celebrity hot spots from ordinary traffic.
- Scale feed workers using queue lag and keep ingestion responsive during fanout backlogs.
- Monitor feed latency, propagation delay, cache hit rate, and media-processing failures separately.

Final Design
- Durable post metadata and object storage form the source of truth.
- Hybrid feed fanout, shared post caches, and cursor pagination keep reads predictable.
- Background media processing and CDN delivery handle large files independently of feed computation.
