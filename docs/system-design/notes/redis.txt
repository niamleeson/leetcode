Overview
- Redis is an in-memory data-structure server commonly used for caching, counters, rankings, coordination, and messaging.
- Its speed does not remove the need to choose persistence, replication, eviction, and failure semantics for the role it plays.

Redis Basics
- Keys address strings, hashes, lists, sets, sorted sets, and other structures with operations performed near the data.
- TTL expires individual keys; eviction policies reclaim memory when capacity is reached.
- Atomic commands and short scripts can combine checks and updates without a client-side race.
- Long scripts or large blocking operations can delay unrelated clients, so keep request work bounded.

Process: Execute a key operation on its owning node
- Step 1: The client connects to Redis and, in a clustered deployment, routes the key to the node owning its hash slot.
- Step 2: The node executes the command or short atomic script against its current in-memory state; a GET checks whether an entry has logically expired.
- Step 3: A mutating command updates the relevant data structure and feeds the configured persistence and replication paths.
- Step 4: Redis returns the command result under its configured acknowledgement semantics; a normal successful write does not imply that every replica has acknowledged or a disk fsync has completed.
- Step 5: The application handles misses, ownership redirects, timeouts, and uncertain retries according to the operation's semantics rather than assuming every retried increment is harmless.

Infrastructure Configurations
- A standalone instance is simple but has one capacity and failure boundary.
- Replication provides copies and failover options; asynchronous replicas may lag and recent writes can be lost during promotion.
- Cluster partitioning spreads keys across hash slots. Multi-key operations often require related keys to share a slot.
- Snapshot or append-only persistence improves recovery, with durability and latency depending on configuration.

Performance and Caching
- Cache frequently reused values with keys that include relevant parameters and authorization scope.
- Define cache-aside or update behavior, TTL, invalidation, and protection against concurrent miss storms.
- Memory capacity, value size, network traffic, and hot keys often matter more than average command speed.
- Use batching or pipelining to reduce round trips where operations permit it.

Distributed Locks
- A basic lease uses SET with NX and an expiry plus a unique owner token.
- Release only if the token still matches; blindly deleting a lock can remove a newer owner's lease.
- Lease expiry does not stop a paused worker from resuming. Protected resources need fencing or another way to reject stale operations.
- Do not assume a Redis lock makes a payment or database update transactionally safe across failures.

Leaderboards, Rate Limiting, and Proximity
- Sorted sets support score updates, ranked ranges, and rank lookup for leaderboards.
- Define ties and keep durable score sources so the ranking cache can be rebuilt.
- Atomic scripts support token buckets or window accounting; shared keys coordinate limits across API instances.
- Geospatial commands support nearby searches, but location freshness and filtering still belong to the application.

Streams and Pub/Sub
- Streams retain ordered entries with IDs and support consumer groups, pending work, acknowledgements, and replay within retention.
- Pub/Sub delivers live messages to current subscribers and does not retain missed messages for later recovery.
- Choose Streams or another durable log when reconnects or worker crashes must recover work.
- A queue or event log still needs idempotent consumers because repeated delivery can occur.
- Building custom pub/sub from ordinary keys or lists creates subscription, cleanup, and fanout problems already handled by dedicated primitives.

Process: Consume a Redis Stream job with recovery
- Step 1: A producer appends an entry and receives its stream ID; retention and persistence determine how long that entry remains recoverable.
- Step 2: A worker reads through its consumer group, and delivered work appears in that group's pending state until acknowledged.
- Step 3: The worker applies the business effect using a stable entry/job identity and persists the outcome.
- Step 4: It acknowledges the stream entry after that outcome is safe; an acknowledgement removes pending delivery state, not necessarily the retained entry itself.
- Step 5: If the worker stops, another worker can claim sufficiently idle pending work and repeat it safely using the same deduplication identity.

Hot Keys
- Sharding distributes different keys; one heavily accessed key can still overload its owner.
- Replicate read-heavy hot values, use bounded local caches, or split aggregatable counters where semantics allow.
- Local copies introduce invalidation and freshness tradeoffs; they do not provide automatic strong consistency.

When Not to Use and Summary
- Avoid treating an evicting cache as the sole durable record for critical data.
- Large cold datasets, complex relational queries, and heavy multi-key transactions may fit another store better.
- State the data structure, access pattern, failure behavior, and memory strategy when proposing Redis, rather than using it as a generic fast box.
