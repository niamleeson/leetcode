Overview
- PostgreSQL is a relational database with transactions, constraints, flexible queries, and multiple index types.
- It is a strong starting point when related records and correctness-sensitive updates fit within one database boundary.

Read Performance
- B-tree indexes support common equality, range, and ordering queries; composite index order must match access patterns.
- Unique indexes enforce invariants such as one review per user/business pair under concurrency.
- GIN indexes support appropriate document, array, and full-text workloads; spatial extensions provide specialized geographic capabilities.
- Use EXPLAIN and measured query plans to inspect scans, joins, row estimates, and sorting rather than guessing which index helps.

Process: Execute an indexed read
- 1. The application sends a parameterized query through its connection pool.
- 2. PostgreSQL parses and plans the query, choosing scans, indexes, joins, and sorting based on available statistics and predicates.
- 3. Execution reads candidate tuples and checks visibility under the transaction's snapshot, using suitable indexes to avoid unnecessary rows.
- 4. The executor applies remaining filters and aggregation, orders or limits the result, and returns rows to the client.
- 5. A query on a replica observes that replica's replay progress; the application routes freshness-sensitive reads to a path that satisfies their requirement.

Query Optimization
- Covering indexes can avoid some table lookups, subject to visibility and query requirements.
- Partial indexes target a useful subset, such as active records, reducing index size and maintenance work.
- Cursor pagination and selective predicates avoid increasingly expensive offset scans.
- Connection pooling bounds database connection overhead; it does not fix inefficient queries or lock contention.

Write Performance
- Each write may update indexes, produce WAL, and participate in replication; unnecessary indexes make writes more expensive.
- Keep transactions short and batch operations where their atomicity and latency requirements permit.
- Bulk loading and appropriate upsert patterns reduce per-row overhead.
- Partitioning can improve pruning and lifecycle management, but partitions inside one primary do not automatically provide independent write servers.
- Monitor WAL, storage latency, checkpoints, autovacuum, and lock waits to identify the actual bottleneck.

Replication and High Availability
- Read replicas distribute read traffic and provide recovery candidates, but asynchronous replicas can lag.
- Route read-after-write or other freshness-sensitive requests to a suitable authoritative path.
- Synchronous replication improves specified acknowledgement guarantees at a latency and availability cost.
- Failover needs a single writable primary and fencing against the old primary; promoting a replica alone does not solve split brain.
- Backups and WAL-based recovery complement replication because replicas can also copy accidental deletion or bad writes.

Transactions and Concurrent Operations
- ACID transactions commit related changes together and enforce database constraints.
- A read followed by an unconditional update can still race under common isolation settings.
- Use conditional updates, unique constraints, row locks, or serializable transactions according to the invariant.
- Serializable conflicts and deadlocks require bounded whole-transaction retries.
- Avoid keeping locks open across user interaction or external network calls; represent longer claims with explicit reservation state.
- Use a transactional outbox when a committed database change must reliably produce an external event.

Process: Commit a correctness-sensitive transaction
- 1. The service begins a transaction and establishes the required isolation level and retry policy.
- 2. It obtains needed row locks or includes current-state/version predicates in the writes, then validates the business invariant against that protected state.
- 3. It updates related rows and any outbox/audit records; uniqueness and other constraints can reject invalid results before successful commit.
- 4. PostgreSQL commits according to the selected durability settings, including the required WAL flush and configured synchronous-replication acknowledgement conditions.
- 5. Only after successful commit does the service acknowledge the business operation. A rollback, deadlock, or serialization failure returns an error or causes a bounded whole-transaction retry.
- 6. Replicas apply WAL asynchronously or according to the selected synchronization mode, and background checkpoints persist dirty data pages separately from transaction commit.

When to Use and Alternatives
- Choose PostgreSQL for relational models, transactional workflows, flexible querying, and workloads an indexed primary can serve well.
- Add replicas and caches when reads dominate, and consider specialized search or analytical stores for distinct query workloads.
- Very high distributed write volume may require sharding or another storage model, with corresponding coordination costs.
- Do not replace the database solely because a design is 'large'; estimate the workload and name the limiting operation.

SQL and ACID Essentials
- Tables represent related entities, primary keys identify rows, and foreign keys enforce supported relationships.
- Atomicity means all-or-nothing transaction effects; consistency means preserving declared invariants.
- Isolation describes concurrent transaction behavior; durability concerns committed data surviving failures under the configured guarantees.
- SELECT reads data; INSERT, UPDATE, and DELETE modify it; schema and transaction commands define structure and execution boundaries.

Summary
- Start with a sound schema, explicit constraints, and query-driven indexes.
- Scale measured bottlenecks and retain clear transaction, replication, and recovery semantics as infrastructure grows.
