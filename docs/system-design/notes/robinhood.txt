Understanding the Problem
- The application displays stock prices and manages customer orders. External trading infrastructure accepts orders and reports executions.
- A displayed price, a submitted order, an external acknowledgement, and an execution are different records with different timing.

Functional Requirements
- Users can view live stock prices. They can create and cancel market or limit orders.
- Users can list their orders and inspect the latest recorded state.
- The system integrates with an external exchange interface. Designing an exchange matching engine is outside this scope.

Non-functional Requirements
- Order state needs strong consistency and durability. The target is less than 200 ms for normal price updates and order requests.
- The scenario has 20 million daily users and about five trades per user. Repeated requests must not create unintended orders.
- Minimize expensive external feed connections. Scale popular-symbol delivery separately from order processing.

Core Entities
- User identifies the authenticated customer. Symbol identifies a traded stock.
- Order contains its owner, symbol, side, quantity, type, limit price where applicable, and lifecycle state.
- Execution records a fill quantity, price, external identifier, and time. External order metadata maps provider IDs to local orders.
- Quote contains symbol, price, sequence information, and timestamp. Account and Position records are needed if portfolio management enters scope.

API
- GET /symbol/{name} returns a price snapshot. A subscription request lists the symbols for live updates.
- POST /order creates an order with a stable client request ID. Represent currency with a defined exact numeric representation.
- GET /orders lists the authenticated user's orders. DELETE /order/{id} requests cancellation of an eligible order.
- A cancellation request does not prove cancellation. The order can fill before the external system confirms the request.

High-Level Design

1) Live prices
- Direct client polling of the exchange creates redundant external calls. An internal Symbol Price Processor can share the upstream feed.
- The processor updates the Symbol Cache. The initial internal design lets clients poll the Symbol Service for current values.
- The improved Symbol Service sends an initial snapshot and later updates through SSE. Clients no longer poll for every change.
- Include timestamps or sequence information. A client must not replace a newer displayed price with an older update.

Process: Subscribe to current prices and live updates
- 1. The Symbol Price Processor receives the external price feed and updates the Symbol Cache.
- 2. The client requests a symbol subscription through the API Gateway.
- 3. The Symbol Service reads the current prices from the cache and sends that snapshot.
- 4. It keeps an SSE connection open. Later processor updates reach the client through that connection.

2) Orders
- Direct client submission leaves order tracking on an unreliable device. A server-side Order Service owns the durable local record.
- A queued dispatcher can absorb bursts, but queue delay can exceed the order target. The source selects synchronous dispatch through a gateway.
- The Order Service stores a pending order before contacting the exchange through the Order Dispatch Gateway.
- After acknowledgement, it stores the external order ID and marks the order submitted. The Trade Processor later applies execution reports.
- Stable client order IDs support recovery after a lost response. Local acceptance must not claim that the order has filled.

Process: Submit an order through the dispatch gateway
- 1. The client submits order parameters and a stable request ID to the Order Service.
- 2. The service validates the authenticated request. It stores a pending order in the Orders DB.
- 3. It sends the order through the Order Dispatch Gateway to the external exchange.
- 4. The exchange returns its order ID. The service records that ID and the submitted state.
- 5. The service returns the confirmed submission result. A timeout triggers reconciliation instead of an unchecked second order.
- 6. Later execution reports update the order through the Trade Processor. Submission is not proof of a fill.

Deep Dives

1) Scale price delivery
- The Symbol Price Processor publishes updates through Redis Pub/Sub. Each Symbol Service instance subscribes only to symbols its clients need.
- One server subscription can serve many local clients. Remove the upstream subscription when that server has no interested clients.
- Coalesce display updates if the product only needs the latest price. Keep authoritative execution events separate from that lossy path.
- Bound buffers for slow clients. After reconnecting, send a fresh snapshot instead of an unlimited backlog of old prices.

Process: Distribute a price through shared subscriptions
- 1. A Symbol Service instance records the symbols requested by its connected clients.
- 2. It subscribes to each needed Redis Pub/Sub channel once for that server.
- 3. The Symbol Price Processor updates the latest quote and publishes the change to the symbol's channel.
- 4. Interested Symbol Service instances receive the update. Each sends it to the relevant local clients.
- 5. When no local client needs a symbol, the server removes that subscription. Reconnecting clients receive a fresh snapshot.

2) Track order updates
- Partition the Orders DB by user ID. Keep a separate mapping from external order ID to local order ID and user ID.
- The Trade Processor uses that mapping to find the correct database partition and order. It applies each execution report once.
- Model pending, submitted, partially filled, filled, pending cancellation, cancelled, and rejected states explicitly.
- Preserve cumulative fills and external report IDs. Reconcile missing acknowledgements or reports with the external provider.
- Publish customer-facing changes after committing state. A notification must not announce a fill that the system failed to record.

Process: Apply an external execution report
- 1. The Trade Processor receives a report containing the external order ID.
- 2. It queries the External Order Metadata DB for the corresponding local order ID and user ID.
- 3. The user ID identifies the Orders DB partition. The processor loads the order from that partition.
- 4. It deduplicates the execution report and updates the cumulative fill and order state.
- 5. It commits the update before notifying the customer. An unresolved mapping or missing report enters reconciliation.

3) Order consistency
- Store pending intent before submission. After an uncertain response, query the provider using the stable client order ID.
- The Order Clean-up Job checks unresolved pending and cancellation states. It repairs local records from confirmed external outcomes.
- A timeout does not prove rejection. An unverified retry can create a second order.
- If funds and positions enter scope, reserve the required amount atomically with order acceptance. Fills consume only their corresponding reservation.
- Cancellation or rejection releases only the unfilled remainder. Keep transition history so audits can reconstruct what occurred.

Process: Resolve cancellation racing a fill
- 1. The Order Service records a cancellation request as pending cancellation.
- 2. It submits the request through the Order Dispatch Gateway using the provider's order ID.
- 3. The Trade Processor continues applying valid execution reports. A cancellation request cannot undo an already completed fill.
- 4. After external confirmation, the service closes only the unfilled remainder.
- 5. If the response is uncertain, the Order Clean-up Job queries external status and repairs the local record.

Final Design
- The Symbol Price Processor maintains the cache and shared price channels. Symbol Service instances send relevant updates to clients.
- The Order Service stores intent and submits through the Order Dispatch Gateway. The Trade Processor updates orders using external-ID mappings.
- The Order Clean-up Job reconciles uncertain outcomes. Stable identifiers and durable transitions support retries and recovery.
