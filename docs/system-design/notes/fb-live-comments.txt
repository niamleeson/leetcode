Understanding the Problem
- Viewers post comments on a live video. Other viewers receive them quickly. Stored history supports later joins and reconnects.
- A comment is small, but one comment can have millions of recipients. Distribution creates the main scaling challenge.

Functional Requirements
- A viewer can post a comment on a live video.
- A viewer can receive new comments and request comments posted before joining.
- After a connection failure, the viewer can recover a bounded set of missed comments.

Non-functional Requirements
- The target is less than 200 ms for typical live delivery. The scenario includes millions of viewers and high comment rates.
- Favor availability over immediate consistency. Persist accepted comments and recover from connection-server failures.
- Define comment ordering within each video. Replayed events must not appear twice in the viewer's feed.

Core Entities
- User identifies a commenter, viewer, or broadcaster. Live Video identifies the stream and its comment channel.
- Comment contains its ID, video ID, author, text, and creation time. An ordering key supports history queries.
- A subscription connects a viewer's active connection to a video. Each messaging server keeps its local subscriptions.
- A cursor records the last applied comment position. It supports pagination and recovery after a disconnect.

API
- POST /comments/{liveVideoId} creates a comment. The server obtains the user ID from the validated session token.
- GET /comments/{liveVideoId} returns a bounded history page. A cursor and page size identify the requested range.
- An SSE connection receives new comments. HTTP requests can still submit comments. WebSockets provide an alternative transport.
- Responses include comment IDs and ordering information. These let the client merge history and live events without duplicates.

High-Level Design

1) Post and store comments
- The Comment Management Service validates the request. It stores the comment in the Comments DB, using DynamoDB in the source design.
- Live publication is added later. A reliable publication record or outbox can prevent a gap after database commit.
- Organize history by video ID and ordering key. Use a consistent key schema for both writes and range queries.

Process: Store a comment
- 1. The Commenter Client sends a comment and video ID to the Comment Management Service.
- 2. The service validates the request and obtains the author from the session.
- 3. The service writes the comment to the Comments DB. It confirms acceptance after storage succeeds.

2) Deliver and read history
- The initial design polls the Comment Management Service for comments after the last received position. This creates many empty reads.
- Historical pages use a cursor to request older comments. Offset pagination can skip or repeat comments when the feed changes.
- The later push design must coordinate history with live events. Buffer events or use a shared boundary during the transition.

Process: Poll for new comments
- 1. The Viewer Client sends the last received comment position to the server.
- 2. The Comment Management Service queries the database for later comments on that video.
- 3. The server returns the new comments. The client displays them and advances its cursor.
- 4. The client repeats the request after a polling interval. This initial design trades delivery delay against request volume.

Deep Dives

1) Real-time transport
- Polling is simple, but frequent requests increase load. Infrequent requests increase delivery delay.
- SSE supports server-to-client updates over one open connection. The source uses HTTP POST for comment creation.
- WebSockets support communication in both directions. Choose them when the interaction requires that capability.
- Check proxy buffering, connection limits, and heartbeats. Neither transport supplies durable history by itself.

Process: Push comments through SSE
- 1. The viewer opens an SSE connection and selects a video.
- 2. The Comment Management Service stores a newly submitted comment in the database.
- 3. The service sends the stored comment to its connected viewers for that video.
- 4. Each client deduplicates the comment ID and adds the comment to its feed.

2) Audience fanout
- A single Redis Pub/Sub channel sends every comment to every messaging server. This wastes work on irrelevant videos.
- Partition channels by video ID. Each Realtime Messaging Server subscribes only to channels needed by its viewers.
- A Layer 7 Load Balancer can place viewers of the same video on related servers. This reduces unnecessary subscriptions.
- A Dispatcher is an alternative to pub/sub. It looks up the responsible servers and sends each comment directly to them.
- Keep routing and subscription state current as servers join or fail. ZooKeeper or etcd can hold shared coordination data.
- A viral video can exceed one server's capacity. Distribute its viewers across servers and bound buffers for slow clients.
- Redis Pub/Sub does not retain missed events. Recover missed live comments from stored history or a shared recent-history cache.

Process: Route comments with partitioned pub-sub
- 1. The Layer 7 Load Balancer routes a viewer using the video ID.
- 2. The Realtime Messaging Server records the connection. It subscribes to the Redis Pub/Sub channels needed by its viewers.
- 3. The Comment Management Service stores a new comment. It publishes the comment to the video's assigned channel.
- 4. Interested messaging servers receive the event. Each server sends it to the relevant local SSE connections.
- 5. Servers update subscriptions when their viewer population changes. Stored history supplies missed comments after a failure.

Process: Route comments with a dispatcher
- 1. A messaging server registers the videos watched by its connected viewers.
- 2. The Comment Management Service stores a new comment and sends it to the Dispatcher.
- 3. The Dispatcher looks up the messaging servers responsible for that video. It forwards the comment to those servers.
- 4. Each messaging server sends the comment to its local viewers through SSE.

3) Reconnection and overload
- On reconnect, send the last applied comment ID. Request later comments before continuing normal live delivery.
- Deduplicate overlapping history and live events by comment ID. Use ordering information to merge them consistently.
- Limit replay duration and result size. For a long absence, show a recent snapshot and allow the viewer to jump to live.
- For extreme traffic, sample comments or serve a recent-comment snapshot through a CDN. This changes the delivery target and completeness.
- The source's CDN alternative permits about one to two seconds of delay. The client can display its own comment immediately.
- Use different thresholds to enter and leave snapshot mode. Heartbeats and delayed reconnect attempts reduce repeated connection failures.

Process: Recover missed comments
- 1. The client records the last applied comment ID before a disconnect.
- 2. On reconnect, it sends that position through Last-Event-ID or an HTTP catch-up request.
- 3. The server returns a bounded set of later comments from shared history. The client buffers concurrent live events during recovery.
- 4. The client merges history and live events by their ordering keys. It removes duplicate comment IDs.
- 5. The client advances its cursor after applying each event. If replay is unavailable, it shows a recent snapshot and the gap.

Final Design
- The Comment Management Service stores comments in DynamoDB. The final source diagram uses a Dispatcher to locate interested messaging servers.
- The Realtime Messaging Service sends comments through SSE. Partitioned pub/sub is a separate alternative described in the deep dive.
- Cursor recovery, deduplication, bounded replay, and special handling for viral videos keep the viewing experience usable at scale.
