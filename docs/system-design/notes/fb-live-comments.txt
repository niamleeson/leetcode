Understanding the Problem
- Deliver comments for a live video to viewers in near real time while preserving history for later joins and reconnects.
- Comment writes are relatively small; fanout to a huge audience is the dominant scaling challenge.

Functional Requirements
- Post a comment on a live video.
- Receive comments while watching and fetch comments posted before joining.
- Recover missed comments after disconnecting.

Non-functional Requirements
- Keep delivery latency low for millions of concurrent viewers.
- Persist accepted comments and tolerate connection-server failures.
- Define ordering within a video and prevent duplicate rendering after replay or reconnection.

Core Entities
- Video identifies the live stream and its comment channel.
- Comment stores video ID, author, text, ID, and ordering position.
- Subscription maps a viewer connection to the live videos it follows.
- Cursor records the last consumed position for history and reconnection.

API
- Post a comment through an authenticated request with a retry-safe ID.
- Fetch paginated history by video ID and before/after cursor.
- Open an SSE or WebSocket subscription for new comments.
- Return comment IDs and ordering positions so the client can merge history with live events safely.

High-Level Design

1) Post and store comments
- Validate the request, persist the comment, and publish an event for fanout.
- Use reliable publication or an outbox so a crash between database commit and event publication does not permanently hide a comment.
- Index history by video and ordering key for efficient range reads.

Process: Persist and broadcast a comment
- 1. A viewer posts text and a stable request ID for a video; the API authenticates and validates the request.
- 2. The service commits the comment, its ordering key, and recoverable publication state before acknowledging acceptance.
- 3. The event pipeline publishes that committed comment to the video's shared channel.
- 4. Connection servers subscribed for that video receive the event and fan it out to their local viewers.
- 5. Clients deduplicate by comment ID and insert it according to the ordering key; slow clients follow the bounded-buffer or catch-up policy.

2) Deliver and read history
- Connection servers maintain viewer subscriptions and push new comments to their connected clients.
- The history API provides older pages independently of the live channel.
- Coordinate initial history and live subscription with a cursor or snapshot boundary to avoid a gap between the two.

Process: Join a video without a history/live gap
- 1. The viewer authenticates and subscribes to the video's live channel, establishing a cursor boundary or buffering live events while history loads.
- 2. The history service reads a bounded page ending at that boundary and returns ordered comments with a continuation cursor.
- 3. The client displays history and merges buffered or replayed live events after the boundary, removing duplicate IDs.
- 4. As new comments arrive, the client advances its last-applied cursor after displaying them.
- 5. On reconnect, it requests comments after that cursor and repeats the handoff rather than starting from an arbitrary current moment.

Deep Dives

1) Real-time transport
- Simple polling is easy but either adds delay or creates many empty requests.
- SSE fits server-to-client comment delivery while comments can still be submitted over HTTP.
- WebSockets are appropriate when bidirectional interaction is needed, but add connection and heartbeat management.
- Transport does not provide durable replay by itself; history storage remains necessary.

2) Audience fanout
- Broadcast through pub/sub to the connection servers with interested viewers, then fan out locally.
- Avoid one database read or upstream subscription for every viewer when many viewers share the same video.
- Partition channels across infrastructure, but account for a single viral video that exceeds ordinary shard capacity.
- Replicate or hierarchically distribute a hot channel, batch events where useful, and apply bounded buffers for slow clients.
- Distinguish a durable event log from ephemeral pub/sub; recover lost live notifications from persisted history.

3) Reconnection and overload
- Send a last-seen cursor on reconnect and fetch events after it, then resume live delivery.
- Deduplicate by comment ID because replay can overlap with events already displayed.
- Use sequence information to detect gaps and keep ordering stable across server handoffs.
- If an audience cannot consume every comment, define sampling, prioritization, or backlog limits explicitly rather than silently growing memory forever.
- Heartbeats and bounded reconnection backoff reduce stale connections and synchronized reconnect storms.

Final Design
- Durable comment storage and an ordered publication path support both history and replay.
- A shared fanout layer routes each video's comments to a horizontally scaled connection tier.
- Cursor recovery, deduplication, and hot-channel handling make the live experience reliable at large audience sizes.
