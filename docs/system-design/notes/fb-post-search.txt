Understanding the Problem
- Search a large corpus of social posts by keyword and order results by recency or popularity.
- Posting and liking update the primary data; a derived search index supports query patterns the primary store cannot serve efficiently.

Functional Requirements
- Create and like posts.
- Search by keyword, with multi-keyword and phrase searches as deeper requirements.
- Sort results by recency or like count and paginate them.

Non-functional Requirements
- Keep queries fast over a very large corpus and accept bounded indexing delay.
- Handle high post and like write volume, including popular terms and posts.
- Preserve visibility and deletion rules even when the search index or caches lag.

Core Entities
- Post stores author, text, creation time, visibility, and authoritative like information.
- TermPosting maps a normalized term to matching document IDs and optional positions.
- SearchDocument stores fields needed for filtering and sorting; indexing progress tracks source changes.

API
- Create a post and like or unlike it through authenticated write APIs.
- Search with query text, sort order, filters, limit, and a stable continuation cursor.
- Return post summaries and enforce access controls before exposing restricted content.

High-Level Design


1) Writes and indexing
- Persist posts and likes in the primary system, then publish change events reliably.
- Indexing workers tokenize text and update a derived inverted index.
- Track indexing versions so delayed updates cannot overwrite newer content or resurrect deleted posts.

2) Keyword retrieval
- Full table scans are unsuitable for frequent keyword searches across a large corpus.
- An inverted index maps each term to a posting list of matching post IDs.
- Partition the index and coordinate queries across relevant shards, merging bounded result sets.
- Hydrate selected results from stored search fields or batched primary/cache reads.

3) Sorting
- Recency ordering can exploit timestamps and time-partitioned data.
- Popularity ordering requires maintaining sortable like counts or ranking structures as likes arrive.
- Return stable tie-breakers in cursors because equal timestamps or counts are common.

Deep Dives


1) Read scale
- Replicate query capacity and cache popular queries or posting-list fragments where freshness allows.
- A popular term can touch enormous posting lists; bound candidate work and avoid transferring every match to a coordinator.
- Include filters, sort mode, and relevant visibility scope in cache keys.

2) Multiple terms and phrases
- AND queries intersect posting lists; OR queries union them.
- Process selective terms first to reduce intermediate candidates.
- Phrase queries need term positions or a verification phase; matching all words alone does not prove adjacency or order.

3) Write scale
- Batch indexing updates and separate post creation from frequent like-count changes.
- Popularity updates can be coalesced when a small ranking delay is acceptable.
- Keep durable change streams so rebuilding or resharding the index does not lose concurrent writes.
- Apply deletions and permission changes reliably; stale index entries must not bypass final visibility checks.

4) Storage efficiency
- Compress sorted posting lists, use compact document IDs, and avoid duplicating fields that are not needed for search.
- Partition old data by time and use retention or tiered storage according to product requirements.
- Index size, query fanout, and update cost should drive the choice of a specialized search engine versus custom infrastructure.

Final Design
- Primary post storage feeds a versioned, replayable indexing pipeline.
- Sharded inverted indexes and sortable metadata support retrieval, while query replicas and caches serve reads.
- Batched popularity updates, compressed postings, and explicit visibility checks control cost without sacrificing access correctness.
