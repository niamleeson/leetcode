The Problem
- A workflow can call several services and wait on people or external systems. One database transaction cannot cover all those operations.
- A server can crash after an external action succeeds but before it records the result. An unsafe retry can repeat that action.

Solutions

1) Single-server primitives
- The simplest API Server calls Payment, Inventory, Shipping, and Email Services in sequence. A crash can erase its in-memory progress.
- Save completed steps in an Order State DB. A callback can then reach another server, which loads the state and continues.
- Shared state alone does not restart stalled work. The application still needs ownership, retries, callback routing, and compensation.

Process: Continue an order from recorded state
- 1. The API Server loads the order's progress from the Order State DB.
- 2. It calls the next required service, such as Payment or Inventory.
- 3. It records the confirmed result before moving to the next dependent action.
- 4. A later webhook reaches the shared callback path and publishes through Pub/Sub.
- 5. An available API Server loads the order and resumes it. Separate retry and ownership logic must recover stalled work safely.

2) Saga pattern
- A saga performs a sequence of local transactions. If a later step fails, compensating actions reverse the relevant earlier effects.
- Compensation is another operation, not a rollback of history. A refund creates a new financial event after an earlier charge.
- Store saga progress durably. Both forward actions and compensations must tolerate repeated attempts.
- Identify irreversible actions and unresolved results. Some failed compensations need reconciliation or human intervention.

Process: Complete or compensate an order
- 1. The workflow records its identity and starts the payment action with a stable idempotency key.
- 2. After confirmed payment, it reserves inventory and records that outcome.
- 3. If inventory succeeds, it proceeds to shipping and confirmation under the defined dependencies.
- 4. If a later action fails permanently, it schedules compensation for affected completed actions, such as release or refund.
- 5. Compensation results are recorded and retried as needed. Uncertain outcomes remain available for reconciliation or human handling.

3) Event-driven choreography
- In choreography, workers consume events and publish the next outcomes. The sequence follows event subscriptions instead of one central coordinator.
- Kafka or Redis Streams can retain the event history. Workers resume from committed positions after failures and may process an event again.
- Correlation IDs connect related events across services. The log preserves evidence, but tracing a complex workflow still requires suitable tooling.
- Choreography fits moderately complex, loosely coupled flows. Changes in the middle require coordinated event-contract changes across neighboring workers.

Process: Advance an order through durable events
- 1. The API Server writes an OrderPlaced event to the Event Store.
- 2. Payment Workers consume it and call the Payment Service.
- 3. A confirmed callback produces PaymentCharged or PaymentFailed in the Event Store.
- 4. Inventory Workers react to PaymentCharged and publish InventoryReserved or InventoryFailed.
- 5. Shipping and Email Workers consume the outcomes they need. Payment Workers also react to InventoryFailed by issuing the required refund.
- 6. Workers record progress after recoverable work. Repeated event delivery must not repeat an already completed business effect.

4) Workflow orchestration
- In orchestration, one workflow definition selects activities, retries, timers, and compensations. Temporal records the decisions and results durably.
- The Temporal Server schedules tasks and records history. Workflow Workers run workflow code; Activity Workers perform external operations.
- Workflow decisions must replay deterministically. On recovery, recorded activity results replace completed calls, while uncertain activities may need another attempt.
- Signals and durable timers support long waits without holding a worker thread or database transaction. A later event resumes the correct workflow.
- Temporal describes workflows in code. AWS Step Functions and Google Cloud Workflows use managed state machines, with different operational and programming tradeoffs.

Process: Execute and recover a Temporal workflow
- 1. The API Server starts a workflow through the Temporal Server.
- 2. A Workflow Worker runs deterministic workflow code and requests the next activity.
- 3. The Temporal Server schedules that task for an Activity Worker.
- 4. The Activity Worker calls the external service and reports its result, which the server records in the History Database.
- 5. A Workflow Worker uses the recorded result to select the next action.
- 6. After a worker failure, replay returns recorded results for completed activities. An activity with an uncertain result may be retried safely.

When to Use
- Use workflows for payment, fulfillment, reservations, and human approval. They fit processes with several steps and meaningful partial-failure handling.
- A simple database transaction or single queued task usually does not need a workflow engine. Each workflow adds persistence and scheduling overhead.
- Choose the engine after defining retries, compensation, and wait behavior. Be ready to explain its recovery model.

Process: Wait for a driver to accept a ride
- 1. The Rider Service requests a matching workflow.
- 2. Matching Workers retrieve a nearby candidate through the workflow and ask the Driver Service to propose the ride.
- 3. The workflow waits for driver acceptance, rejection, or timeout.
- 4. Rejection or timeout causes another candidate attempt. Acceptance causes the Rider Service to receive the confirmed match.

Common Deep Dives

1) Crashes and exactly-once effects
- Record each confirmed step durably. After a crash, a replacement must know what completed and what remains uncertain.
- An activity can finish externally while its completion report is lost. The engine may then attempt that activity again.
- Use stable idempotency keys or provider status lookup for repeated attempts. Retain uncertain in-progress outcomes for reconciliation.
- Durable orchestration does not make an arbitrary payment or email execute exactly once. The external effect needs its own protection.

2) Workflow changes
- Old workflow histories must remain compatible with the code that replays them. Version or patch behavior when changing the sequence.
- Keep old worker versions for existing workflows when needed. A migration must define how in-flight executions reach the new behavior.
- Include workflows waiting on timers and signals in deployment checks. Testing only new executions misses replay failures.

3) History size and external events
- Keep large data outside workflow history. Pass durable identifiers that an activity can use to retrieve the payload.
- Bound long-running histories with supported continuation mechanisms. Temporal Continue-as-New starts a new run with selected current state.
- Correlate callbacks with the workflow ID. Validate and deduplicate signals so repeated or late callbacks do not advance the wrong process.
- Use durable timeouts for external waits. Define reminder, cancellation, and human-resolution paths when the expected event does not arrive.

Conclusion
- A reliable workflow needs durable state and retry-safe actions. An in-memory function alone cannot provide crash recovery.
- Compensation, idempotency, compatible code changes, and reconciliation make cross-service workflows recoverable. The engine manages progress; activities still own their effects.
