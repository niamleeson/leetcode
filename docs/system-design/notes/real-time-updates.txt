The Problem
- Deliver new information to interested clients quickly. Repeated database polling becomes expensive when many clients need frequent updates.
- Solve two paths separately: server to client, and update source to the server that holds the client connection.

The Solution
- Select a transport from the required direction, frequency, and latency. Every proxy on the path must support that transport.
- A live connection does not retain history. Store events separately when clients must recover updates missed during a disconnection.

Client-Server Connection Protocols

1) Networking and load balancers
- IP routes packets. TCP provides an ordered connection, while HTTP defines application requests and responses; connection setup adds latency.
- A Layer 4 Load Balancer routes using transport information such as addresses and ports. It does not inspect application messages.
- A Layer 7 Load Balancer can inspect HTTP requests and choose an upstream service. It can terminate the incoming connection.
- Configure timeouts and keepalives for persistent connections. Plan for reconnects when a deployment drains or closes those connections.

2) Polling and long polling
- Simple polling requests current data at a fixed interval. Shorter intervals improve freshness but produce more requests, including empty responses.
- Long polling holds a request until an update arrives or a timeout occurs. After the response, the client opens another request.
- Reopening long polls adds delay when updates arrive close together. Use a cursor and retained updates to cover gaps between requests.
- Polling is suitable when a few seconds of delay is acceptable. It also works well for brief waits on asynchronous work.

3) SSE and WebSockets
- SSE sends server events through an open HTTP response. It fits one-way updates such as notifications, dashboards, and generated text.
- EventSource can reconnect with the last event ID. The server still needs retained events to replay what the client missed.
- WebSockets carry messages in both directions on one connection. They fit frequent interactive exchanges such as chat, games, and document editing.
- A dedicated WebSocket Service can manage connections while application services remain stateless. Authenticate subscriptions and bound slow-client buffers.

Process: Deliver a driver update through a WebSocket service
- 1. The client establishes a WebSocket connection through the Layer 4 Load Balancer to the WebSocket Service.
- 2. The WebSocket Service keeps the connection and associates it with the authorized user.
- 3. The Driver Service sends an update intended for that user.
- 4. The WebSocket Service forwards the update through the existing connection. The client applies it to its local display.

4) WebRTC
- WebRTC can connect peers directly for media or data transfer. A Signaling Server helps peers exchange connection information.
- A STUN Server helps discover reachable addresses. A TURN Server relays traffic when the peers cannot establish a direct connection.
- Peer connections reduce central bandwidth but add setup and network complexity. Use them when media or peer communication justifies that cost.

Process: Connect two peers
- 1. Each client contacts the Signaling Server and discovers the other peer.
- 2. The clients use STUN to discover reachable addresses and exchange connection candidates through signaling.
- 3. They attempt a direct peer connection with that information.
- 4. If the direct path fails, a TURN Server relays their traffic.
- 5. The connected peers exchange media or data and refresh connection information as needed.

Server-Side Push and Pull

1) Pull from shared state
- An update source writes shared database state. A client poll causes the server to read new records and return them.
- This separates producers from clients but adds polling delay and database reads. Estimate total poll traffic before choosing its interval.

2) Route by ownership
- Assign each user or resource to a connection server. An Update Server can then route events to that owner.
- Simple modulo hashing changes many assignments when the server count changes. Consistent hashing moves only affected portions of the keyspace.
- ZooKeeper or etcd can distribute server membership. During reassignment, coordinate old and new owners and reconnect affected clients.
- A hot user or channel can still overload its owner. Evenly distributed keys do not guarantee evenly distributed traffic.

Process: Send an update to the connection owner
- 1. The Update Server obtains the current server membership and routing information from ZooKeeper.
- 2. It hashes the destination user ID to identify the responsible connection server.
- 3. It sends the update to that server.
- 4. The destination server finds the user's existing connection and forwards the update.
- 5. Changes in membership require coordinated reassignment and reconnects. Hashing alone does not move an active connection.

3) Pub/sub
- An Endpoint Server subscribes to topics for its connected clients. Publishers send updates to Redis Pub/Sub or another suitable broker.
- The broker routes events without requiring the publisher to know each connection owner. It adds subscription state, capacity needs, and another network hop.
- Redis Pub/Sub drops messages when subscribers are absent. Retained history or Redis Streams can support replay when the product requires it.
- Track which local clients need each upstream topic. Reuse subscriptions and remove them when no local client needs them.

Process: Register a connection for shared updates
- 1. A client connects to any available Endpoint Server.
- 2. The Endpoint Server associates the client with its authorized topics.
- 3. It subscribes to those topics in Redis Pub/Sub and records the local topic-to-connection mapping.
- 4. Several local clients can share the same upstream subscription when they need the same topic.

Process: Forward a published update to clients
- 1. The Update Server publishes an event to the relevant Redis Pub/Sub topic.
- 2. Redis sends the event to connected Endpoint Servers subscribed to that topic.
- 3. Each Endpoint Server looks up its interested client connections.
- 4. It forwards the event over those connections. A disconnected subscriber needs a separate retained-history path to recover missed events.

Common Deep Dives
- Use heartbeats to detect dead connections. On reconnect, authenticate and resume after a cursor or fetch a current snapshot.
- Route related events through one owner or partition when strict ordering is necessary. Independent wall clocks do not establish that order.
- For a large audience, aggregate incoming events and distribute updates through Broadcast Nodes. Bound each component's work and client buffers.
- Stagger reconnect attempts with backoff and jitter. This prevents all disconnected clients from immediately overloading replacement servers.

Process: Recover a disconnected stream
- 1. A heartbeat failure or transport error causes the client to reconnect with backoff.
- 2. The client authenticates and presents its last applied event cursor.
- 3. The server replays retained events after that cursor, then joins live delivery without leaving a gap.
- 4. The client ignores duplicate event IDs and checks the expected ordering before advancing its cursor.
- 5. If retained history no longer covers the cursor, the client fetches a supported snapshot and resumes from that state.

Process: Aggregate and distribute a high-volume channel
- 1. Write Processors receive comments or like events for their assigned keys.
- 2. Each processor combines updates over a short window and sends a batch to the Root Processor.
- 3. The Root Processor merges those batches into the shared channel update.
- 4. It sends the result to Broadcast Nodes instead of contacting every viewer itself.
- 5. Each Broadcast Node forwards the update to its local clients.

When to Use and Conclusion
- Start with the simplest transport that meets the required freshness. Use SSE for one-way updates and WebSockets for frequent bidirectional messages.
- Explain both routing paths, then address ordering, reconnects, and overload. A protocol name alone does not describe the whole system.
- Keep polling where its delay is acceptable. Add persistent delivery when it provides a required product benefit.
