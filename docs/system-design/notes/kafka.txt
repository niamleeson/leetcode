Overview
- Kafka is a distributed event log. It separates producers from consumers, retains events, and supports replay.
- A consumer group can distribute work between consumers. Separate groups can each process the same retained events.

A Motivating Example
- Producers publish sports events. Consumers read those events and update the website.
- Use a match ID as the key to keep one match's events in one partition. Different partitions can run in parallel.
- Consumer groups distribute partitions between workers. Separate topics keep soccer events separate from basketball events.

Basic Terminology and Architecture
- A broker stores partition replicas and serves clients. A topic groups partitions for a logical event stream.
- Each partition is an ordered, append-only log. An offset identifies a record's position within that partition.
- Within one consumer group, each partition has at most one active consumer. Other groups maintain their own assignments and progress.
- Kafka preserves partition order. It does not automatically create one order across all partitions in a topic.

How Kafka Works
- A record contains a value and can include a key, timestamp, and headers. The producer uses a partitioning strategy.
- The partition leader accepts writes. Followers copy the log. Acknowledgement and in-sync replica settings determine the write's failure guarantees.
- Consumers fetch records and track their positions. Each group commits its progress independently from producer writes.
- Committing before processing can skip unfinished work after a crash. Committing after processing can repeat work whose effects already succeeded.
- Reading a record does not delete it. Retention limits or compaction control how long log data remains available.

Process: Publish a record and advance consumer progress
- 1. The producer selects a partition, usually from the event key. Cluster metadata identifies the broker that hosts its leader.
- 2. The leader appends the record. Followers replicate it, and Kafka acknowledges the write under the configured policy.
- 3. The consumer assigned to that partition fetches records in offset order.
- 4. The consumer performs the application work. It makes the required output or checkpoint recoverable.
- 5. For at-least-once processing, it commits the next position only after that recovery boundary.
- 6. After a crash or reassignment, a consumer resumes from committed progress. Work completed before an offset commit can repeat.

Scalability
- A group's partition count limits its parallelism. Consumers beyond the number of assigned partitions have no partition to process.
- Choose keys for both ordering and load distribution. A popular key can overload one partition.
- Batch and compress records to reduce network and storage overhead.
- Store large files in object storage. Put their locations in Kafka records instead of transferring the file bytes through Kafka.
- Adding partitions can change key routing. Plan the transition when events for a key must retain their order.

Fault Tolerance and Durability
- Replicas provide replacement leaders after broker failures. Recovery depends on the acknowledgement, replica, and election policies.
- Choose replication factor, acknowledgements, and minimum in-sync replicas for the permitted data loss. Kafka is not immune to outages.
- A consumer failure causes partition reassignment. The new consumer resumes from committed progress and can repeat unfinished attempts.
- Monitor consumer lag and retained capacity. A long outage must not exceed the retention needed for recovery.

Handling Retries and Errors
- Idempotent production prevents certain duplicate appends after producer retries. It uses producer identity and sequencing.
- Consumer side effects still need idempotency or compatible transactions. Producer idempotence alone does not make the complete pipeline exactly once.
- Define a retry policy for temporary failures. Move repeatedly failing records to a retry topic or dead-letter topic when appropriate.
- A separate retry path can change processing order. Decide whether a failed record blocks its partition or leaves the main path.

Process: Move failed records through retry and dead-letter topics
- 1. A consumer reads a record from the main topic and tries to process it.
- 2. After the configured initial failures, it sends the record to the retry topic. The handoff must succeed before it advances past unfinished work.
- 3. A retry consumer attempts the same logical operation under the retry policy. It preserves the record's business identity.
- 4. If processing succeeds, it records safe progress. External effects must tolerate any repeated attempt.
- 5. After the final failure, the system moves the record to the dead-letter topic for investigation.

When to Use and Summary
- Use Kafka for retained event pipelines, stream processing, and multiple independent consumers.
- A simpler work queue can provide easier delayed delivery, visibility timeouts, and per-message retries.
- Explain the partition key, consumer groups, offset commits, retention, and failure behavior. These choices determine how the pipeline operates.
