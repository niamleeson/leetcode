Understanding the Problem
- The system returns posts from followed accounts in reverse chronological order, with the newest post first.
- The main choice is when to build feeds. The system can assemble them during reads or distribute post IDs during writes.

Functional Requirements
- Users can create posts and follow accounts.
- Users can view posts from the accounts they follow.
- Users can request older feed pages without repeatedly receiving the same entries.
- Personalized ranking, reactions, and restricted post visibility are outside the initial scope.

Non-functional Requirements
- Posting and feed requests should take less than 500 ms, even when users follow many accounts.
- The scenario contains two billion users. It does not impose a fixed limit on follows or followers.
- The feed favors availability and permits up to one minute of post delay. Posts and follow relationships need durable storage.

Core Entities
- User identifies an account. Post records durable content, the author ID, and creation time.
- Follow is a directed relationship. The design supports queries for both followed accounts and an author's followers.
- FeedEntry records a recipient, post ID, and ordering value. It is a derived record that the system can rebuild.
- A separate post cache lets many feeds share one post object instead of duplicating all its content.

API
- POST /posts creates a post. The service returns the post ID after the durable write succeeds.
- PUT /users/:id/follow follows an account. Repeated requests have the same effect as one request.
- GET /feed accepts a cursor and page size. The response contains posts and a continuation cursor.
- A timestamp plus post ID gives stable ordering when timestamps match. New posts do not shift a previously issued cursor.

High-Level Design

1) Posts and follows
- The API Gateway routes writes to stateless Post Service and Follow Service instances. DynamoDB stores their records.
- The Follow table indexes the follower and followed account. Its reverse index supports queries for all followers of an author.
- The initial Post Service only persists posts. The fanout deep dive adds a queue and workers after that write.

Process: Create a durable post
- 1. The author submits a post through the API Gateway.
- 2. The API Gateway forwards the request to a Post Service instance.
- 3. The Post Service inserts the content, author ID, and creation time into DynamoDB.
- 4. After the write succeeds, the service returns the post ID. Later deep dives add asynchronous feed distribution.

Process: Follow an account
- 1. The authenticated client sends a follow request for the target account.
- 2. The Follow Service writes the directed relationship to the Follow table.
- 3. The primary index supports queries by follower. The reverse index supports queries by followed account.
- 4. The service returns success. A repeated request retains the same relationship.

2) Assemble and paginate feeds
- The Feed Service first lists followed accounts. It reads their recent posts and sorts the combined result by creation time.
- The post index groups records by author and orders them by creation time. This avoids a full post-table scan.
- The cursor identifies the oldest returned position. The next request selects posts older than that position.
- The post store remains separate from feed entries. An edit does not require a copy of the full post in every feed.

Process: Assemble the initial feed page
- 1. The reader sends a cursor and page size to the Feed Service through the API Gateway.
- 2. The Feed Service lists the accounts that the reader follows.
- 3. It uses the post index to fetch those authors' posts older than the requested cursor.
- 4. It merges the results with the newest first. It returns one page and a cursor for the oldest returned position.

Deep Dives

1) Users following many accounts
- PrecomputedFeed stores recent post IDs for each recipient. The write path adds new posts to the appropriate feeds.
- The Feed Service can read one recipient's list instead of querying every followed author.
- The example keeps approximately 200 entries per user. An older-page fallback can query the original post and follow tables.
- Precomputation uses extra storage and write capacity to reduce read latency. Activity-based policies can avoid unnecessary work for inactive readers.

2) Users with many followers
- A synchronous write to millions of feeds delays post creation. One Post Service instance cannot efficiently perform all this work.
- A queue such as SQS distributes work to Feed Workers. Large follower sets need smaller tasks and retry-safe writes.
- The hybrid design skips write fanout for celebrity accounts. The Feed Service merges their recent posts with the precomputed feed.
- A flag records whether an account uses precomputation. The threshold depends on follower count, workload, and the allowed propagation delay.

Process: Distribute ordinary posts and merge celebrity posts
- 1. The Post Service saves the post. It places the post and creator IDs on the Post Create Queue.
- 2. Feed Workers look up the author's followers. They skip relationships whose precomputed flag is disabled.
- 3. Workers insert the post ID into the remaining recipients' feed lists. A retry must preserve one entry per recipient and post.
- 4. At read time, the Feed Service reads the recipient's precomputed entries.
- 5. It also fetches recent posts from accounts that bypass precomputation.
- 6. It merges both sets in reverse chronological order. It reads post content and returns the requested page.

3) Uneven post reads
- A cache partitioned by post ID spreads different posts across nodes. One viral post can still overload its assigned node.
- Independent Post Cache instances can each store the same post. A load balancer spreads requests across those instances.
- This replication increases hot-post read capacity. More partitions alone do not divide requests for one hot key.
- Each cache instance fills its own misses from DynamoDB. Request coalescing can further limit repeated reads during a sudden miss burst.
- Edited posts require cache invalidation. If restricted visibility is added, cached content must also obey current access rules.

Process: Read a hot post through replicated caches
- 1. The Feed Service requests the selected post IDs through the Post Cache layer.
- 2. A load balancer spreads requests across independent cache instances. Different instances can hold the same post.
- 3. A cache hit returns the stored post. A miss reads the post from DynamoDB and fills that cache instance.
- 4. The Feed Service assembles the metadata response. Each instance limits stale data with expiration and edit invalidation.

Final Design
- DynamoDB retains post and follow records. A Post Create Queue feeds asynchronous workers that maintain derived feed lists.
- The Feed Service merges precomputed posts with celebrity posts. It reads the selected content through the replicated Post Cache.
- Stable cursors, bounded feed lists, and retry-safe fanout limit repeated work. The database remains the source for rebuilding cached data.
