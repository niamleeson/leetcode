What Is an API Gateway?
- An API gateway is a shared entry point that routes client requests to backend services.
- It can apply common middleware without forcing every client to understand the internal service topology.
- Request routing is its primary role; additional responsibilities should serve a concrete requirement.

Core Responsibilities and Request Flow
- Validate the request, apply middleware, select a backend, forward the request, and return or transform the response.
- Keep gateway behavior bounded so a common entry point does not become a central business-logic bottleneck.

Process: Route one client request end to end
- 1. A load balancer sends the incoming request to a gateway instance, which terminates or handles the configured transport connection.
- 2. The gateway validates request shape and limits, then applies configured identity, authorization-scope, and rate-limit middleware before expensive backend work.
- 3. It matches the path, method, or routing metadata to a backend service and selects a healthy instance.
- 4. If an authorized compatible response-cache hit is available, it can return that response without calling the backend; otherwise it forwards the request with bounded deadlines and trusted context.
- 5. The backend performs domain validation and business work and returns its result; the gateway does not replace the backend's resource-specific checks.
- 6. The gateway applies configured response headers or transformation, caches only eligible responses under the correct key, and sends the result to the client.
- 7. A backend timeout follows an explicit retry/idempotency policy; the gateway must not blindly retry an uncertain non-idempotent action.

1) Request Validation
- Check supported routes, methods, required headers, body shape, and request-size limits.
- Reject malformed requests early, while leaving domain-specific validation in the service that owns the data.
- Validation at the gateway does not replace service authorization for the requested resource.

2) Middleware
- Common tasks include authentication, rate limiting, TLS termination, logging, tracing, CORS, and timeout enforcement.
- Authenticate tokens using a trusted configuration and forward verified identity through a protected internal contract.
- Scope rate limits appropriately by user, tenant, API key, or resource rather than assuming one global rule fits all traffic.
- Avoid logging secrets or sensitive request bodies as a side effect of central traffic visibility.

3) Routing
- Match paths, methods, headers, or versions to the appropriate backend service.
- Integrate routing with service discovery and backend health information where needed.
- Separate client-to-gateway load balancing from the gateway's distribution across backend instances.

4) Backend Communication
- Forward over HTTP or another supported internal protocol, with connection pooling and bounded timeouts.
- Protocol translation can hide internal differences, but adds complexity and is not required for every architecture.
- Retries must respect operation idempotency; retrying a timed-out payment request blindly can duplicate its effect.

5) Response Transformation and Caching
- Normalize response formats or headers where the client contract requires it.
- Cache reusable responses only with correct keys, freshness rules, and authorization boundaries.
- Personalized responses must not leak across users through a shared cache entry.
- TTL or invalidation limits staleness; cache failure needs a bounded fallback path to backend services.

Scaling an API Gateway
- Run stateless gateway instances behind a load balancer and keep routing/policy configuration synchronized.
- Deploy regional entry points when geographic latency and availability justify them.
- Persistent streaming or WebSocket connections require suitable proxy buffering, timeouts, and graceful draining.
- Rate-limit or shed load before downstream overload propagates through the gateway.

Managed and Self-Hosted Options
- Managed gateways reduce operational work and integrate with cloud identity and monitoring, at the cost of service limits and usage pricing.
- Self-hosted gateways offer more control but require ownership of upgrades, scaling, availability, and configuration rollout.
- The interview decision should focus on required behavior rather than a catalog of product names.

When to Propose One
- A gateway is useful when clients need a stable facade over multiple services and shared request policies.
- A simple application with one backend may not benefit from another routing layer.
- Explain routing and essential middleware briefly, then spend design time on the application's harder data and coordination problems.
