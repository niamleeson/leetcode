Understanding the Problem
- Accept merchant payment requests, coordinate external payment processing, and expose reliable payment status.
- External networks are asynchronous: a timeout can leave an unknown outcome, and retries must not cause duplicate charges.

Functional Requirements
- Let merchants create payment requests and customers pay with cards.
- Track and expose payment lifecycle status.
- Deliver asynchronous merchant updates, including webhooks where required.

Non-functional Requirements
- Preserve durable, auditable transaction history and financial integrity.
- Protect payment credentials and isolate sensitive handling from ordinary application services.
- Scale to high transaction volume while retaining a clear correctness boundary for each payment.

Core Entities
- PaymentIntent describes amount, currency, merchant, customer, and requested operation.
- PaymentAttempt records an external submission, idempotency key, provider reference, and outcome.
- LedgerEntry records durable financial movement; state transitions and webhook events retain an audit trail.
- PaymentMethod stores a provider token or reference rather than exposing raw credentials throughout the system.

API
- Create a payment intent with amount, currency, merchant reference, and an idempotency key.
- Confirm or submit a payment method through an appropriate tokenized flow.
- Query payment status and register authenticated webhook endpoints.
- Reject reuse of an idempotency key with incompatible parameters instead of treating it as a new payment.

High-Level Design

1) Create and execute payments
- Validate and durably store the payment intent before coordinating external work.
- Use an explicit state machine for pending, processing, successful, failed, and unresolved states.
- Persist the attempt and provider request identifier so a crash does not erase knowledge of an in-flight charge.
- Use a durable workflow or queue for retries and reconciliation; do not hold a database transaction open while waiting for a payment network.

Process: Create, submit, and confirm a payment
- Step 1: The merchant creates an intent with amount, currency, and an idempotency key; the API validates merchant authority and request parameters.
- Step 2: The service commits the intent and returns its ID. Reusing the key with the same parameters resolves to that intent rather than a second charge request.
- Step 3: The customer supplies a payment-method token through the supported collection flow and confirms the intent.
- Step 4: A durable workflow records a payment attempt and stable provider key before sending the external authorization or charge request.
- Step 5: The provider responds or sends a verified callback. The workflow deduplicates the result and applies only valid payment-state transitions.
- Step 6: The system commits the resulting financial and payment records under their defined transaction boundary, retaining the audit trail.
- Step 7: Only then does it publish merchant/customer status updates. Accepted or processing status is not reported as a successful payment before the outcome is known.

2) Status updates
- Apply provider callbacks idempotently and verify their authenticity.
- Persist status transitions before notifying the merchant or customer.
- Poll or reconcile with the provider when callbacks are missing, delayed, or contradictory.
- A network timeout is an unknown outcome, not definitive proof of failure.

Deep Dives

1) Security
- Use tokenization or hosted collection to minimize where raw card data is handled.
- Encrypt sensitive data in transit and at rest, restrict service access, and keep secrets out of logs.
- Authenticate merchants and callbacks and validate amounts and ownership on the server.
- Separate security boundaries and operational responsibilities explicitly rather than assuming encryption alone protects the workflow.

2) Durability and auditability
- Write immutable financial records and use compensating entries for corrections instead of erasing history.
- Keep ledger invariants within transactional boundaries and distinguish ledger state from a mutable UI status.
- Replication, backups, and tested recovery protect records; an event log also enables investigation and reconciliation.

3) Transaction safety
- Deduplicate customer requests, worker retries, and provider callbacks at their respective boundaries.
- Use provider-supported idempotency and query existing attempts before issuing an uncertain replacement charge.
- Reconcile local records with provider settlement or status reports to identify missing and mismatched outcomes.
- Exactly-once queue processing does not by itself guarantee exactly one external financial side effect.

Process: Resolve an uncertain external charge
- Step 1: The outbound call times out after submission, leaving an attempt whose external outcome is unknown.
- Step 2: The workflow retains the attempt and provider identity and marks it unresolved instead of assuming no charge occurred.
- Step 3: It queries provider status or retries the same logical request using supported provider idempotency.
- Step 4: A confirmed outcome is applied once to payment state and relevant ledger records; duplicate callbacks resolve to the same result.
- Step 5: If automated resolution fails, reconciliation or manual handling retains the pending evidence rather than issuing an unrelated replacement charge blindly.

4) Scale and webhooks
- Partition independent payment workflows while keeping each payment's transitions serialized.
- Deliver webhooks through a durable queue with signatures, event IDs, retry backoff, and delivery history.
- Merchants must tolerate duplicate and out-of-order webhooks; expose an API for fetching current authoritative status.
- Isolate slow merchant endpoints and providers so they do not block unrelated payments.

Process: Deliver a committed payment event to a merchant
- Step 1: A payment transition commits together with recoverable notification intent.
- Step 2: A publisher enqueues a stable webhook event ID, and a delivery worker signs the payload for the merchant endpoint.
- Step 3: The worker sends the event with bounded timeout and records the response as a delivery attempt.
- Step 4: Failed or uncertain deliveries retry with the same event identity and backoff; one slow merchant does not block other endpoints.
- Step 5: The merchant deduplicates events and can fetch current payment status when events are delayed or reordered.

Final Design
- Durable intents, attempts, and ledger records form the source of truth.
- Retry-safe workflows coordinate external providers, with reconciliation resolving uncertainty.
- Tokenized credential handling and asynchronous status delivery support scale without weakening transaction safety.
